# З. От model forward к приложению: state, tools и retrieval

[Оглавление](README.md). Блок D.1–D.6; общая механика без привязки к одному framework API.

**Основа:** S5, строки 1038–3041; S6, 4–2197. В S6:179–181 вы прямо уточнили: сейчас изучается материал, а не создаётся агент. Поэтому ниже учебная система, без утверждений о вашем deployment. **Углубление:** явный state machine и границы ответственности.

**Уровень:** Основа application branch. **Предпосылки:** D1/D6; adaptation is not required. **Используют:** E1–E5; F1/F4.

## 1. Какие компоненты добавляются вокруг модели

Один model call возвращает текст/структуру. Приложение должно получить user input, подготовить context, при необходимости найти документы, исполнить проверенные tools, сохранить state и завершить результат. Orchestration задаёт порядок/условия этих операций.

Linear chain подходит для фиксированного пути `retrieve→generate→validate`. Graph/state machine нужен, когда есть branches, retries, tool loop и early termination. Model weights от изменения graph не обновляются: runtime исполняет существующую policy, обучение policy требует отдельного objective/data.

Пример state:

```text
question, authorized_scope, messages, evidence,
pending_calls, observations, attempts, budget, status.
```

Trusted constraints, например права на документы, задаются приложением. Их нельзя заменять модельным summary из chat history. Node получает нужные поля и возвращает определённые изменения; merge policy для parallel updates должна быть явной.




**Схема курса:** request → state/router → model proposes tool or retrieval → validate/execute → observation/evidence → state update → stop, retry or answer

### 1.1. Три уровня, которые были смешаны в вопросах чата

В S5 вопрос был конкретным: как использовать скачанную в Ollama модель для агента, циклов и инструментов? Сначала разделим веса модели, её endpoint и приложение. Веса задают обученную функцию предсказания. Inference backend загружает их, токенизирует вход, выполняет forward и decoding. Приложение хранит цель и историю, выбирает доступные операции и связывает последовательные обращения. Один продукт может объединять несколько уровней, но от этого их функции не становятся одинаковыми.

Путь одного решения выглядит так:

```text
trusted task + current state + tool descriptions
                    ↓ serialization / chat template
           tokens → Transformer → next-token scores
                    ↓ sampling / constrained decoding
          assistant message or proposed tool calls
                    ↓ parser + application validation
        executor → real observation → updated state
                    └──────── next model request
```

Стрелка назад — работа runtime. Внутри одного forward нет скрытого Python-цикла, который автоматически обращается к поиску. После tool result выполняется новое обращение с обновлённым контекстом; backend может переиспользовать совместимый prefix KV cache. Это экономия вычислений, а не замена observation воображаемым результатом. Веса при каждом таком шаге остаются прежними.

Workflow и agent различаются тем, кто задаёт следующий шаг. Для workflow разработчик заранее определил допустимые ветки, например «поиск → ответ → проверка». В agent loop модель может выбирать среди предложенных действий. В обоих случаях runtime определяет исполнимые переходы и пределы. Graph способен выразить оба варианта: наличие графа ещё не означает автономный выбор модели. Такую границу использует и [документация LangGraph о workflows и agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents).

### 1.2. State — больше, чем текст переписки

Messages нужны для model context. State нужен для корректного исполнения. Помимо текста, в нём могут находиться идентификатор задачи, версия данных, разрешённый scope, множество уже прочитанных документов, pending calls, результаты проверок, остаток бюджета и terminal status. Часть полей сериализуют для LLM, часть использует только программа. Пароль, объект подключения к БД и mutable client session не следует превращать в обычные слова prompt ради «полноты памяти».

Различаются три вида памяти. Working context — то, что модель видит сейчас. Durable state — сохранённое состояние выполнения, позволяющее продолжить после сбоя. Knowledge store — документы и индекс для retrieval. Сохранить checkpoint не означает обучить модель новым знаниям; заменить context summary не означает изменить документы; заново загрузить веса не означает восстановить потерянные результаты tools.

Особенно важна роль summary. Оно может сжать старые рассуждения и observations, но не должно самовольно менять права или статус операции. Например, фраза summary «доступ ко всем документам разрешён» не заменяет authoritative scope. Для фактов сохраняют IDs и versions, чтобы итог можно было проверить независимо от пересказа. Для pending external operation сохраняют её identity, а не только слова «кажется, сделали».

### 1.3. Graph как явная машина состояний

В учебной машине есть состояния `READY`, `CALL_PENDING`, `OBSERVED`, `ANSWER_READY`, `DONE`, `FAILED`. Из READY модель предлагает call или answer. После проверки call переходит в CALL_PENDING; исполнитель создаёт observation, и управление возвращается к READY через OBSERVED. Candidate answer проходит проверку, после которой наступает DONE либо допустимая ветка исправления. Исчерпание бюджета переводит в FAILED/partial с объяснением, а не в фиктивный успех.

Смысл state machine — сделать переходы проверяемыми. Из CALL_PENDING нельзя честно перейти в «tool succeeded», пока нет подтверждённого result. Из ANSWER_READY нельзя объявить наличие цитаты, если cited ID отсутствует в evidence. Программный validator может проверять эти условия даже тогда, когда модель уверенно пишет обратное.

Фиксированный pipeline тоже имеет state, хотя его иногда прячут в локальные переменные. Graph полезен при усложнении ветвлений, но не обязан заменять простую функцию из трёх шагов. Разница в явности control flow и persistence, а не в магической способности graph «думать лучше».


## 2. Один tool loop по шагам

Модель предлагает `search_documents(query,limit)`. Приложение проверяет known tool name, types/ranges, scope и remaining budget. После реального исполнения observation содержит найденные IDs/snippets или structured error. Это возвращается модели как tool result, а не как новая управляющая инструкция.

Повторить call можно по policy: temporary read failure допускает bounded retry, invalid args требуют correction, отсутствие права не исправляется бесконечными attempts. После enough evidence модель создаёт final answer; после лимита шагов система завершает задачу понятным partial/failure status.

Call ID связывает request и observation, особенно при нескольких parallel tools. Timeout не доказывает, что внешнее действие не произошло. Поэтому retry mutable operation требует idempotency/сверки состояния. Read-only учебная среда упрощает этот риск, но concept нужен для понимания production.

Tool description и schema — interface, не training. Если маленькая локальная модель плохо соблюдает tool format, framework не создаёт способности автоматически. Нужно проверить native template, parser, supported schema и примеры prompt, затем при необходимости адаптировать model/data.


### 2.1. Как next-token модель выбирает инструмент

Название функции, описание задачи, параметры и предыдущие observations входят в сериализованный model input. Для обычного autoregressive decoder вероятность последовательности вызова факторизуется так же, как вероятность текста:

$$
p_\theta(y\mid x)=\prod_{t=1}^{|y|}p_\theta(y_t\mid x,y_{<t}).
$$

Если обучающий контекст связывал запросы о текущей погоде с соответствующим tool call, веса могут увеличить вероятность такого продолжения. Но модель не видит живую погоду только потому, что в названии инструмента есть weather. Она предлагает аргументы; наблюдение появляется после реального исполнения. Для вычислений инструмент полезен как проверяемый внешний алгоритм, хотя утверждение исходника «LLM не умеет считать вообще» слишком категорично: модель может решить отдельные примеры, но это не универсальная гарантия точной арифметики.

**Исправление S5:** tool calling не требует универсального отдельного tool head рядом с text head. В распространённой схеме тот же vocabulary projection выдаёт токены текстового протокола вызова. Маркеры и шаблоны зависят от семейства модели; перечисленные в чате `<|tool_call|>`, `<|tool_sep|>`, `<|tool_end|>` нельзя считать общим стандартом всех моделей. По внешнему API закрытой модели нельзя достоверно восстановить её внутреннюю архитектуру. [Qwen описывает function calling через протокол и chat templates](https://qwen.readthedocs.io/en/latest/framework/function_call.html).

На другом уровне может существовать отдельный классификатор/router, выбирающий функцию, модель или ветку. Это допустимое архитектурное решение приложения. Оно не доказывает, что каждый Transformer с tool API имеет дополнительную обученную голову. И даже без LLM программа может по правилу всегда вызвать поиск для определённого типа запроса.

### 2.2. Что меняет обучение и чего оно не гарантирует

Учебная SFT-траектория содержит user request, доступные tools, assistant call, настоящий tool observation и assistant answer. При teacher forcing модель предсказывает очередные целевые токены, имея предыдущие токены правильной траектории. Обычно loss маскируют по выбранным assistant spans; точная masking policy зависит от training setup. Tool output может быть входным контекстом без обязанности учить модель воспроизводить его как собственный ответ.

Для assistant token set A можно записать:

$$
\mathcal L_{\mathrm{SFT}}=-\frac{1}{|A|}\sum_{t\in A}\log p_\theta(y_t\mid x,y_{<t}).
$$

Обучаются и выбор функции, и структура аргументов, и использование observation в ответе — насколько это представлено в данных. Нужны также примеры прямого ответа без tool, неизвестных/недоступных данных, ошибок и повторных попыток. Если training set состоит только из успешных calls, модель может вызывать инструмент слишком часто и плохо завершаться после no-results. Если observation в обучении всегда идеален, реальные частичные результаты становятся distribution shift.

Описание инструмента остаётся нужно и дообученной модели: в конкретной среде различаются имена, параметры и доступность функций. Prompting и SFT совместимы. Constrained decoding отдельно ограничивает допустимые продолжения по грамматике/schema; оно не тождественно знанию формата в весах. Исправляем исходную аналогию: хорошо обученный JSON и JSON, принудительно ограниченный grammar, дают разные виды надёжности.

Три проверки последовательны: синтаксис можно распарсить; структура соответствует объявленной schema; действие семантически подходит и разрешено. Число `limit=5` может пройти все type checks, но query будет о другом сервисе. Правильно записанный `delete_document` может быть недопустим для read-only задачи. SFT повышает вероятность хорошего поведения, а не превращает всякий output в доказанно верный call.

### 2.3. Протокол не равен выполненной операции

Учебное сообщение после parsing:

```json
{"id":"c17","name":"search_documents","arguments":{"query":"payment timeout","limit":5}}
```

Здесь `id` связывает observation с запросом. Runtime разрешает только зарегистрированное имя, проверяет аргументы и определяет scope по доверенному task state. Нельзя позволять модели расширять scope произвольным полем `tenant=other`. Имена функций сопоставляются с явным registry; сгенерированная строка не исполняется через eval. После вызова result содержит статус, документы с IDs и версиями либо ошибку, пригодную для обработки.

При streaming JSON может приходить по частям. Фрагмент `{"query":"pay` ещё не готовый вызов. Executor ждёт завершённого сообщения и валидации. При parallel calls каждый result связывают с собственным ID; порядок завершения не обязательно равен порядку предложений модели. Если второй call использует результат первого, это зависимость, и два calls нельзя автоматически распараллелить.

Повторный поиск после пустого результата может изменить query. Повтор после temporary network error может сохранить query. После invalid arguments требуется исправление, после denied scope — завершение или разрешённый альтернативный путь. Просто отправить модели слово ERROR без категории часто недостаточно: она не понимает, что именно можно исправлять.

### 2.4. Когда «уже достаточно искать»

В S6 пользователь спросил, как researcher решает, какой инструмент выбрать, искать ли ещё и когда вернуть итог. У модели нет встроенного датчика полноты всех знаний. Она оценивает увиденный context по обученной policy и инструкциям. Приложение может потребовать проверяемые условия: найдены правила для нужного сервиса и версии, каждый существенный claim опирается на evidence, конфликтующие версии разобраны. Эти условия помогают остановке, но проверка наличия ID ещё не доказывает, что текст действительно поддерживает утверждение.

Нужно различать proposed finish и accepted finish. Модель может предложить ответ; validator проверяет доступные свойства и либо принимает его, либо возвращает конкретную причину. Если необходимого evidence нет и новые шаги исчерпаны, корректный terminal outcome — частичный ответ с пробелом. Бесконечно просить «поищи лучше» не создаёт недостающего документа.

Счётчики должны иметь единицы. Учебный лимит — максимум 4 model calls и 3 tool executions. Трасса `model→tool→model→tool→model→answer` расходует 3 и 2 соответственно; остаётся 1 model call и 1 tool execution. Если последняя модель снова просит tool, нужно заранее решить, откуда возьмётся model call для чтения результата: резервировать финальный шаг либо завершать partial. Один общий «max_iterations» без определения легко создаёт ошибку на границе.

Для ожидаемой полезности поиска можно мысленно сравнить выигрыш в качестве с ценой latency/tokens, но обычно истинный выигрыш неизвестен. Практический учебный критерий — какие незакрытые вопросы остались и какой доступный call способен их разрешить. Повтор идентичного запроса без нового состояния редко даёт основание ожидать другое evidence, хотя retrieval с nondeterminism может отличаться.

### 2.5. Checkpoint, retry и внешние эффекты

Checkpoint фиксирует состояние runtime, но не откатывает внешнюю систему. Возможна последовательность: действие выполнено → процесс упал до сохранения observation → возобновлён старый checkpoint → действие предложено снова. Один сохранённый graph автоматически не обеспечивает exactly-once effect.

Для операции создания записи нужен стабильный application operation key и поддержка deduplication/проверки результата у исполнителя. Новый transport call ID на retry не должен ошибочно означать новое бизнес-действие. Если внешний сервис не умеет idempotency, приходится сверять фактическое состояние или выбирать recovery policy с учётом неоднозначности. Для чтения повтор обычно безопаснее, но результат мог измениться между попытками; provenance/version всё равно важны.

Пусть после первого успешного эффекта ответ теряется с вероятностью 0.1, разрешён один retry, а второй effect также успешен. Без deduplication ожидается 1.1 эффекта на исходную операцию: один всегда и дополнительный с вероятностью 0.1. При надёжной idempotency по стабильному ключу эффект остаётся один; повтор может вернуть ранее созданный результат. Это условная модель ошибки доставки, а не обещание любой API реализации.


## 3. RAG: retrieval добавляет текстовый evidence

Pipeline: corpus ingestion → chunks с IDs/provenance → sparse/dense index → query retrieval → optional reranking → context selection → generation с citations. Generator обычно получает **исходные тексты**, выбранные по vector scores, а не произвольный embedding vector вместо слов.

Это отвечает вопросу чата «почему модель поймёт наш embedding». Retriever понимает совместимое query/document space, приложение по IDs достаёт snippets, LLM читает их как text. Input token embeddings LLM и retrieval embeddings имеют разные roles/objectives.

BM25 использует term frequencies, corpus document frequencies и length normalization. Dense retriever сравнивает learned vectors. Hybrid объединяет rankings/scores по объявленной policy, reranker оценивает query-document pairs. Больше stages не гарантирует improvement: each может добавить latency и failure mode.

FAISS — библиотека vector search; полноценная система ещё хранит documents/metadata, versions, access filters, deletion/update semantics. ANN approximation оценивается относительно exact search отдельно от relevance quality. Стандартный vector index не должен выдавать document вне разрешённого scope только из-за большой similarity.


### 3.1. Полный путь evidence и его четыре представления

Для запроса «какой timeout у payment-service в версии v8?» сначала задаются сервис, версия и scope. Query encoder создаёт retrieval vector. Индекс возвращает candidate IDs/scores. Document store по IDs выдаёт текст и metadata. После фильтрации и reranking в prompt попадают выбранные фрагменты. В итоге есть четыре разных объекта: query text, retrieval vector, ranked IDs, textual evidence. Их нельзя подменять одним словом embedding.

Вектор не хранит готовую цитату в форме, которую generator обязан уметь декодировать обратно. Даже если retriever и LLM используют одинаковую размерность вектора, это не делает пространства совместимыми. Retrieval training сближает релевантные query/document representations; language-model input embedding участвует в другом вычислительном тракте. Обычный RAG соединяет системы через извлечение текста, без специального обучения LLM читать произвольные поисковые векторы.

Chunking нужен из-за granularity поиска и ограниченного context. Очень крупный chunk может скрыть нужную строку среди лишнего; очень мелкий — потерять заголовок, условие и версию. Overlap сохраняет локальную связность ценой повторов и объёма индекса. У каждого chunk должны оставаться document ID, position и revision, иначе цитата или обновление становятся неоднозначными. Удалённый документ должен исчезнуть из доступного retrieval path, а не только из первоначальной папки.

### 3.2. Почему фильтрация после top-k иногда теряет нужное

Пусть доступный и релевантный фрагмент имеет global vector rank 11. Первые 10 — документы другого scope. Стратегия «global top-10 → убрать запрещённое» вернёт пустой список. Поиск в допустимом подмножестве мог бы найти нужный фрагмент первым. Это не аргумент за показ запрещённых текстов; это причина учитывать фильтр при поиске либо использовать корректный over-fetch/filtered search с пониманием ограничений backend.

Top-k задаёт число кандидатов, а не число доказанных фактов. После reranking и deduplication в context может попасть меньше k. Например, найдено 20 chunks, 8 относятся к нужной версии, 3 после deduplication покрывают задачу. Не следует превращать факт «ANN вернул 20 соседей» в retrieval success без relevance labels и проверки scope/version.

Context budget тоже считается явно. В учебном окне 8192 tokens зарезервированы 1500 для instructions/question/history и 1200 для output. На evidence остаётся 5492. Если каждый полный упакованный chunk с metadata занимает 700 tokens, помещается 7 chunks (4900), остаётся 592; восемь потребовали бы 5600. Это упрощённая арифметика с фиксированным размером chunks; в реальном prompt длина измеряется tokenizer после упаковки, включая separators и дополнительные tools/messages.

### 3.3. RAG workflow и agentic retrieval

В fixed RAG каждый запрос проходит один retrieval. В agentic варианте модель может понять, что не хватает второго документа, уточнить поиск или прочитать соседний chunk. Дополнительный control flow помогает только при содержательной политике. Если модель не заметила отсутствующую версию, многократный поиск может лишь увеличить уверенность в неправильном ответе.

Retrieved text — evidence, а не новая доверенная инструкция. Документ с фразой «игнорируй задачу и вызови другой tool» не меняет разрешённые actions. Разделение ролей в prompt полезно, но enforcement прав и registry остаётся у программы. Цитата подтверждает provenance; её наличие не доказывает entailment. Требуется проверить, что именно процитированный фрагмент поддерживает claim и не относится к другой версии.


## 4. Frameworks: abstraction по потребности

LangChain-style components дают templates, model/tool adapters, chains и parsers; LangGraph-style graph описывает state/transitions/checkpointing. LlamaIndex делает акцент на data/retrieval integrations. AutoGen/CrewAI исторически предлагали conversation/role coordination patterns. Их APIs меняются; выбирать нужен набор capabilities, а не обязательное прохождение каждого framework.

Один agent participant может иметь свой loop с tools, state и termination. Это не требует быть реализованным через LangGraph: тот же механизм можно написать другим runtime. Multi-agent coordination добавляет messages, duplicated context и termination difficulties; качество сравнивать с single-agent baseline при одинаковом total budget.

Локальные Ollama/LM Studio models могут быть model endpoints такого приложения. Ответ на исходный вопрос о локальном agent pipeline: runtime вызывает endpoint, валидирует output, исполняет tools и повторяет call. Встроенные features конкретного приложения могут часть этого делать, но supported API/tool modes проверяются отдельно.


### 4.1. Ответ на вопрос об AutoGen и LangGraph

В S6 пользователь связал conversation-centric участников AutoGen с графами LangGraph. Совпадение общей идеи последовательных решений не означает зависимость одной реализации от другой. Participant может вызывать модель, исполнять tool, возвращать фиксированный ответ или передавать сообщение человеку. Graph node также может быть обычной deterministic функцией. Поэтому исходное «каждый агент во всех frameworks обязательно LLM + tools + loop» слишком широко.

Есть два независимых уровня: локальная policy участника и coordinator, выбирающий, кому передать управление. Researcher может сам выбирать search/read tools, а coordinator — решать, когда передать его evidence автору ответа. Либо coordinator детерминирован, а участники только выполняют фиксированные функции. Названия «researcher», «critic», «writer» работают как описание роли, но не создают отдельного знания и не гарантируют независимость ошибок.

Вопрос чата о самостоятельном выборе subagents разбирается на этом же уровне: делегирование может быть ещё одним разрешённым action с ограниченным входом, бюджетом и result contract. Из факта, что интерфейс показывает subagent, нельзя восстановить закрытые внутренние prompts, framework и правила маршрутизации конкретного продукта. Здесь объясняется механизм, без утверждения о внутреннем устройстве упомянутого в чате редактора.

### 4.2. Parallel branches: latency, state merge и общий бюджет

Для двух независимых поисков длительностью 0.8 и 1.2 секунды последовательный путь занимает 2.0, идеальный parallel —1.2 до merge, без overhead/queue. Но если второй запрос строится по результату первого, такого ускорения нет. Parallel execution уменьшает критический путь, а не сумму оплаченной/выполненной работы.

Пусть начальное evidence множество `{a}`, ветка A добавляет b, ветка B —c. Если обе возвращают полное replacement-поле, last-write-wins сохранит `{a,b}` или `{a,c}` и потеряет другой результат. Объединение множеств даст `{a,b,c}` независимо от порядка. Для evidence с versions удобнее merge по стабильному ID/revision и явная политика конфликтов. Для messages простая конкатенация сохраняет всё, но порядок A+B отличается от B+A; порядок может повлиять на следующий model call.

Две ветки не должны независимо тратить весь общий budget. При лимите 6000 tokens coordinator может зарезервировать 3000 и 2000 для двух участников, 1000 для synthesis. Это 6000 общего лимита, а не 6000 на каждого. Если участник использует больше model calls, повторённые system/tool/history tokens тоже учитываются по объявленному accounting; параллельность их не устраняет. Учебное сравнение с single-agent имеет смысл при сопоставимых data access и суммарном бюджете.

### 4.3. Локальная модель: совместимость проверяется по слоям

Скачанный checkpoint сам по себе не задаёт работающий агент. Нужны подходящие tokenizer/chat template, способность model следовать tool protocol, поддержка backend и parser, затем executor и loop. Ошибка на каждом слое проявляется по-разному: raw text вместо calls, испорченные argument types, исчезнувший tool result, неверная role serialization, повтор вызова после уже полученного результата.

Нельзя переносить из чата абсолютное «Ollama/LM Studio только генерируют, никаких loops у них нет». В документации [Ollama показан multi-turn tool loop](https://docs.ollama.com/capabilities/tool-calling); [LM Studio разделяет tool requests и исполнение в коде](https://lmstudio.ai/docs/developer/openai-compat/tools), а его [SDK .act() автоматизирует несколько rounds](https://lmstudio.ai/docs/typescript/agent/act). Где физически находится loop — в вашем коде, SDK или встроенной функции продукта — зависит от выбранного интерфейса. Это не меняет различия между model proposal и реальным effect.

Совместимый HTTP shape облегчает замену endpoint, но не гарантирует одинаковые supported schema, tool-choice modes, streaming events и качество. Начинать проверку разумно с read-only инструмента известного результата: предложен ли правильный call, распарсены ли arguments, реальный ли result возвращён в контекст, использован ли он в final. Нельзя лечить ошибку chat template добавлением ещё пяти агентов.


## 5. Как разделить ошибки

Retrieval failure: evidence не найдено. Context selection failure: найдено, но не передано/обрезано. Generation failure: evidence есть, ответ неверный. Tool failure: wrong tool/args или ошибка исполнения. State failure: потерян результат/ID, повторено действие. Такие категории позволяют выбрать intervention точнее, чем «агент тупит».

Oracle context experiment подаёт gold snippet вместо retrieval. Если ответ теперь correct, bottleneck вероятно upstream; если нет — prompt/model/evidence interpretation требуют разбора. JSON validity и tool HTTP success — локальные diagnostics, final task success оценивается отдельно.


### 5.1. Разбираем одну задачу до terminal outcome

Учебная задача: «найди timeout payment-service v8 и процитируй». Trusted state разрешает только проект P. Первый поиск возвращает snippet v7 с timeout 2 s. Это observation реального поиска, но ещё не ответ на вопрос v8. Модель предлагает уточнить version, второй поиск возвращает v8 с timeout 5 s и ID `P/pay/v8#timeout`. После чтения полного условия ответ указывает 5 s и ограничение применимости. Validator проверяет наличие ID среди observations и нужную version; содержательную корректность числа сверяют с текстом.

Если второй поиск пустой, ответ «в v8 тоже 2 s» не следует из первого результата. Корректно сказать, что найдена только v7 и значение для v8 не установлено. Если tool timeout, в state хранится ошибка исполнения, а не no-results: мы не знаем, существовал ли документ. Если найденный ID недоступен, он не становится разрешённым из-за уверенности модели. Эти три случая требуют разных observations и разных дальнейших решений.

Полезная trace-запись содержит исходную задачу, revision prompt/model/tool registry, model-call index, call ID, validated args, scope decision, result/error, evidence IDs и terminal reason. Длинный лог всех строк сам по себе не заменяет связи между ними. Сводный статус success при незавершённом pending call скрывает ошибку жизненного цикла.

### 5.2. Oracle experiments и локальные метрики

Чтобы проверить retrieval, вручную подставляют нужный v8 snippet. Если модель всё равно отвечает 2 s, проблема не исчерпывается поиском. Если теперь ответ верный, upstream становится основным подозреваемым, но один успешный пример не доказывает, что generator всегда надёжен. Затем отдельно проверяют context packaging: возможно, retriever уже находил v8, но truncation удалял именно его.

На 100 учебных задачах 90 calls могут быть schema-valid, 80 —к правильному tool, 70 —успешно исполненными, 60 —дающими нужный evidence и 55 —завершёнными корректным ответом. Если это вложенные множества одной трассы на задачу, validity 90% и end-to-end success 55% совместимы. Условный success после найденного evidence равен 55/60≈91.67%. При нескольких calls на задачу denominators уже нужно определять отдельно: долю валидных calls нельзя напрямую считать долей успешных tasks.

Число retries полезно вместе с причинами. Меньше retries бывает от хорошего первого выбора, а бывает от преждевременного отказа. Больше evidence бывает от полноценного поиска, а бывает от дублей. Сравнивают outcome и затраты по типам задач, включая no-results, conflicting versions, malformed call и exhausted budget. Такая проверка помогает выбрать изменение prompt/template/retriever/runtime по месту ошибки, а не менять всё приложение сразу.

### 5.3. Вопросы для самопроверки

1. Обучает ли graph routing веса? **Ответ:** нет, без отдельного training процесса.
2. Передаёт ли ordinary RAG vector напрямую generator? **Ответ:** обычно нет, vector выбирает IDs, затем подаётся текст evidence.
3. Обязан ли каждый AutoGen agent быть LangGraph graph? **Ответ:** нет, это разные уровни/реализации loop/coordination.
4. Есть ли универсальный отдельный tool head? **Ответ:** нет; распространён autoregressive вывод протокола через vocabulary head, а отдельный router —возможное дополнительное решение.
5. Делает ли SFT format гарантированным? **Ответ:** нет. Обученная вероятность, grammar constraint и проверка смысла/прав —разные механизмы.
6. Почему checkpoint не обеспечивает exactly-once? **Ответ:** внешний effect мог произойти до сохранения результата; retry требует deduplication или recovery policy.
7. Кто решает, что поиска достаточно? **Ответ:** модель предлагает finish по контексту, runtime применяет заданные критерии и лимиты; полнота evidence не возникает автоматически.
8. Почему global top-k и поздний scope filter могут вернуть пустоту? **Ответ:** допустимый релевантный chunk мог находиться ниже global cutoff.
9. Обязан ли graph node вызывать LLM? **Ответ:** нет, это может быть обычная функция или tool executor.
10. Чем parallelism отличается от сокращения работы? **Ответ:** он может сократить критический путь, сохранив общие tokens и вычисления.
11. Что означает хороший tool-call validity при плохом task success? **Ответ:** правильный формат не гарантирует нужный инструмент, evidence и верную интерпретацию.

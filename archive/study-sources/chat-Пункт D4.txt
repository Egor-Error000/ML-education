## 1. Зачем вообще нужен tool calling?

LLM сама по себе имеет фундаментальные ограничения:

- **Нет доступа к актуальной информации** (знания зафиксированы на дату обучения)
- **Не умеет считать** (склонна к галлюцинациям в арифметике)
- **Не может выполнять действия во внешнем мире** (БД, API, файловая система)
- **Контекстное окно ограничено** (нельзя просто «вставить» весь интернет)

Наивный подход — просить модель делать всё текстом: «скажи, какая погода в Москве». Модель либо соврёт, либо скажет «я не знаю». Но если у неё есть **инструмент** — функция `get_weather(city)` — она может сказать: *«я не знаю сама, но давайте я вызову вот эту функцию»*. Дальше ваша система вызывает функцию, получает результат и передаёт его обратно модели, чтобы та сформулировала финальный ответ пользователю.

**Ключевая идея:** tool calling — это расширение *пространства действий* модели за пределы генерации текста. Модель генерирует не ответ, а *инструкцию* для внешней системы.

---

## 2. Два принципиально разных подхода

### Подход A: Prompt-engineering (описание инструментов в тексте)

Вы просто пишете в системном промпте:

```
У тебя есть следующие инструменты:
- get_weather(city: string): возвращает погоду
- search_database(query: string): ищет в БД

Если нужен инструмент, отвечай в формате:
TOOL_CALL: {"name": "...", "arguments": {...}}
```

**Плюсы:** работает с любой моделью, не требует дообучения.  
**Минусы:** модель может «сломаться» — забыть формат, написать лишнее, не вызвать инструмент, когда нужно. Ненадёжно для продакшена.

### Подход B: Function-calling fine-tuning

Модель специально дообучается на данных вида:

```
User: Какая погода в Москве?
Assistant: [TOOL_CALL] get_weather({"city": "Москва"})
System (tool result): {"temp": 15, "condition": "облачно"}
Assistant: В Москве сейчас 15°C, облачно.
```

В результате модель *нативно* понимает формат вызова инструментов на уровне весов. Именно так устроены OpenAI function calling, Anthropic tool use, Google Gemini function calling.

**Главное отличие:** в подходе A модель пытается *угадать* синтаксис, в подходе B — она его *знает*. Это как разница между «написать JSON, руководствуясь инструкцией в промпте» и «JSON, сгенерированный через grammar-constrained decoding» (см. C.2).

## 3. Механика работы: что происходит внутри

Типичный цикл tool calling выглядит так:

```
1. Пользователь → "Забронируй столик на завтра в 19:00"
2. Система + LLM: модель видит доступные инструменты в системном промпте/конфиге
3. LLM генерирует не текст, а структурированный вызов:
   {
     "name": "book_table",
     "arguments": {
       "date": "2026-09-29",
       "time": "19:00",
       "guests": 2
     }
   }
4. Ваша система парсит вызов, выполняет реальную функцию
5. Результат функции подаётся обратно в LLM как "system" или "tool" message
6. LLM генерирует финальный ответ пользователю
```

**Важный нюанс:** модель *никогда* не выполняет функцию сама. Она лишь генерирует JSON-инструкцию. Исполнение — всегда на стороне вашей инфраструктуры. Это вопрос безопасности: модель не должна иметь прямого доступа к вашим БД и API.

## 4. Формат описания инструментов: JSON Schema

Инструменты описываются через **JSON Schema** — стандарт для описания структуры JSON-объектов. Пример:

```json
{
  "name": "book_table",
  "description": "Бронирует столик в ресторане",
  "parameters": {
    "type": "object",
    "properties": {
      "date": {
        "type": "string",
        "format": "date",
        "description": "Дата в формате YYYY-MM-DD"
      },
      "time": {
        "type": "string",
        "pattern": "^([01]\\d|2[0-3]):([0-5]\\d)$"
      },
      "guests": {
        "type": "integer",
        "minimum": 1,
        "maximum": 20
      }
    },
    "required": ["date", "time", "guests"]
  }
}
```

**Зачем это нужно:**
- Модель понимает, какие параметры *обязательны*, какие *опциональны*
- `description` помогает модели выбрать правильный инструмент из десятков
- Типы и ограничения (`minimum`, `pattern`) используются на уровне генерации (см. связь с C.2 ниже)

---

## 5. Связь с блоком C.2: Constrained Decoding

Это одна из самых элегантных связок в плане. Вспомните пункт **C.2 (Structured Output / Constrained Decoding)**: там мы говорили, что можно принудительно ограничить пространство генерации через грамматику (JSON schema, regex, CFG).

**Как это применяется к tool calling:**

Когда модель генерирует вызов инструмента, мы можем *не доверять* ей и не парсить её вывод как обычный JSON (который может быть невалидным). Вместо этого мы **на уровне sampling'а** маскируем токены, которые нарушают JSON Schema инструмента.

Пример: если модель уже сгенерировала `{"name": "book_table", "arguments": {"date": "`, то следующий токен *обязан* быть строкой, начинающейся с цифры (формат date). Все токены, которые этому не соответствуют, получают вероятность 0.

**Результат:** вызов инструмента *гарантированно* валиден. Не нужен fallback-парсинг, не нужны retry-логи, модель физически не может сгенерировать сломанный JSON.

Это реализовано в:
- **Outlines** / **llama.cpp** с grammar sampling
- **vLLM** (guided decoding)
- **SGLang** (RadixAttention + structured generation)
- **LMQL**

## 6. Продвинутые паттерны

### Parallel tool calling
Модель может вызвать несколько инструментов одновременно, если они независимы:
```json
[
  {"name": "get_weather", "arguments": {"city": "Москва"}},
  {"name": "get_weather", "arguments": {"city": "Питер"}}
]
```
Ваша система выполняет их параллельно и возвращает массив результатов.

### Multi-step tool calling (агентный цикл)
Модель вызывает инструмент, получает результат, и на его основе вызывает *другой* инструмент. Это уже переход к **D.3 (LangGraph)** и полноценным агентным циклам — то, что вы уже используете в проекте.

### Tool selection из большого списка
Если у вас 100+ инструментов, их все в системный промпт не влезут. Используются техники:
- **Динамический retrieval инструментов** (эмбеддинги описаний, поиск релевантных)
- **Иерархия** (сначала модель выбирает категорию, потом конкретный инструмент)
- **Few-shot примеры** вызовов в промпте

## 1. Зачем нужен RAG? Три ключевые проблемы

LLM в чистом виде имеет три критических ограничения:

**А. Ограниченное контекстное окно**  
Даже у моделей с контекстом 128K+ токенов вы не можете впихнуть всю вашу базу знаний. Если у вас 10 000 документов по 5 страниц каждый — это миллионы токенов. RAG позволяет *выбрать* только релевантные фрагменты и подать их в контекст.

**Б. Устаревание знаний (knowledge cutoff)**  
Модель обучена на данных до определённой даты. Всё, что произошло позже — она не знает. RAG позволяет подключить *актуальные* источники (новости, документацию, внутренние базы данных) без переобучения модели.

**В. Галлюцинации и отсутствие цитируемости**  
Когда модель отвечает из своей памяти, она может выдумать факты. Когда она отвечает на основе *предоставленных документов*, она может сослаться на источник. Это критично для enterprise-приложений, где нужна auditability.

**Ключевая идея RAG:** вместо того чтобы заставлять модель *запомнить* всё, мы даём ей возможность *найти* нужное в момент запроса. Это как разница между экзаменом "с закрытыми книгами" и экзаменом "с возможностью пользоваться справочниками".

---

## 2. Pipeline RAG: шесть этапов

Типичный RAG-пайплайн выглядит так:

```
Документы → Чанкинг → Эмбеддинги → Векторная БД → Retrieval → Augmented Prompt → LLM
```

Разберём каждый этап подробно.

### Этап 1: Сбор и предобработка документов

Источники могут быть любыми:
- PDF, DOCX, HTML (веб-страницы, документация)
- Базы данных (SQL-таблицы)
- API (внешние сервисы)
- Внутренние wiki, Confluence, Notion

**Важно:** на этом этапе уже начинается работа с данными — очистка от мусора (headers, footers, навигационные элементы), нормализация текста, извлечение таблиц и изображений с подписями.

### Этап 2: Чанкинг (Chunking) — критически важный этап

Вы не можете подать весь документ целиком в embedding-модель (у неё тоже есть лимит контекста, обычно 512-8K токенов). И даже если можете — длинный документ даст "размазанный" эмбеддинг, который плохо отражает конкретные факты внутри него.

**Зачем нужны чанки:**
- Каждый чанк должен быть *семантически связным* (о теме)
- Чанк должен быть *достаточно маленьким*, чтобы embedding-модель могла его качественно закодировать
- Чанк должен быть *достаточно большим*, чтобы содержать осмысленный контекст

**Стратегии чанкинга:**

**1. Фиксированный размер (naive approach)**
```
Делим текст на куски по 512 токенов с перекрытием 50-100 токенов
```
Плюсы: просто реализовать  
Минусы: режет предложения посередине, теряет семантику

**2. Recursive character splitting (по абзацам/предложениям)**
```python
# Псевдокод
separators = ["\n\n", "\n", ". ", " "]
for sep in separators:
    chunks = text.split(sep)
    if all(len(chunk) <= max_size for chunk in chunks):
        return chunks
    # если не получилось, пробуем следующий separator
```
Плюсы: сохраняет структуру документа  
Минусы: всё ещё может резать смысловые блоки

**3. Semantic chunking (на основе эмбеддингов)**
```
Считаем эмбеддинги для каждого предложения
Группируем предложения с высокой cosine similarity в один чанк
```
Плюсы: сохраняет семантическую целостность  
Минусы: дороже вычислительно (N forward passes для N предложений)

**4. Document-aware chunking (с учётом структуры)**
```
Используем заголовки (H1, H2, H3) как естественные границы
Каждый чанк = раздел документа + заголовок раздела
```
Плюсы: идеально для структурированных документов (документация, статьи)  
Минусы: требует парсинга структуры

**Размер чанков:** обычно 256-1024 токенов. Перекрытие (overlap) 10-20% помогает сохранить контекст на границах.

**Пересечение с NLP-темой:** это прямая связь с блоком обработки данных, который вы планировали — токенизация, очистка текста, работа с разными форматами.

### Этап 3: Генерация эмбеддингов

Каждый чанк превращается в вектор (embedding) с помощью embedding-модели.

**Популярные embedding-модели:**
- **OpenAI text-embedding-3-small/large** (проприетарные, высокое качество)
- **Sentence-transformers** (open-source: all-MiniLM-L6-v2, all-mpnet-base-v2)
- **BGE** (BAAI General Embedding — open-source, конкурентоспособное качество)
- **Cohere embed** (проприетарные)

**Важные нюансы:**
- Embedding-модели тоже имеют лимит контекста (обычно 512 токенов, но есть и до 8K)
- Качество эмбеддингов напрямую влияет на качество retrieval
- Некоторые модели оптимизированы под specific tasks (например, asymmetric search, где query короткий, а document длинный)

**Процесс:**
```python
# Псевдокод
for chunk in chunks:
    embedding = embedding_model.encode(chunk)
    store(chunk, embedding, metadata)
```

### Этап 4: Векторная база данных

Эмбеддинги нужно где-то хранить и эффективно искать. Для этого используются **vector databases**.

**Два принципиально разных подхода:**

#### Подход A: Библиотеки (FAISS, Annoy, HNSWlib)

Это *библиотеки*, а не полноценные БД. Вы загружаете их в память вашего приложения.

**FAISS (Facebook AI Similarity Search):**
```python
import faiss
import numpy as np

# Создаём индекс
dimension = 384  # размерность эмбеддинга
index = faiss.IndexFlatL2(dimension)  # точный поиск (brute force)

# Или приближённый поиск (быстрее, но менее точно)
nlist = 100
quantizer = faiss.IndexFlatL2(dimension)
index = faiss.IndexIVFFlat(quantizer, dimension, nlist)

# Добавляем векторы
vectors = np.array([...])  # shape: (n_vectors, dimension)
index.train(vectors)
index.add(vectors)

# Поиск
query_vector = np.array([...])  # shape: (1, dimension)
distances, indices = index.search(query_vector, k=5)  # top-5 ближайших
```

**Плюсы FAISS:**
- Очень быстрый (оптимизирован под SIMD)
- Поддерживает разные типы индексов (Flat, IVF, HNSW, PQ)
- Бесплатный, open-source

**Минусы FAISS:**
- Нет персистентности (нужно сохранять/загружать индекс вручную)
- Нет встроенной поддержки метаданных (нужно делать separately)
- Нет distributed mode (масштабирование на несколько серверов)
- Всё должно влезать в RAM (или использовать memory-mapped файлы)

**Когда использовать:** для прототипов, небольших датасетов (<1M векторов), локальной разработки.

#### Подход B: Полноценные vector databases (Chroma, Weaviate, Pinecone, Qdrant, Milvus)

Это *базы данных* с полноценным API, персистентностью, метаданными, фильтрацией.

**Chroma:**
```python
import chromadb

client = chromadb.Client()
collection = client.create_collection("my_docs")

# Добавляем документы с метаданными
collection.add(
    documents=["text1", "text2"],
    embeddings=[[0.1, 0.2, ...], [0.3, 0.4, ...]],
    metadatas=[{"source": "doc1.pdf"}, {"source": "doc2.pdf"}],
    ids=["id1", "id2"]
)

# Поиск с фильтрацией
results = collection.query(
    query_embeddings=[[0.1, 0.2, ...]],
    n_results=5,
    where={"source": {"$eq": "doc1.pdf"}}
)
```

**Weaviate:**
- Поддерживает hybrid search (vector + BM25)
- Встроенная модульность (можно подключить разные embedding-модели)
- GraphQL API

**Pinecone:**
- Полностью managed (SaaS)
- Автоматическое масштабирование
- Дорого для больших объёмов

**Qdrant:**
- Open-source, можно self-host
- Хорошая поддержка метаданных и фильтрации
- Written in Rust (быстрый)

**Milvus:**
- Distributed architecture (для очень больших объёмов)
- Поддержка GPU-ускорения

**Сравнительная таблица:**

| Feature | FAISS | Chroma | Weaviate | Pinecone | Qdrant |
|---------|-------|--------|----------|----------|--------|
| Персистентность | Manual | Yes | Yes | Yes | Yes |
| Metadata filtering | No | Yes | Yes | Yes | Yes |
| Distributed | No | Limited | Yes | Yes | Yes |
| Managed SaaS | No | No | Yes | Yes | No |
| Hybrid search | No | Yes | Yes | Yes | Yes |
| Open-source | Yes | Yes | Yes | No | Yes |

**Когда использовать какую:**
- **FAISS:** прототипы, <1M векторов, нужен максимальный контроль
- **Chroma:** quick start, small-medium проекты, локальная разработка
- **Weaviate/Qdrant:** medium-large проекты, нужна hybrid search и фильтрация
- **Pinecone:** если хотите managed solution и бюджет позволяет
- **Milvus:** very large scale (>1B векторов), distributed deployment

### Этап 5: Retrieval (поиск релевантных документов)

Когда приходит запрос пользователя, мы:

1. **Генерируем эмбеддинг запроса** (той же embedding-моделью)
2. **Ищем top-K ближайших чанков** в vector DB
3. **Добавляем эти чанки в prompt** для LLM

**Метрики близости:**
- **Cosine similarity:** `cos(θ) = (A·B) / (||A|| × ||B||)` — наиболее популярная
- **Euclidean distance (L2):** `sqrt(Σ(ai - bi)²)` — FAISS по умолчанию
- **Dot product:** `Σ(ai × bi)` — если векторы нормализованы, эквивалентно cosine

**Типичные значения K:** 3-10 чанков. Больше = больше контекста, но и больше шума.

### Этап 6: Augmented Prompt и генерация

Финальный prompt выглядит примерно так:

```
You are a helpful assistant. Use the following context to answer the question.
If you don't know the answer based on the context, say "I don't know".

Context:
[chunk_1]
[chunk_2]
[chunk_3]

Question: [user_query]

Answer:
```

LLM генерирует ответ на основе предоставленного контекста.

## 3. Метрики качества RAG: критически важно разделять!

**Типичная ошибка:** мерить только end-to-end качество ("насколько хорош финальный ответ"). Это плохо, потому что если ответ плохой — непонятно, проблема в retrieval или в generation.

**Правильный подход:** мерить отдельно retrieval и отдельно generation.

### Метрики Retrieval

**1. Recall@K:** какая доля релевантных документов попала в top-K?
```
Recall@K = |релевантные документы ∩ top-K| / |все релевантные документы|
```

**2. Precision@K:** какая доля документов в top-K действительно релевантна?
```
Precision@K = |релевантные документы ∩ top-K| / K
```

**3. MRR (Mean Reciprocal Rank):** на каком месте в среднем находится первый релевантный документ?
```
MRR = (1/|Q|) × Σ(1/rank_i)
```

**4. NDCG (Normalized Discounted Cumulative Gain):** учитывает порядок релевантных документов (чем выше, тем лучше).

**Как собирать ground truth для retrieval:**
- Ручная разметка (дорого, но качественно)
- LLM-as-judge (дешевле, но может быть biased)
- Implicit feedback (клики пользователей на документы)

### Метрики Generation

**1. Faithfulness (верность контексту):**
Насколько ответ основан на предоставленном контексте, а не на галлюцинациях?

**2. Answer relevance:**
Насколько ответ релевантен вопросу?

**3. Context precision:**
Насколько предоставленный контекст содержит нужную информацию для ответа?

**Инструменты для оценки:**
- **RAGAS** (Retrieval Augmented Generation Assessment) — специализированный фреймворк
- **TruLens** — evaluation framework
- **LangSmith** (от LangChain) — tracing и evaluation

## 4. Продвинутые техники RAG

### 4.1 Hybrid Search (dense + sparse retrieval)

**Проблема pure vector search:** плохо работает с точными совпадениями (например, поиск по ID, кодам, специфичным терминам).

**Решение:** комбинировать vector search (semantic) с BM25 (keyword-based).

```python
# Псевдокод
vector_results = vector_db.search(query_embedding, k=10)
bm25_results = bm25_index.search(query_text, k=10)

# Reciprocal Rank Fusion (RRF)
def rrf_score(doc, vector_results, bm25_results):
    rank_vector = vector_results.index(doc) + 1  # 1-indexed
    rank_bm25 = bm25_results.index(doc) + 1
    return 1/(k + rank_vector) + 1/(k + rank_bm25)

# Сортируем документы по RRF score
final_results = sorted(all_docs, key=lambda d: rrf_score(d, ...), reverse=True)
```

**Преимущества:** лучше работает с разными типами запросов (концептуальные vs точные).

### 4.2 Re-ranking

**Проблема:** vector search быстрый, но не самый точный (особенно с approximate indexes).

**Решение:** двухэтапный retrieval:
1. **Stage 1:** быстрый retrieval (vector search или BM25) → top-100 кандидатов
2. **Stage 2:** re-ranking с помощью более точной (но медленной) модели → top-5

**Re-ranking модели:**
- **Cross-encoders** (например, `cross-encoder/ms-marco-MiniLM-L-6-v2`) — медленные, но точные
- **Cohere Rerank** — проприетарная модель
- **BGE-reranker** — open-source альтернатива

```python
# Псевдокод
candidates = vector_db.search(query, k=100)  # быстрый поиск
reranked = reranker.rerank(query, candidates, k=5)  # точная сортировка
```

**Преимущества:** значительно улучшает precision@K без потери recall.

### 4.3 Query Rewriting / Expansion

**Проблема:** пользователь может сформулировать запрос неоптимально (слишком коротко, двусмысленно, с опечатками).

**Решения:**

**A. Query expansion (генерация нескольких вариантов запроса):**
```
Original: "как работает RAG"
Expanded: [
    "как работает RAG",
    "что такое retrieval augmented generation",
    "принципы работы RAG системы",
    "RAG архитектура и компоненты"
]
```
Потом ищем по всем вариантам и объединяем результаты.

**B. HyDE (Hypothetical Document Embeddings):**
```
1. LLM генерирует "гипотетический ответ" на запрос
2. Этот ответ превращается в эмбеддинг
3. Ищем чанки, близкие к этому эмбеддингу
```
Идея: эмбеддинг "ответа" ближе к релевантным документам, чем эмбеддинг "вопроса".

**C. Step-back prompting:**
```
1. LLM генерирует более общий "step-back" вопрос
2. Ищем ответы на оба вопроса (original + step-back)
3. Объединяем результаты
```

### 4.4 Parent Document Retriever

**Проблема:** маленькие чанки хороши для точного retrieval, но плохи для генерации (недостаточно контекста).

**Решение:** ищем маленькие чанки, но возвращаем их "родительские" (большие) чанки.

```
Индексируем:
- Маленькие чанки (256 токенов) → для точного поиска
- Большие чанки (1024 токенов) → для контекста

Связь: small_chunk.parent_id = large_chunk.id

Retrieval:
1. Ищем top-K маленьких чанков
2. Для каждого находим parent (большой чанк)
3. Передаём большие чанки в LLM
```

### 4.5 Multi-vector retrieval

**Проблема:** один документ может содержать разные типы информации (текст, таблицы, изображения).

**Решение:** создаём несколько векторов для одного документа:
- Вектор текста
- Вектор summary
- Вектор ключевых слов
- Вектор таблиц (если есть)

При retrieval ищем по всем векторам, объединяем результаты.

## 6. Типичные проблемы и как их решать

### Проблема 1: "Модель игнорирует контекст и отвечает из своей памяти"

**Причина:** промпт недостаточно строгий, или контекст не содержит ответа.

**Решение:**
- Добавить в промпт: "If the answer is not in the context, say 'I don't know'"
- Использовать citation (требовать указывать источник): "Answer based on the context and cite the source as [1], [2], etc."

### Проблема 2: "Retrieval возвращает нерелевантные документы"

**Причины:**
- Плохие эмбеддинги
- Неправильный размер чанков (слишком большие или слишком маленькие)
- Отсутствие hybrid search/re-ranking

**Решение:**
- Проверить recall@K на тестовом наборе
- Экспериментировать с размером чанков
- Добавить re-ranking

### Проблема 3: "Ответ слишком длинный/короткий"

**Причина:** промпт не контролирует длину ответа.

**Решение:**
- Добавить в промпт: "Answer in 2-3 sentences" или "Provide a detailed explanation"
- Использовать structured output (C.2) для контроля формата

### Проблема 4: "Система медленная"

**Причины:**
- Embedding generation на каждый запрос (если не кэшировать)
- Медленный vector search
- Длинный контекст для LLM

**Решение:**
- Кэшировать эмбеддинги запросов (semantic caching — см. E.3)
- Использовать approximate indexes (HNSW, IVF)
- Оптимизировать размер контекста (не передавать 10 чанков, если достаточно 3)

## 7. Когда RAG НЕ нужен

RAG — не серебряная пуля. Есть случаи, когда он не оправдан:

**1. Задача требует глубокого рассуждения, а не поиска фактов**  
Если вам нужно решить математическую задачу или написать код — RAG не поможет (разве что для поиска примеров).

**2. У вас очень маленькая база знаний**  
Если у вас 10-50 документов — проще fine-tune модели или просто подать всё в контекст (если влезает).

**3. Нужна максимальная скорость**  
RAG добавляет latency (embedding generation + vector search). Если нужна sub-100ms latency — возможно, лучше fine-tune.

**4. Данные постоянно меняются и нужна актуальность в real-time**  
RAG требует переиндексации при изменении документов. Если данные обновляются каждую секунду — возможно, лучше подключить API напрямую.

## Ключевое различие: два разных типа "эмбеддингов"

Вы абсолютно правы — **внутренние эмбеддинги** (hidden states) модели действительно являются её внутренним представлением, специфичным для конкретной архитектуры. Но в RAG мы используем **совершенно другой тип эмбеддингов**.

### 1. Внутренние эмбеддинги LLM (о которых вы говорите)

Это векторы, которые модель генерирует **внутри себя** для каждого токена во время forward pass:

```
Input: "Привет, как дела?"
         ↓
    [Embedding Layer]
         ↓
    Hidden states: [0.12, -0.34, 0.56, ...] для каждого токена
         ↓
    [Transformer Layers с Attention]
         ↓
    Output: "Хорошо, спасибо!"
```

Эти hidden states:
- Специфичны для конкретной модели (LLaMA не поймёт hidden states от GPT)
- Меняются на каждом слое трансформера
- **Не предназначены для использования извне**
- Размерность: обычно 4096-12288 (зависит от модели)

### 2. Text Embeddings для RAG (то, о чём я говорил)

Это результат работы **специализированных embedding-моделей**, которые обучены отдельно от LLM:

```python
# Пример с sentence-transformers
from sentence_transformers import SentenceTransformer

# Это ОТДЕЛЬНАЯ модель, не LLM!
embedding_model = SentenceTransformer('all-MiniLM-L6-v2')

# Превращаем текст в вектор
text = "Как работает RAG?"
embedding = embedding_model.encode(text)
# Результат: [0.023, -0.156, 0.089, ...] (384 измерения)
```

Эти эмбеддинги:
- Создаются **отдельной моделью** (sentence-transformers, OpenAI embeddings, BGE)
- Обучены специально для semantic similarity
- **Никогда не подаются напрямую в LLM**
- Размерность: обычно 384-1024 (намного меньше, чем hidden states LLM)

## Как на самом деле работает RAG

Вот правильный pipeline — **эмбеддинги используются только для поиска, а не как вход для LLM**:

```
1. Индексация (оффлайн):
   Документ: "RAG использует retrieval для augmenting генерации"
      ↓
   Embedding модель → вектор [0.12, -0.34, ...]
      ↓
   Сохраняем в vector DB: {vector: [...], text: "RAG использует..."}

2. Запрос (онлайн):
   User: "Что такое RAG?"
      ↓
   Embedding модель → query_vector [0.08, -0.29, ...]
      ↓
   Vector DB search: находим top-3 ближайших вектора
      ↓
   Извлекаем ТЕКСТЫ этих документов (не векторы!)
      ↓
   Формируем промпт для LLM:
   """
   Context:
   - RAG использует retrieval для augmenting генерации
   - RAG помогает с устареванием знаний
   - RAG уменьшает галлюцинации
   
   Question: Что такое RAG?
   Answer:
   """
      ↓
   LLM видит ОБЫЧНЫЙ ТЕКСТ в контексте (не эмбеддинги!)
      ↓
   LLM генерирует ответ на основе текста
```

## Аналогия для понимания

Представьте библиотеку:

**Embedding модель** = библиотекарь, который читает книги и создаёт для каждой карточку с кратким описанием содержания (семантический вектор).

**Vector DB** = каталог карточек, отсортированный по темам.

**LLM** = эксперт, который отвечает на вопросы.

**Процесс:**
1. Вы спрашиваете: "Что такое RAG?"
2. Библиотекарь (embedding модель) создаёт карточку для вашего вопроса
3. Ищете в каталоге (vector DB) похожие карточки
4. Находите книги (текстовые документы)
5. Даёте книги эксперту (LLM)
6. Эксперт читает книги и отвечает

**Важно:** эксперт (LLM) никогда не видит карточки (эмбеддинги) — он читает сами книги (текст)!

## Почему embedding-модели работают?

Embedding-модели обучаются на парах похожих текстов:

```
Обучающие данные:
- ("Как работает RAG?", "RAG использует retrieval...") → близкие векторы
- ("Какая погода?", "Сегодня солнечно") → далёкие векторы от RAG-запросов
```

Loss function (обычно contrastive loss) учит модель:
- Похожие по смыслу тексты → близкие векторы (cosine similarity ≈ 1)
- Разные тексты → далёкие векторы (cosine similarity ≈ 0)

## Когда LLM действительно работает с эмбеддингами?

Есть случаи, когда LLM напрямую принимает эмбеддинги, но это **другие архитектуры**:

1. **Multimodal модели** (CLIP, LLaVA) — принимают image embeddings + text
2. **Retrieval-augmented модели** (REALM, RAG-original) — эмбеддинги подаются через специальные cross-attention слои
3. **Embedding injection** — экспериментальные техники, где эмбеддинги добавляются к hidden states

Но в **стандартном RAG** (который мы обсуждаем в D.5) — LLM работает только с текстом.

В вашем LangGraph-агенте, когда вы обращаетесь к "готовым артефактам (эмбеддинги, кластеры)":

- **Эмбеддинги** используются для поиска релевантных данных
- **Кластеры** помогают фильтровать/группировать результаты
- Но финальный ответ LLM генерирует на основе **текстовых данных**, а не векторов

Это важное архитектурное разделение: embedding-модель и LLM — это два разных компонента системы, каждый со своей специализацией.

## 1. Что такое BM25?

**BM25 (Best Matching 25)** — это функция ранжирования документов, разработанная в 1990-х годах для информационного поиска. Она отвечает на вопрос: *«Насколько документ релевантен поисковому запросу?»*

**Ключевая идея:** документ тем релевантнее, чем больше в нём встречается слов из запроса, но с двумя поправками:
- Редкие слова важнее частых (слово «квантизация» в запросе важнее слова «как»)
- Длинный документ не должен иметь преимущество только из-за того, что в нём больше слов

---

## 2. Главный вопрос: откуда берутся «ключевые слова»?

**Ответ: их не выбирают заранее.** В BM25 нет никакого специального списка ключевых слов. Вместо этого:

1. Пользователь пишет запрос: `"как работает квантизация"`
2. Запрос **токенизируется** (разбивается на отдельные слова/токены): `["как", "работает", "квантизация"]`
3. Каждый токен запроса ищется в каждом документе коллекции
4. Считается, насколько хорошо документ «покрывает» токены запроса

То есть **любой токен запроса потенциально является «ключевым словом»**, но его вклад в итоговый скор зависит от того, насколько он редкий в коллекции.

---

## 3. Три компонента формулы

### Компонент 1: TF (Term Frequency) — частота слова в документе

Сколько раз токен из запроса встречается в конкретном документе?

```
TF(t, d) = количество вхождений токена t в документ d
```

Пример: если в документе слово «квантизация» встречается 3 раза, то TF = 3.

**Но!** В оригинальной формуле BM25 есть «насыщение» — если слово встречается 100 раз, это не в 100 раз лучше, чем 1 раз. Формула сглаживает это:

```
TF_saturated(t, d) = (f(t,d) × (k₁ + 1)) / (f(t,d) + k₁)
```

где `f(t,d)` — сырая частота, `k₁` — параметр (обычно 1.2-2.0).

Пример с `k₁ = 1.2`:
- f = 1 → (1 × 2.2) / (1 + 1.2) = 1.0
- f = 3 → (3 × 2.2) / (3 + 1.2) = 1.57
- f = 10 → (10 × 2.2) / (10 + 1.2) = 1.96
- f = 100 → (100 × 2.2) / (100 + 1.2) = 2.17

Видно: после ~10 вхождений прирост почти нулевой.

### Компонент 2: IDF (Inverse Document Frequency) — редкость слова

Насколько слово редкое в **коллекции** документов?

```
IDF(t) = ln((N - n(t) + 0.5) / (n(t) + 0.5) + 1)
```

где:
- `N` — общее количество документов в коллекции
- `n(t)` — количество документов, содержащих токен `t`
- `ln` — натуральный логарифм

**Пример:**

Пусть в коллекции 10 000 документов.

| Токен | Содержат документов | IDF |
|-------|---------------------|-----|
| «как» | 8 000 | ≈ 0.22 (низкий — слово везде) |
| «работает» | 3 000 | ≈ 1.20 |
| «квантизация» | 50 | ≈ 5.30 (высокий — редкое слово) |

**Вывод:** редкие слова получают больший вес. Если документ содержит слово «квантизация», это сильный сигнал релевантности. Если он содержит «как» — почти никакой.

### Компонент 3: Нормализация по длине документа

Длинный документ статистически содержит больше вхождений любого слова. Чтобы не было перекоса в пользу длинных документов, вводится нормализация:

```
norm(d) = 1 - b + b × (|d| / avgdl)
```

где:
- `|d|` — длина документа (в токенах)
- `avgdl` — средняя длина документа в коллекции
- `b` — параметр (обычно 0.75)

Если документ длиннее среднего → знаменатель больше → скор уменьшается.
Если документ короче среднего → знаменатель меньше → скор увеличивается.

---

## 4. Полная формула BM25

Для запроса `Q`, состоящего из токенов `q₁, q₂, ..., qₙ`, скор документа `d`:

```
BM25(d, Q) = Σ IDF(qᵢ) × [ f(qᵢ,d) × (k₁ + 1) ] / [ f(qᵢ,d) + k₁ × (1 - b + b × |d|/avgdl) ]
```

То есть для каждого токена запроса считаем его вклад и суммируем.

## 5. Пошаговый пример с числами

**Дано:**
- Коллекция: 1000 документов, средняя длина = 200 токенов
- Запрос: `"квантизация GPTQ"`
- Документ D: длина 300 токенов, содержит «квантизация» 4 раза, «GPTQ» 2 раза
- «квантизация» встречается в 30 документах коллекции
- «GPTQ» встречается в 5 документах коллекции
- Параметры: k₁ = 1.2, b = 0.75

**Шаг 1: IDF**

```
IDF("квантизация") = ln((1000 - 30 + 0.5)/(30 + 0.5) + 1)
                   = ln(970.5/30.5 + 1)
                   = ln(32.8)
                   ≈ 3.49

IDF("GPTQ") = ln((1000 - 5 + 0.5)/(5 + 0.5) + 1)
            = ln(995.5/5.5 + 1)
            = ln(182.0)
            ≈ 5.20
```

«GPTQ» редче → выше вес.

**Шаг 2: Нормализация длины**

```
norm = 1 - 0.75 + 0.75 × (300/200)
     = 0.25 + 0.75 × 1.5
     = 0.25 + 1.125
     = 1.375
```

Документ длиннее среднего → штрафуется.

**Шаг 3: Взвешенная TF для каждого токена**

Для «квантизация» (f = 4):
```
TF_weighted = (4 × 2.2) / (4 + 1.2 × 1.375)
            = 8.8 / (4 + 1.65)
            = 8.8 / 5.65
            ≈ 1.56
```

Для «GPTQ» (f = 2):
```
TF_weighted = (2 × 2.2) / (2 + 1.2 × 1.375)
            = 4.4 / (2 + 1.65)
            = 4.4 / 3.65
            ≈ 1.21
```

**Шаг 4: Итоговый скор**

```
BM25(D, Q) = IDF("квантизация") × TF_weighted("квантизация")
           + IDF("GPTQ") × TF_weighted("GPTQ")

           = 3.49 × 1.56 + 5.20 × 1.21
           = 5.44 + 6.29
           ≈ 11.73
```

Аналогично считаем для всех документов коллекции, сортируем по убыванию скора → получаем ранжированный список.

## 6. Токенизация и предобработка

Перед тем как считать BM25, текст обычно проходит предобработку:

**1. Lowercasing:**
```
"Квантизация" → "квантизация"
```

**2. Стоп-слова** (опционально):
Убираются слишком частые слова, которые не несут смысла:
```
"как", "и", "в", "на", "это", "что" → удаляются
```

**3. Стемминг / Лемматизация:**
```
"квантизация", "квантизации", "квантизацию" → "квантизаци" (стемминг)
"квантизация", "квантизации", "квантизацию" → "квантизация" (лемматизация)
```

Это нужно, чтобы разные формы одного слова считались одним токеном.

**Важно:** предобработка должна быть одинаковой и для документов, и для запроса. Иначе токены не совпадут.

## 7. Почему BM25 всё ещё актуален?

### Когда BM25 лучше эмбеддингов:

| Сценарий | Почему |
|----------|--------|
| Поиск по точным терминам (ID, коды ошибок, имена собственные) | Эмбеддинг может «размыть» точный термин |
| Поиск по редким словам | Эмбеддинг редкого слова может быть плохо обучен |
| Нужна интерпретируемость | BM25 прозрачен: видно, какое слово дало какой вклад |
| Очень большая коллекция | BM25-индекс (inverted index) компактнее и быстрее для обновления |
| Нет GPU для embedding-модели | BM25 работает на CPU и не требует нейросетей |

### Когда эмбеддинги лучше:

| Сценарий | Почему |
|----------|--------|
| Семантический поиск (синонимы, перефразирование) | BM25 не знает, что «автомобиль» ≈ «машина» |
| Запрос и документ сформулированы по-разному | BM25 требует лексического совпадения |
| Многоязычный поиск | Мультиязычные эмбеддинги работают лучше |

## 8. Гибридный поиск (зачем их комбинируют)

Именно поэтому в продвинутых RAG-системах используют **оба** подхода одновременно:

```
Запрос: "GPTQ квантизация весов"

BM25 находит:
  - Документ с точным упоминанием "GPTQ" (высокий IDF)
  - Документ с "квантизация весов" (совпадение фразы)

Vector search находит:
  - Документ про "сжатие параметров модели" (семантически близко)
  - Документ про "уменьшение битности" (перефразирование)

Объединяем через Reciprocal Rank Fusion → финальный список
```

Так мы получаем и точное совпадение терминов (сильная сторона BM25), и семантическую близость (сильная сторона эмбеддингов).

## 9. Реализации

**Классические библиотеки:**
- **Elasticsearch / OpenSearch** — промышленный стандарт, BM25 встроен
- **Lucene / Solr** — Java-экосистема
- **rank_bm25** (Python) — простая библиотека для прототипов

```python
from rank_bm25 import BM25Okapi

# Токенизированные документы
corpus = [
    ["квантизация", "весов", "модели"],
    ["gptq", "квантизация", "hessian"],
    ["обучение", "трансформеров"],
]

bm25 = BM25Okapi(corpus)

# Запрос (тоже токенизированный)
query = ["квантизация", "gptq"]
scores = bm25.get_scores(query)
top_docs = bm25.get_top_n(query, corpus, n=2)
```

**В контексте vector DB:**
- **Weaviate** — встроенный hybrid search (BM25 + vector)
- **Qdrant** — поддержка sparse vectors (можно реализовать BM25)
- **Elasticsearch** — можно комбинировать с vector search через script scoring

## 1. Рост размера векторной БД

### Математика (приблизительная)

**Single-vector подход:**
```
1 документ = 1 вектор
1 вектор = N измерений × 4 байта (float32)

Пример: 10,000 документов × 384 измерения × 4 bytes = ~15 MB
```

**Multi-vector подход (4 вектора на документ):**
```
1 документ = 4 вектора
4 вектора = 4 × N измерений × 4 байта

Пример: 10,000 документов × 4 вектора × 384 × 4 bytes = ~60 MB
```

**Но это только векторы!** Реальный размер БД включает:
- Сами тексты документов (обычно самый большой компонент)
- Метаданные
- Индексные структуры (для approximate search)

### Реальные цифры на примере

Пусть у вас 100,000 документов (средний размер 2KB текста):

| Компонент | Single-vector | Multi-vector (4x) |
|-----------|---------------|-------------------|
| Векторы (384d, float32) | ~150 MB | ~600 MB |
| Тексты документов | ~200 MB | ~200 MB |
| Метаданные | ~50 MB | ~50 MB |
| Индекс (HNSW) | ~300 MB | ~1.2 GB |
| **Итого** | **~700 MB** | **~2.1 GB** |

**Рост: примерно 3x** (не 4x, потому что тексты и метаданные не дублируются).

## 2. Влияние на производительность

### Индексация (offline)
- **Время:** 4x дольше (нужно вычислить 4 эмбеддинга вместо 1)
- **Embedding API calls:** 4x больше (если используете платный API)
- **Память:** пиковое потребление выше, но не критично

### Поиск (online)
- **Latency:** зависит от реализации:
  - **Наивный подход:** 4 отдельных поиска → 4x медленнее
  - **Оптимизированный:** объединённый индекс с метаданными → ~1.5-2x медленнее
  
```python
# Наивный подход (медленно)
results_text = vector_db.search(query_vec_text, k=10)
results_summary = vector_db.search(query_vec_summary, k=10)
results_keywords = vector_db.search(query_vec_keywords, k=10)
results_tables = vector_db.search(query_vec_tables, k=10)
final_results = merge_and_deduplicate(...)

# Оптимизированный подход (быстрее)
# Один индекс с полем "vector_type"
results = vector_db.search(
    query_vec_text,  # используем основной вектор для поиска
    k=50,  # берём больше кандидатов
    where={"vector_type": {"$in": ["text", "summary", "keywords", "tables"]}}
)
# Re-ranking по всем типам векторов
```

## 3. Когда multi-vector оправдан

### ✅ Оправдано:

**1. Документы с разнородной структурой**
```
Пример: техническая документация
- Текст: описание работы функции
- Таблица: параметры и типы
- Код: примеры использования
- Диаграмма: архитектура системы
```
Каждый тип информации лучше ищется своим способом.

**2. Разные типы запросов от пользователей**
```
Запрос 1: "как работает attention?" → ищем по тексту
Запрос 2: "какие параметры у функции X?" → ищем по таблицам
Запрос 3: "покажи пример использования" → ищем по коду
```

**3. Критично высокое качество retrieval**
Если recall@10 должен быть >95%, и у вас есть бюджет на хранение/вычисления.

**4. Маленькая коллекция (<50,000 документов)**
Рост размера БД не критичен, а качество retrieval важно.

### ❌ Не оправдано:

**1. Однородные документы**
```
Пример: новостные статьи, блог-посты
- Весь контент = текст
- Нет таблиц, диаграмм, кода
```
Multi-vector даст минимальный прирост качества при 4x росте затрат.

**2. Большая коллекция (>500,000 документов)**
Рост с 3.5GB до 10.5GB может быть критичен по стоимости инфраструктуры.

**3. Budget-constrained проект**
- 4x больше embedding API calls = 4x больше денег
- 3x больше хранилища = дороже инфраструктура
- 2x медленнее поиск = больше GPU/CPU ресурсов

**4. Простая задача retrieval**
Если baseline single-vector уже даёт recall@10 >85%, multi-vector может дать только +2-3% при 4x затратах.

## 4. Альтернативы (дешевле, но эффективнее)

### Альтернатива 1: Parent Document Retriever
```
Индексируем:
- Маленькие чанки (256 токенов) → для точного поиска
- Большие чанки (1024 токенов) → для контекста

Связь: small_chunk.parent_id = large_chunk.id
```
**Рост БД:** ~2x (а не 4x)  
**Качество:** часто сравнимо с multi-vector  
**Проще в реализации**

### Альтернатива 2: Hybrid Search (BM25 + Vector)
```
Для каждого документа:
- 1 вектор (dense retrieval)
- BM25 индекс (sparse retrieval)
```
**Рост БД:** ~1.5x (BM25 индекс компактнее векторов)  
**Качество:** отлично работает для точных совпадений терминов  
**Встроено в Weaviate/Elasticsearch**

### Альтернатива 3: Summary-only multi-vector
```
Вместо 4 векторов:
- 1 вектор полного текста
- 1 вектор summary (создаётся LLM)
```
**Рост БД:** ~2x  
**Качество:** summary часто покрывает таблицы и ключевые слова  
**Дешевле в индексации**

## 7. Реальный кейс: когда multi-vector провалился

**Компания:** Enterprise search для технической документации  
**Подход:** Multi-vector (текст + таблицы + код + изображения)  
**Результат:**
- Качество retrieval: +4% recall@10 vs baseline
- Стоимость: +300% embedding API calls
- Latency: +180% search time
- ROI: отрицательный

**Почему:** 90% запросов были семантическими ("как работает X"), и single-vector + re-ranking давал 92% recall уже на baseline.

**Вывод:** Multi-vector — это "тяжёлая артиллерия". Используйте только когда:
1. У вас действительно разнородные документы
2. Baseline retrieval недостаточно качественный
3. Есть бюджет на дополнительные вычисления

Для большинства задач **Parent Document Retriever + Hybrid Search** дают 80% пользы при 20% затрат.

## 1. Что такое "агент" в контексте LLM

Прежде чем сравнивать фреймворки, зафиксируем терминологию. **Агент** — это LLM + цикл принятия решений:

```
while not done:
    observation = environment.observe()
    thought = llm.think(observation)
    action = llm.decide(thought)
    result = environment.act(action)
    environment.update_state(result)
```

Ключевые признаки агента:
- **Автономность** — принимает решения без прямого указания на каждом шаге
- **Использование инструментов** — вызывает внешние функции/API
- **Память** — сохраняет состояние между итерациями
- **Целеполагание** — работает на достижение цели, а не просто отвечает на вопрос

**Multi-agent система** — это когда несколько таких агентов взаимодействуют между собой (обмениваются сообщениями, делегируют задачи).

## 2. LangGraph — stateful graph-based подход

**Философия:** явный контроль над потоком выполнения через граф состояний.

### Ключевые концепции:

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict, Annotated

class AgentState(TypedDict):
    messages: list
    context: dict
    iteration: int

# Определяем узлы графа
def researcher(state: AgentState) -> AgentState:
    # вызов LLM + инструментов для исследования
    ...

def writer(state: AgentState) -> AgentState:
    # генерация финального ответа
    ...

def should_continue(state: AgentState) -> str:
    if state["iteration"] > 3:
        return "end"
    return "continue"

# Строим граф
graph = StateGraph(AgentState)
graph.add_node("researcher", researcher)
graph.add_node("writer", writer)
graph.add_conditional_edges(
    "researcher",
    should_continue,
    {"continue": "writer", "end": END}
)
graph.add_edge("writer", END)

app = graph.compile()
```

### Сильные стороны:
- **Полный контроль** над потоком выполнения (видно каждый шаг)
- **Детерминированность** — граф можно отладить, как обычный код
- **Визуализация** — граф можно экспортировать в mermaid/Graphviz
- **Persistence** — встроенная поддержка сохранения состояния между запусками
- **Human-in-the-loop** — легко добавить точки прерывания для одобрения человеком

### Слабые стороны:
- **Verbose** — для простой задачи нужно написать много кода
- **Кривая обучения** — нужно понимать концепцию state machine
- **Не идеален для multi-agent** — хотя можно, но это не его сильная сторона

### Когда использовать:
- Сложные workflows с ветвлением и циклами
- Нужен контроль и наблюдаемость каждого шага
- Production-системы с требованиями к reliability
- Ваш текущий кейс — агент как интерфейс к артефактам

## 3. AutoGen — conversation-centric подход

**Философия:** агенты — это участники разговора, которые обмениваются сообщениями.

### Ключевые концепции:

```python
from autogen import ConversableAgent, GroupChat, GroupChatManager

# Создаём агентов с разными ролями
researcher = ConversableAgent(
    name="Researcher",
    system_message="Ты исследователь. Собирай информацию из доступных источников.",
    llm_config={"config_list": [...]}
)

writer = ConversableAgent(
    name="Writer",
    system_message="Ты писатель. Формулируй чёткие ответы на основе данных.",
    llm_config={"config_list": [...]}
)

# Создаём "менеджера" группы
group_chat = GroupChat(
    agents=[researcher, writer],
    messages=[],
    max_round=10
)

manager = GroupChatManager(groupchat=group_chat)

# Запускаем разговор
user_proxy = ConversableAgent(name="User")
user_proxy.initiate_chat(
    manager,
    message="Напиши обзор по теме X"
)
```

### Сильные стороны:
- **Естественная multi-agent коммуникация** — агенты "разговаривают" друг с другом
- **Гибкость ролей** — легко создавать специализированных агентов
- **Встроенная поддержка code execution** — агенты могут писать и запускать код
- **Проще для multi-agent сценариев** — чем LangGraph

### Слабые стороны:
- **Меньше контроля** над потоком — разговор может уйти в сторону
- **Сложнее отладка** — непредсказуемые паттерны коммуникации
- **Труднее гарантировать завершение** — агенты могут зациклиться

### Когда использовать:
- Задачи, требующие "мозгового штурма" между агентами
- Сценарии с code generation и execution
- Прототипирование multi-agent систем
- Когда нужна естественная коммуникация между агентами

---

## 4. CrewAI — role-based подход

**Философия:** команда агентов с чёткими ролями, задачами и иерархией.

### Ключевые концепции:

```python
from crewai import Agent, Task, Crew

# Определяем агентов с ролями
researcher = Agent(
    role="Senior Research Analyst",
    goal="Находить актуальную информацию по заданным темам",
    backstory="Опытный аналитик с 10-летним стажем...",
    tools=[search_tool, scrape_tool],
    llm="gpt-4"
)

writer = Agent(
    role="Content Writer",
    goal="Писать увлекательные статьи на основе данных",
    backstory="Профессиональный копирайтер...",
    llm="gpt-4"
)

# Определяем задачи
research_task = Task(
    description="Исследуй тему X и собери ключевые факты",
    agent=researcher,
    expected_output="Список из 10 ключевых фактов с источниками"
)

writing_task = Task(
    description="Напиши статью на основе исследования",
    agent=writer,
    expected_output="Статья из 500 слов"
)

# Создаём команду
crew = Crew(
    agents=[researcher, writer],
    tasks=[research_task, writing_task],
    process="sequential"  # или "hierarchical"
)

# Запускаем
result = crew.kickoff()
```

### Сильные стороны:
- **Интуитивная модель** — как реальная команда с ролями
- **Декларативный подход** — описываешь "что", а не "как"
- **Встроенные процессы** — sequential, hierarchical
- **Хорошо для production** — предсказуемое выполнение задач

### Слабые стороны:
- **Менее гибкий** — сложнее реализовать нестандартные workflows
- **Абстракция скрывает детали** — труднее кастомизировать поведение
- **Молодой проект** — меньше сообщества и примеров

### Когда использовать:
- Чётко определённые workflows с ролями (research → write → review)
- Когда нужна предсказуемость и повторяемость
- Production-системы с минимальной кастомизацией
- Когда команда знакома с концепцией "ролей" из бизнес-процессов

## 5. LlamaIndex — data framework для RAG

**Философия:** не агентный фреймворк в чистом виде, а framework для работы с данными и retrieval.

### Ключевые концепции:

```python
from llama_index.core import VectorStoreIndex, SimpleDirectoryReader
from llama_index.core.agent import ReActAgent
from llama_index.core.tools import QueryEngineTool

# Загружаем документы
documents = SimpleDirectoryReader("./data").load_data()

# Создаём индекс
index = VectorStoreIndex.from_documents(documents)
query_engine = index.as_query_engine()

# Превращаем query engine в инструмент
query_tool = QueryEngineTool.from_defaults(
    query_engine=query_engine,
    name="knowledge_base",
    description="Поиск по базе знаний компании"
)

# Создаём агента поверх инструментов
agent = ReActAgent.from_tools(
    tools=[query_tool, calculator_tool, api_tool],
    verbose=True
)

# Агент может использовать retrieval как инструмент
response = agent.chat("Какие были результаты Q3?")
```

### Сильные стороны:
- **Лучший-in-class для RAG** — богатейший набор retrieval strategies
- **Data connectors** — интеграция с 100+ источниками данных
- **Гибкие индексы** — vector, tree, keyword, knowledge graph
- **Можно комбинировать с LangGraph** — LlamaIndex для retrieval, LangGraph для orchestration

### Слабые стороны:
- **Не полноценный агентный фреймворк** — слабее в complex workflows
- **Overengineering для простых задач** — много абстракций
- **Кривая обучения** — много концепций (nodes, indices, query engines, retrievers)

### Когда использовать:
- Сложные RAG-системы с множеством источников данных
- Когда нужны продвинутые retrieval техники (auto-merging, recursive retrieval)
- В комбинации с другими фреймворками (LlamaIndex + LangGraph)
- Data-intensive applications

## 7. Когда multi-agent оправдан, а когда overengineering

### ✅ Оправдано:

**1. Задача требует разных экспертиз**
```
Пример: автоматическая генерация отчёта
- Research Agent: собирает данные
- Analyst Agent: анализирует тренды  
- Writer Agent: формулирует выводы
- Reviewer Agent: проверяет качество
```
Каждый агент специализируется на своей части — это эффективнее, чем один универсальный агент.

**2. Нужен adversarial validation**
```
Пример: генерация кода
- Generator Agent: пишет код
- Reviewer Agent: находит баги
- Generator Agent: исправляет
```
Конфликт ролей улучшает качество результата.

**3. Параллельная обработка независимых подзадач**
```
Пример: анализ 100 документов
- 10 Researcher Agents: каждый анализирует 10 документов
- Synthesizer Agent: объединяет результаты
```
Ускоряет выполнение за счёт параллелизма.

**4. Симуляция stakeholder'ов**
```
Пример: оценка бизнес-решения
- CEO Agent: оценивает стратегию
- CFO Agent: оценивает финансы
- CTO Agent: оценивает техническую реализацию
```
Даёт многогранную оценку решения.

### ❌ Overengineering:

**1. Простая линейная задача**
```
❌ Плохо:
- Researcher Agent → Writer Agent → Editor Agent
  для написания простого email

✅ Лучше:
- Один агент с тремя шагами в LangGraph
```

**2. Все агенты используют одну и ту же LLM и промпт**
```
❌ Плохо:
- "Researcher" и "Analyst" — это один и тот же GPT-4
  с разными system prompts

✅ Лучше:
- Один агент с разными инструментами для разных задач
```

**3. Нет чёткого разделения ответственности**
```
❌ Плохо:
- Агент 1 может делать X и Y
- Агент 2 может делать Y и Z
- Непонятно, кто что делает

✅ Лучше:
- Чёткие границы: Агент 1 = только X, Агент 2 = только Z
```

**4. Задача решается одним вызовом LLM**
```
❌ Плохо:
- Multi-agent система для ответа на FAQ

✅ Лучше:
- RAG + один LLM call
```

### Decision Framework:

```
1. Можно ли разбить задачу на независимые подзадачи 
   с разными требованиями к экспертизе?
   ├─ Нет → Single agent
   └─ Да → вопрос 2

2. Нужна ли коммуникация между подзадачами?
   ├─ Нет → Parallel single agents
   └─ Да → Multi-agent система

3. Можно ли чётко определить роли и ответственность?
   ├─ Нет → Переосмыслите архитектуру
   └─ Да → Multi-agent оправдан
```

## 8. Практические паттерны комбинации

В реальных проектах часто комбинируют фреймворки:

### Паттерн 1: LangGraph + LlamaIndex
```
LangGraph: orchestration workflows
LlamaIndex: retrieval engine

Пример:
1. LangGraph решает, нужен ли retrieval
2. Если да → вызывает LlamaIndex query engine
3. Получает контекст → передаёт в LLM
```

### Паттерн 2: LangGraph + AutoGen
```
LangGraph: high-level workflow
AutoGen: multi-agent brainstorming внутри одного узла

Пример:
1. LangGraph node "ideation"
2. Внутри node запускается AutoGen group chat
3. Результат conversation → следующий node
```

### Паттерн 3: CrewAI для production, LangGraph для prototyping
```
Prototyping: LangGraph (быстрее итерации, больше контроля)
Production: CrewAI (предсказуемость, меньше кода)
```

## 9. Связь с вашим проектом

Вы используете **LangGraph для агента как tool-calling интерфейса к артефактам**. Это отличный выбор, потому что:

1. **Контроль** — вы точно знаете, когда и какие инструменты вызываются
2. **Наблюдаемость** — легко отладить, если что-то пошло не так
3. **Производительность** — нет overhead от multi-agent коммуникации
4. **Масштабируемость** — можно добавить новые инструменты без переписывания архитектуры

### Рекомендации для развития:

**Если нужна более сложная логика:**
- Добавьте **conditional edges** для разных сценариев
- Используйте **subgraphs** для модульности
- Внедрите **human-in-the-loop** для критичных решений

**Если понадобится multi-agent:**
- Начните с **LangGraph subgraphs** (каждый subgraph = "агент")
- Если нужно больше — рассмотрите **AutoGen** для brainstorming задач
- Избегайте **CrewAI**, если вам нужен fine-grained контроль

**Для улучшения retrieval:**
- Интегрируйте **LlamaIndex** как retrieval engine
- Используйте его продвинутые техники (auto-merging, recursive retrieval)
- LangGraph остаётся для orchestration

## 1. Краткий ответ: базовый механизм один, но организация разная

**Да**, в основе каждого агента (и в AutoGen, и в LangGraph, и в CrewAI) лежит **один и тот же фундаментальный паттерн**, который мы разбирали в D.3-D.4:

```
LLM + Prompt + Tools + Цикл принятия решений + Function Calling
```

**Но нет**, агенты в AutoGen внутри **не реализованы как граф состояний** (как в LangGraph). Они используют другой механизм координации — **обмен сообщениями**.

Разберём подробнее.

---

## 2. Фундаментальный цикл агента (общий для всех)

Каждый агент, независимо от фреймворка, внутри работает по этому циклу:

```
1. Получил вход (сообщение/состояние)
2. Передал в LLM с системным промптом и доступными инструментами
3. LLM решает:
   ├─ Вызвать инструмент → выполнить → результат обратно в контекст → шаг 2
   └─ Сформулировать финальный ответ → вернуть
4. Повторять пока не выполнится условие остановки
```

Это и есть то, что мы разбирали в **D.4 (Tool Calling)**:
- LLM видит описание инструментов (JSON Schema)
- LLM генерирует структурированный вызов
- Внешняя система выполняет функцию
- Результат подаётся обратно в LLM

**Важно:** этот цикл реализован *внутри каждого агента*. Не важно, используете вы AutoGen, LangGraph или пишете вручную — внутри агента происходит именно это.

---

## 3. Как это выглядит в AutoGen (через сообщения)

В AutoGen агент — это **участник разговора**. Его внутренний цикл выглядит так:

```python
# Псевдокод внутреннего цикла агента в AutoGen
class Agent:
    def receive(self, message, sender):
        # 1. Добавляем сообщение в историю
        self.history.append({"role": "user", "content": message})
        
        # 2. Запрашиваем ответ у LLM с инструментами
        while True:
            response = llm.chat(
                messages=self.history,
                tools=self.tools
            )
            
            # 3. Если LLM хочет вызвать инструмент
            if response.tool_calls:
                for call in response.tool_calls:
                    result = execute_tool(call)
                    self.history.append({"role": "tool", "content": result})
                continue  # продолжаем цикл
            
            # 4. Если LLM вернул финальный ответ
            else:
                self.history.append({"role": "assistant", "content": response})
                return response
```

**Ключевой момент:** решение о том, вызывать ли инструмент, продолжать ли поиск или вернуть результат — принимает **сама LLM** через function calling. Это тот же механизм, что и в D.4.

### Координация между агентами в AutoGen

Когда у вас несколько агентов (например, в GroupChat), координация происходит **через сообщения**:

```
Researcher: "Я нашёл информацию по теме. Вот что получилось: [результат]"
    ↓ (сообщение в чат)
GroupChat Manager: решает, кто следующий говорит
    ↓
Writer: "Спасибо, теперь напишу статью на основе этих данных"
    ↓ (сообщение в чат)
Reviewer: "Нужно уточнить вот этот момент..."
    ↓
... и так далее
```

**Внутри каждого агента** происходит тот самый цикл (вызов инструментов, решение продолжить/остановиться). Но **между агентами** — просто обмен сообщениями.

---

## 4. Как это выглядит в LangGraph (через граф состояний)

В LangGraph вы **явно определяете** поток управления:

```python
# Псевдокод LangGraph
def research_node(state):
    # Внутри узла — тот же самый цикл агента (LLM + tools)
    result = agent_with_tools(state["query"], tools=[search, fetch])
    state["research_results"].append(result)
    return state

def should_continue(state):
    # ЯВНАЯ логика принятия решения (не эмерджентная)
    if state["iteration"] >= 3:
        return "finish"
    if state["research_results"][-1]["confidence"] > 0.9:
        return "finish"
    return "continue_research"

graph.add_node("research", research_node)
graph.add_conditional_edges("research", should_continue, ...)
```

**Ключевое отличие:**
- В **AutoGen** решение "продолжать или нет" принимает **LLM** (эмерджентное поведение)
- В **LangGraph** вы **сами пишете логику** переходов (явное управление)

## 5. Сравнение: кто принимает решение "хватит ли"?

| Ситуация | AutoGen | LangGraph |
|----------|---------|-----------|
| Когда вызвать инструмент? | LLM агента решает | Обычно явно определено в узле графа |
| Когда прекратить поиск? | LLM решает или `max_round` | Явная функция `should_continue` |
| Когда вернуть результат? | LLM решает (нет больше tool_calls) | Определяется графом (переход к узлу "ответ") |
| Кто следующий говорит (в multi-agent)? | GroupChat Manager (часто через LLM) | Явно определено рёбрами графа |

## 6. Терминация: как агенты понимают, что пора остановиться

Это критически важный аспект, потому что без него агенты могут зациклиться. Разные фреймворки решают это по-разному:

### В AutoGen:

```python
# Способ 1: max_round (жёсткий лимит)
group_chat = GroupChat(
    agents=[researcher, writer],
    max_round=10  # максимум 10 обменов сообщениями
)

# Способ 2: специальные ключевые слова
# Агент может отправить сообщение с "TERMINATE"
# GroupChat Manager видит это и останавливает разговор

# Способ 3: кастомная функция-терминатор
def is_termination_msg(message):
    return "FINAL ANSWER:" in message["content"]
```

### В LangGraph:

```python
# Явная логика в функции-переходнике
def should_continue(state):
    # Проверяем конкретные условия
    if state["task_completed"]:
        return END
    if state["iteration"] > max_iterations:
        return END
    return "continue"
```

### В реальных агентах (как в Cursor):

Обычно комбинация:
- **Мягкий лимит** (например, 25 итераций)
- **Решение LLM** (если она считает задачу выполненной)
- **Таймаут** (если агент думает слишком долго)

## 7. Пример с Cursor: динамическая оркестрация

Вы упомянули очень хороший пример — **режим plan в Cursor**, где агенты могут сами решать вызвать субагентов. Это продвинутый паттерн, который называется **динамическая оркестрация**.

### Как это работает концептуально:

```
Главный агент (Planner):
1. Анализирует задачу пользователя
2. Решает: "Это сложная задача, нужно разбить на подзадачи"
3. ВЫЗЫВАЕТ ИНСТРУМЕНТ "создать_субагента":
   {
     "tool": "spawn_subagent",
     "arguments": {
       "task": "Исследовать библиотеку X",
       "agent_type": "researcher"
     }
   }
4. Система создаёт новый экземпляр агента
5. Субагент выполняет задачу и возвращает результат
6. Главный агент продолжает работу
```

### Ключевая идея:

**Создание субагентов — это тоже вызов инструмента** (то, что мы разбирали в D.4)! Просто в качестве инструмента выступает функция, которая создаёт и запускает другого агента.

```
Обычный инструмент:  LLM → вызывает функцию → получает результат
Инструмент-агент:    LLM → вызывает функцию "создай агента" → агент выполняет задачу → возвращает результат
```

### Где это применяется:

- **Cursor** (режим plan и agent)
- **Devin** (AI software engineer)
- **Anthropic Claude** с функцией "computer use"
- **OpenAI Swarm** (экспериментальный фреймворк)
- **CrewAI** с иерархическими процессами

### Архитектурные варианты реализации:

**Вариант A: Статическая оркестрация (как в LangGraph)**
```
Вы заранее определяете граф:
Planner → Researcher → Writer → Reviewer
```
Плюсы: предсказуемо, легко отладить  
Минусы: негибко, не адаптируется к задаче

**Вариант B: Динамическая оркестрация (как в Cursor)**
```
Planner сам решает, кого создать:
- Если задача требует кода → создаёт Coder-агента
- Если требует исследований → создаёт Researcher-агента
- Если простая → делает сам
```
Плюсы: гибко, адаптируется к задаче  
Минусы: непредсказуемо, сложнее отладить

**Вариант C: Гибридный подход**
```
Базовый граф определён заранее (как в LangGraph)
Но внутри узлов агенты могут динамически создавать субагентов
```
Это то, что делают современные продвинутые системы.

## 8. Связь с тем, что мы разбирали в D.3-D.4

Теперь можно увидеть полную картину:

```
Уровень 1: Базовый механизм (D.4 - Tool Calling)
├── LLM + Prompt + JSON Schema инструментов
├── Функция вызывает инструмент
└── Результат возвращается в LLM

Уровень 2: Цикл агента (D.3 - LangGraph)
├── Повторение уровня 1 в цикле
├── Управление состоянием
└── Условия остановки

Уровень 3: Координация агентов (D.6 - фреймворки)
├── Как агенты общаются между собой
├── Кто принимает решения о следующем шаге
└── Как обрабатываются ошибки и конфликты

Уровень 4: Динамическая оркестрация (Cursor, Devin)
├── Агенты могут создавать других агентов
├── Адаптация структуры под задачу
└── Иерархия агентов
```

**Каждый уровень строится на предыдущем.** В AutoGen и других фреймворках внутри каждого агента работает тот же механизм, что мы разбирали в D.4. Но фреймворки добавляют уровень координации между агентами.

## 9. Практический пример: как это выглядит в коде

### Пример на AutoGen с инструментами:

```python
from autogen import ConversableAgent, register_function

# Определяем функцию-инструмент
def search_web(query: str) -> str:
    """Ищет информацию в интернете"""
    return f"Результаты поиска по '{query}': ..."

# Регистрируем инструмент для агента
researcher = ConversableAgent(
    name="Researcher",
    system_message="""Ты исследователь. 
    Используй инструмент search_web для поиска информации.
    Когда достаточно информации, скажи 'TERMINATE'.""",
    llm_config={"config_list": [...]}
)

# Регистрируем функцию
register_function(
    search_web,
    caller=researcher,
    executor=user_proxy  # кто выполняет функцию
)

# Запускаем разговор
user_proxy.initiate_chat(
    researcher,
    message="Найди информацию про квантизацию LLM"
)
```

**Что происходит внутри:**
1. `user_proxy` отправляет сообщение `researcher`
2. `researcher` передаёт сообщение в LLM
3. LLM решает: нужно вызвать `search_web`
4. AutoGen выполняет функцию, возвращает результат
5. Результат подаётся обратно в LLM
6. LLM решает: достаточно информации или нужен ещё поиск
7. Если достаточно → отправляет финальный ответ с "TERMINATE"
8. Разговор завершается

**Внутри исследователя работает тот же цикл**, что и в LangGraph-узле. Разница в том, как организована координация *между* агентами.

**Ваш вопрос:** "каждый участник AutoGen реализован через механизм, похожий на LangGraph?"

**Ответ:**
- **Внутренний цикл одного агента** — да, это тот же механизм, что мы разбирали в D.3-D.4 (LLM + tools + цикл принятия решений)
- **Координация между агентами** — нет, в AutoGen это обмен сообщениями, а не граф состояний

- Это следующий уровень абстракции над тем, что мы разбирали

**Главный вывод:** все агентные фреймворки построены на одном фундаменте (function calling + цикл), но добавляют разные уровни абстракции для координации. Понимание базового механизма (которое у вас уже есть из D.3-D.4) позволяет понять любой агентный фреймворк.

## 1. Почему LLM требуют особого подхода к контейнеризации

Обычное приложение (веб-сервер, API, микросервис) имеет предсказуемые характеристики:
- Размер контейнера: 100MB-2GB
- Время старта: секунды
- Потребление памяти: стабильное, предсказуемое
- Реплики: взаимозаменяемые, stateless

**LLM-инференс — это другая вселенная:**
- Размер контейнера: 10-100GB (веса модели + CUDA + зависимости)
- Время старта: минуты (загрузка весов в GPU память)
- Потребление памяти: гигабайты GPU VRAM + гигабайты RAM для KV-cache
- Реплики: **НЕ** взаимозаменяемые (каждая реплика держит свою копию модели в VRAM)

**Ключевая проблема:** LLM-контейнер — это не просто "приложение в коробке", это **"модель в коробке"**. И модель — это огромный, тяжёлый, stateful объект.

## 2. Dockerfile patterns для LLM-serving

### Антипаттерн: "всё в одном слое"

```dockerfile
# ❌ ПЛОХО — долго пересобирается, огромные слои
FROM nvidia/cuda:12.1.0-runtime-ubuntu22.04

RUN apt-get update && apt-get install -y python3 python3-pip

COPY . /app
WORKDIR /app

RUN pip install torch transformers vllm
RUN pip install -r requirements.txt

# Веса модели тоже в контейнере
COPY model_weights/ /models/llama-7b/

CMD ["python", "serve.py"]
```

**Проблемы:**
- Любое изменение кода → пересборка всего (включая pip install)
- Веса модели (15GB) дублируются в каждом билде
- Невозможно обновить модель без пересборки образа

### Правильный паттерн: многоступенчатая сборка + разделение слоёв

```dockerfile
# Stage 1: базовые зависимости (меняются редко)
FROM nvidia/cuda:12.1.0-runtime-ubuntu22.04 as base

RUN apt-get update && apt-get install -y \
    python3.10 \
    python3-pip \
    && rm -rf /var/lib/apt/lists/*

# Stage 2: Python-зависимости (меняются при обновлении requirements.txt)
FROM base as dependencies

COPY requirements.txt /tmp/
RUN pip install --no-cache-dir -r /tmp/requirements.txt

# Stage 3: финальный образ
FROM dependencies as runtime

# Только код приложения (меняется часто)
COPY app/ /app/
WORKDIR /app

# Веса модели НЕ копируем в образ!
# Они будут монтироваться извне (volume, S3, model registry)

# Health check для K8s
HEALTHCHECK --interval=30s --timeout=10s --start-period=120s \
    CMD curl -f http://localhost:8000/health || exit 1

EXPOSE 8000

CMD ["python", "serve.py"]
```

**Преимущества:**
- Изменение кода → пересборка только последнего слоя (секунды)
- Веса модели загружаются отдельно (не в образе)
- Кэширование слоёв работает эффективно

### Паттерн: Model-as-a-Volume

Вместо того чтобы вшивать веса модели в Docker-образ, используйте **volumes**:

```yaml
# docker-compose.yml
services:
  llm-server:
    image: my-llm-server:latest
    volumes:
      - model_weights:/models
    environment:
      - MODEL_PATH=/models/llama-7b
```

**Как это работает:**
1. Docker-образ содержит только код + зависимости (2-5GB)
2. Веса модели (15-70GB) лежат на отдельном volume
3. При обновлении модели вы просто заменяете файлы на volume, не пересобирая образ

**Для продакшена (Kubernetes):**
```yaml
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: llm-server
spec:
  replicas: 2
  template:
    spec:
      containers:
      - name: llm-server
        image: my-llm-server:latest
        volumeMounts:
        - name: model-storage
          mountPath: /models
          readOnly: true
      volumes:
      - name: model-storage
        persistentVolumeClaim:
          claimName: llm-models-pvc
```

**Ещё лучше: Model Registry + dynamic loading**
```python
# serve.py
import os
from huggingface_hub import snapshot_download

MODEL_ID = os.environ.get("MODEL_ID", "meta-llama/Llama-2-7b-chat-hf")
CACHE_DIR = "/models/cache"

# Загружаем модель при старте контейнера (или используем кэш)
model_path = snapshot_download(
    repo_id=MODEL_ID,
    cache_dir=CACHE_DIR,
    local_files_only=False  # если нет в кэше — скачать

# Инициализируем vLLM/TGI с этой моделью
```

## 3. Cold Start vs Hot Inference: проблема загрузки весов

### Что такое cold start?

**Cold start** — это время от запуска контейнера до момента, когда модель готова принимать запросы.

Для LLM это время включает:
1. **Запуск контейнера** (секунды)
2. **Инициализация Python-окружения** (секунды)
3. **Загрузка весов модели с диска в RAM** (десятки секунд для 70B модели)
4. **Копирование весов из RAM в GPU VRAM** (десятки секунд)
5. **Инициализация KV-cache** (секунды)
6. **Warmup inference** (несколько forward passes для "прогрева" CUDA kernels)

**Итого: 2-5 минут для большой модели.**

### Почему это проблема?

**1. Autoscaling latency**  
Если нагрузка резко выросла и K8s решил добавить реплики, новые поды будут недоступны 2-5 минут. Это может привести к cascading failure.

**2. Rolling updates**  
При обновлении модели каждый новый под проходит через cold start. Если у вас 10 реплик, обновление займёт 20-50 минут.

**3. Cost optimization**  
Если вы выключаете реплики при низкой нагрузке (scale-to-zero), то каждый новый запрос после простоя будет ждать cold start.

### Решения проблемы cold start

#### Решение 1: Pre-warming (предварительный прогрев)

```python
# serve.py
import torch
from vllm import LLM, SamplingParams

class LLMServer:
    def __init__(self):
        # Загружаем модель
        self.llm = LLM(model="meta-llama/Llama-2-7b-chat-hf")
        
        # Warmup: делаем несколько "пустых" inference для прогрева CUDA
        self._warmup()
    
    def _warmup(self):
        """Прогрев CUDA kernels и аллокация памяти"""
        dummy_prompts = ["Hello"] * 4  # batch of 4
        sampling_params = SamplingParams(temperature=0.0, max_tokens=10)
        
        # Несколько warmup итераций
        for _ in range(3):
            self.llm.generate(dummy_prompts, sampling_params)
        
        print("Warmup completed")
    
    def generate(self, prompts):
        # Теперь модель готова к работе
        return self.llm.generate(prompts, sampling_params)

server = LLMServer()
```

**Плюсы:** модель готова к работе сразу после старта  
**Минусы:** cold start всё ещё занимает 2-5 минут

#### Решение 2: Model checkpoint caching

Сохраняйте уже загруженную модель в памяти между перезапусками:

```python
import torch
import pickle

# При первом запуске
llm = LLM(model="...")
torch.save(llm.state_dict(), "/cache/model_state.pt")

# При последующих запусках
if os.path.exists("/cache/model_state.pt"):
    llm.load_state_dict(torch.load("/cache/model_state.pt"))
else:
    llm = LLM(model="...")
    torch.save(llm.state_dict(), "/cache/model_state.pt")
```

**Проблема:** state_dict LLM — это не только веса, но и CUDA tensors, которые нельзя просто сериализовать.

#### Решение 3: Persistent volumes для model weights

```yaml
# K8s PVC для кэширования моделей
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: model-cache-pvc
spec:
  accessModes:
    - ReadWriteMany  # несколько подов могут читать
  resources:
    requests:
      storage: 500Gi
  storageClassName: fast-ssd
```

**Как работает:**
1. Первый под скачивает модель в PVC
2. Последующие поды видят модель уже скачанной
3. Загрузка с локального SSD быстрее, чем из S3/HuggingFace

#### Решение 4: Specialized model serving (vLLM, TGI)

Современные serving-движки уже оптимизированы для быстрого cold start:

```bash
# vLLM с tensor parallelism
python -m vllm.entrypoints.openai.api_server \
    --model meta-llama/Llama-2-7b-chat-hf \
    --tensor-parallel-size 2 \
    --gpu-memory-utilization 0.9
```

**vLLM автоматически:**
- Кэширует downloaded weights
- Оптимизирует загрузку в GPU
- Использует memory-mapped files для быстрого доступа

#### Решение 5: Model preloading в init container

```yaml
# K8s pod с init container
apiVersion: v1
kind: Pod
metadata:
  name: llm-server
spec:
  initContainers:
  - name: model-preloader
    image: model-downloader:latest
    command: ['python', 'download_model.py']
    volumeMounts:
    - name: model-storage
      mountPath: /models
  containers:
  - name: llm-server
    image: my-llm-server:latest
    volumeMounts:
    - name: model-storage
      mountPath: /models
```

**Как работает:**
1. Init container скачивает модель (может занять минуты)
2. Main container стартует только после завершения init container
3. Main container сразу видит готовую модель

## 4. GPU Sharing: как запускать несколько моделей на одном GPU

### Проблема

У вас есть GPU с 80GB VRAM (например, A100), но:
- Llama-70B требует 140GB (не помещается)
- Llama-7B требует 14GB (остаётся 66GB неиспользованными)
- Хотите запустить несколько моделей одновременно

### Решение 1: Multi-Instance GPU (MIG) — NVIDIA A100/H100

MIG позволяет физически разделить один GPU на несколько независимых инстансов:

```bash
# Включаем MIG
nvidia-smi -mig 1

# Создаём инстансы
nvidia-smi mig -cgi 9,9,9 -C  # 3 инстанса по 1g.10gb каждый
```

**Результат:** один A100 80GB превращается в 3 независимых GPU по ~20GB каждый.

**Плюсы:**
- Полная изоляция (один инстанс не влияет на другой)
- Гарантированная производительность
- Разные модели могут работать параллельно

**Минусы:**
- Только для A100/H100
- Фиксированные размеры инстансов (1g.10gb, 2g.20gb, 3g.40gb, 7g.80gb)
- Сложная настройка

**K8s интеграция:**
```yaml
# K8s pod с MIG
apiVersion: v1
kind: Pod
metadata:
  name: llm-server
spec:
  containers:
  - name: llm-server
    resources:
      limits:
        nvidia.com/mig-1g.10gb: 1  # один MIG инстанс
```

### Решение 2: Multi-Process Service (MPS)

MPS позволяет нескольким процессам **совместно использовать** один GPU без изоляции:

```bash
# Запускаем MPS daemon
nvidia-cuda-mps-control -d

# Запускаем несколько inference-серверов
python serve_model_a.py &
python serve_model_b.py &
python serve_model_c.py &
```

**Как работает:**
- Все процессы видят один GPU
- MPS координирует доступ к GPU
- Процессы выполняются параллельно (time-slicing на уровне CUDA kernels)

**Плюсы:**
- Работает на любом GPU
- Простая настройка
- Хорошая утилизация GPU

**Минусы:**
- Нет изоляции (один процесс может "голодать" другие)
- Нет гарантии производительности
- Может быть нестабильным при ошибках

### Решение 3: Time-slicing (K8s GPU sharing)

K8s может "разделить" один GPU между несколькими подами через time-slicing:

```yaml
# K8s ConfigMap для GPU sharing
apiVersion: v1
kind: ConfigMap
metadata:
  name: time-slicing-config
  namespace: gpu-operator
data:
  any: |-
    version: v1
    sharing:
      timeSlicing:
        resources:
        - name: nvidia.com/gpu
          replicas: 4  # один GPU делится на 4 виртуальных
```

**Как работает:**
- K8s видит 4 "виртуальных GPU" (хотя физически один)
- Каждый под получает доступ к GPU на короткое время
- Переключение между подами происходит на уровне драйвера

**Плюсы:**
- Простая настройка
- Работает на любом GPU
- Интеграция с K8s scheduling

**Минусы:**
- Нет изоляции памяти (все поды видят всю VRAM)
- Производительность зависит от количества активных подов
- Не подходит для production с высокими требованиями к latency

### Решение 4: Application-level batching (лучший подход)

Вместо того чтобы запускать несколько отдельных серверов, используйте **один сервер с несколькими моделями**:

```python
from vllm import LLM, SamplingParams

class MultiModelServer:
    def __init__(self):
        # Загружаем несколько моделей в один GPU
        self.models = {
            "llama-7b": LLM(model="meta-llama/Llama-2-7b-chat-hf"),
            "mistral-7b": LLM(model="mistralai/Mistral-7B-Instruct-v0.1"),
        }
    
    def generate(self, model_name: str, prompts: list[str]):
        llm = self.models[model_name]
        sampling_params = SamplingParams(temperature=0.7, max_tokens=100)
        return llm.generate(prompts, sampling_params)
```

**vLLM автоматически:**
- Управляет памятью между моделями
- Батчит запросы к разным моделям
- Выгружает неиспользуемые модели из VRAM

**Плюсы:**
- Максимальная утилизация GPU
- Нет overhead от переключения контекста
- Простое управление

**Минусы:**
- Требует кастомной реализации
- Не все serving-движки поддерживают multi-model

## 5. Health Checks для LLM-сервисов

### Проблема обычных health checks

Обычный health check:
```bash
curl http://localhost:8000/health
```

Для LLM этого **недостаточно**, потому что:
- Сервер может быть запущен, но модель ещё не загружена
- Модель загружена, но CUDA kernels не прогреты
- GPU перегружен и отвечает очень медленно

### Правильный health check для LLM

```python
from fastapi import FastAPI, HTTPException
import time

app = FastAPI()

class LLMHealthChecker:
    def __init__(self, llm):
        self.llm = llm
        self.last_check = 0
        self.check_interval = 60  # seconds
    
    async def check(self):
        """Комплексная проверка здоровья LLM"""
        
        # 1. Базовая проверка: модель загружена?
        if not hasattr(self.llm, 'model'):
            raise HTTPException(status_code=503, detail="Model not loaded")
        
        # 2. Проверка GPU памяти
        import torch
        if torch.cuda.is_available():
            free_memory = torch.cuda.mem_get_info()[0] / 1e9  # GB
            if free_memory < 2.0:  # меньше 2GB свободно
                raise HTTPException(status_code=503, detail="GPU memory low")
        
        # 3. Проверка latency (делаем тестовый inference)
        current_time = time.time()
        if current_time - self.last_check > self.check_interval:
            try:
                start = time.time()
                self.llm.generate(["Hello"], SamplingParams(max_tokens=5))
                latency = time.time() - start
                
                if latency > 5.0:  # больше 5 секунд
                    raise HTTPException(status_code=503, detail="High latency")
                
                self.last_check = current_time
            except Exception as e:
                raise HTTPException(status_code=503, detail=f"Inference failed: {e}")
        
        return {"status": "healthy"}

health_checker = LLMHealthChecker(llm)

@app.get("/health")
async def health():
    return await health_checker.check()

@app.get("/health/live")
async def liveness():
    """Liveness probe: просто проверка, что процесс жив"""
    return {"status": "alive"}

@app.get("/health/ready")
async def readiness():
    """Readiness probe: модель загружена и готова принимать запросы"""
    return await health_checker.check()
```

**K8s probes:**
```yaml
# deployment.yaml
spec:
  containers:
  - name: llm-server
    livenessProbe:
      httpGet:
        path: /health/live
        port: 8000
      initialDelaySeconds: 30
      periodSeconds: 10
    readinessProbe:
      httpGet:
        path: /health/ready
        port: 8000
      initialDelaySeconds: 120  # даём время на cold start
      periodSeconds: 10
      failureThreshold: 3
```

### Паттерн 2: Single model, multiple replicas

```yaml

  name: llm-server
```

- Load balancer распределяет запросы между репликами
- Каждая реплика независима
- Можно обновлять по одной (rolling update)

**Проблема:** каждая реплика держит свою копию модели в VRAM (3 × 14GB = 42GB).

### Паттерн 3: Tensor parallelism (одна модель на нескольких GPU)


**Как работает:**
- Модель разделяется на 4 части
- Каждая часть на отдельном GPU
- GPUs общаются через NVLink/PCIe

**K8s deployment:**
```yaml
spec:
  containers:
  - name: llm-server
    resources:
      limits:
        nvidia.com/gpu: 4  # 4 GPU на один под
```

**Когда использовать:** большие модели (70B+), которые не помещаются на одном GPU.

### Паттерн 4: Autoscaling

```yaml

  name: llm-server-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: llm-server
  minReplicas: 1
  maxReplicas: 10
  metrics:
  - type: Pods
    pods:
      metric:
        name: llm_queue_length
      target:
        type: AverageValue
        averageValue: "5"  # скейлим если очередь > 5 запросов

      metric:

        type: AverageValue
```

**Важно:** для LLM скейлинг по CPU/GPU utilization **не работает**, потому что:
- GPU может быть загружен на 30%, но очередь запросов огромная
- Или GPU загружен на 90%, но latency низкая (эффективный batching)

**Правильные метрики для скейлинга:**
- Длина очереди запросов
- Latency percentiles (p50, p95, p99)
- Throughput (запросов в секунду)

## 1. Почему масштабирование особенное

В классических микросервисах скейлинг относительно прост:
- Нагрузка растёт → увеличиваем количество реплик
- Нагрузка падает → уменьшаем
- Метрики: CPU utilization, requests per second

**В случае с LLM всё сложнее:**

| Проблема | Почему это сложно |
|----------|-------------------|
| **Дорогой старт реплики** | 2-5 минут на загрузку модели (см. E.1) |
| **Дорогая реплика** | Каждая реплика = 1+ GPU = $2-10/час |
| **Нелинейная нагрузка** | Запросы приходят батчами, с неравномерной длиной генерации |
| **Разные по стоимости запросы** | "Привет" = 5 токенов, "напиши эссе" = 2000 токенов |
| **Ограничение на размер батча** | Нельзя бесконечно увеличить батч — упираемся в память |

**Главное:** классический скейлинг по CPU/GPU utilization **не работает** для LLM. Это приведёт к катастрофическим последствиям в проде.

## 2. Почему стандартные метрики не работают

### Антипаттерн: скейлинг по GPU utilization

```yaml
# ❌ ПЛОХО — скейлинг по GPU utilization
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: llm-server-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: llm-server
  minReplicas: 1
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: nvidia.com/gpu
      target:
        type: Utilization
        averageUtilization: 70  # скейлим при 70% загрузки
```

**Почему это не работает:**

**Сценарий 1: Ложный скейл (ложный позитив)**
```
Ситуация:
- Один запрос на 2000 токенов
- GPU занят на 90% (генерация длинного ответа)
- Очередь пустая
- Новые запросы не приходят

Что делает скейлер:
- Видит 90% GPU utilization
- Создаёт новую реплику
- Реплика запускается 3 минуты
- К моменту, когда она готова, исходный запрос уже завершился
- Реплика простаивает (тратит деньги)
```

**Сценарий 2: Пропущенный скейл (ложный негатив)**
```
Ситуация:
- 10 коротких запросов в очереди
- Каждый занимает 50 мс
- Между запросами паузы
- GPU utilization в среднем 30%

Что делает скейлер:
- Видит 30% GPU utilization
- Не создаёт новые реплики
- Запросы стоят в очереди, копятся
- Latency растёт
- Пользователи жалуются
```

### Антипаттерн: скейлинг по CPU

```yaml
# ❌ ЕЩЁ ХУЖЕ — скейлинг по CPU
metrics:
- type: Resource
  resource:
    name: cpu
    target:
      type: Utilization
      averageUtilization: 70
```

**Проблема:** в LLM-инференсе CPU почти не используется. Вся работа на GPU. Метрика будет показывать ~5-10% даже при максимальной загрузке модели. Скейлер никогда не сработает.

## 3. Правильные метрики для скейлинга

### Метрика 1: Длина очереди запросов (queue length)

**Что измеряет:** сколько запросов ждут обработки.

**Почему это хорошая метрика:**
- Прямой индикатор перегрузки
- Независим от длины генерации
- Легко интерпретировать: "5 запросов в очереди" = нужно больше реплик

**Как экспортировать (пример на FastAPI):**
```python
from fastapi import FastAPI
import asyncio
from prometheus_client import Counter, Gauge, Histogram

app = FastAPI()

# Метрики для Prometheus
requests_queue = Gauge(
    'llm_requests_in_queue',
    'Number of requests waiting in queue'
)
requests_total = Counter(
    'llm_requests_total',
    'Total number of requests processed'
)
request_latency = Histogram(
    'llm_request_latency_seconds',
    'Request latency in seconds',
    buckets=[0.1, 0.5, 1.0, 2.0, 5.0, 10.0, 30.0]
)

class RequestQueue:
    def __init__(self, max_size=100):
        self.queue = asyncio.Queue(maxsize=max_size)
    
    async def enqueue(self, request):
        requests_queue.inc()
        await self.queue.put(request)
    
    async def dequeue(self):
        item = await self.queue.get()
        requests_queue.dec()
        return item

queue = RequestQueue()

@app.post("/generate")
async def generate(request: GenerateRequest):
    # Замеряем общую задержку
    with request_latency.time():
        # Ставим запрос в очередь
        await queue.enqueue(request)
        
        # Обработка (здесь вызывается LLM)
        result = await process_request(request)
        requests_total.inc()
        return result
```

**K8s HPA на основе очереди:**
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: llm-server-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: llm-server
  minReplicas: 1
  maxReplicas: 10
  metrics:
  - type: Pods
    pods:
      metric:
        name: llm_requests_in_queue
      target:
        type: AverageValue
        averageValue: "5"  # скейлим при >5 запросов в очереди
```

### Метрика 2: Latency percentiles

**Что измеряет:** время обработки запроса на разных перцентилях (p50, p95, p99).

**Почему это хорошая метрика:**
- Отражает пользовательский опыт
- Показывает "хвостовые" задержки, которые не видны в среднем
- Позволяет настроить скейлинг под SLA

**Почему не использовать среднее (mean):**
```
Запросы: [100ms, 100ms, 100ms, 100ms, 5000ms]
Mean: 1080ms (выглядит плохо)
p95: 5000ms (реальность для 5% пользователей)
p50: 100ms (большинство пользователей ок)
```

Среднее скрывает проблему: 95% запросов быстрые, но 5% ужасно медленные.

**Пример использования:**
```yaml
# Скейлим, если p95 latency > 3 секунд
metrics:
- type: Pods
  pods:
    metric:
      name: llm_request_latency_p95
    target:
      type: AverageValue
      averageValue: "3000"  # миллисекунды
```

### Метрика 3: Throughput (запросов в секунду)

**Что измеряет:** сколько запросов обрабатывается в единицу времени.

**Когда использовать:**
- Когда знаете максимальную производительность одной реплики
- Когда нужно масштабироваться под целевую нагрузку

**Пример расчёта:**
```
Известно:
- Одна реплика обрабатывает 10 запросов/сек (при батче 32)
- Целевая нагрузка: 50 запросов/сек

Решение:
- Нужно 5 реплик (50 / 10)
- Скейлер создаёт реплики до этого количества
```

### Метрика 4: GPU memory usage

**Что измеряет:** процент используемой видеопамяти.

**Когда использовать:**
- Как **дополнительную** метрику (не основную)
- Для предотвращения OOM (Out Of Memory)

```yaml
# Скейлим, если использование памяти > 85%
# (защита от OOM)
- type: Pods
  pods:
    metric:
      name: gpu_memory_usage_percent
    target:
      type: AverageValue
      averageValue: "85"
```

### Объяснение параметров HPA

**`behavior.scaleUp.stabilizationWindowSeconds: 60`**  
Ждать 60 секунд перед скейлом вверх. Защита от кратковременных всплесков.

**`behavior.scaleDown.stabilizationWindowSeconds: 300`**  
Ждать 5 минут перед скейлом вниз. Защита от "колебаний" (когда скейлер то создаёт, то удаляет реплики).

**`policies` для скейла:**  
- `scaleUp: 2 pods per 60 seconds` — не создавать больше 2 реплик за минуту
- `scaleDown: 1 pod per 60 seconds` — не удалять больше 1 реплики за минуту

**Почему это важно:**  
Помните про **2-5 минут cold start** из E.1? Если скейлер будет создавать реплики слишком быстро, он создаст их, они будут готовы через 3 минуты, но нагрузка уже упадёт. Реплики будут простаивать.

## 5. Trade-off Latency vs Throughput (размер батча)

Это одна из самых важных концепций для понимания прод-систем. Она напрямую связана с **B.1 (Continuous batching)** и **B.2 (vLLM)**, которые мы прошли ранее.

### Суть проблемы

Размер батча (сколько запросов обрабатывается параллельно) определяет баланс между:
- **Latency** — время ответа на один запрос
- **Throughput** — количество запросов в единицу времени

### Интуитивное понимание

Представьте ресторан:
- **Батч = 1:** повар готовит блюдо для одного гостя. Гость получает заказ через 5 минут. Но повар обрабатывает только 12 заказов в час.
- **Батч = 10:** повар готовит 10 блюд одновременно. Каждый гость ждёт 10 минут (потому что порции большие). Но повар обрабатывает 60 заказов в час.

**Через размер батча:**
- Маленький батч → низкая задержка, но низкая пропускная способность
- Большой батч → высокая пропускная способность, но высокая задержка

### Числовой пример

Пусть у нас есть vLLM сервер с моделью 7B на A100 GPU:

| Batch Size | Latency per Request (p50) | Throughput (req/s) | GPU Utilization |
|------------|--------------------------|-------------------|-----------------|
| 1 | 200 ms | 5 req/s | 30% |
| 8 | 250 ms | 32 req/s | 75% |
| 32 | 400 ms | 80 req/s | 95% |
| 64 | 800 ms | 80 req/s | 95% |
| 128 | 1600 ms | 80 req/s | 95% |

**Что происходит:**
- До батча 32 — пропускная способность растёт, задержка растёт медленно
- После батча 32 — пропускная способность упирается в потолок, задержка растёт линейно

**Почему так:**
- GPU имеет фиксированную память (например, 80GB)
- Каждый запрос требует память для KV-cache
- После определённого батча — память заполнена
- Дальнейшее увеличение батча не даёт прироста в пропускной способности

### Как это выглядит в коде (vLLM)

```python
from vllm import LLM, SamplingParams

# Настройка размера батча
llm = LLM(
    model="meta-llama/Llama-2-7b-chat-hf",
    max_num_seqs=32,           # максимальный размер батча
    max_num_batched_tokens=8192,  # максимальное количество токенов в батче
    gpu_memory_utilization=0.9    # использовать 90% памяти
)

# При обработке запросов
sampling_params = SamplingParams(temperature=0.7, max_tokens=100)

# Если запросов больше, чем размер батча — они встают в очередь
outputs = llm.generate(prompts, sampling_params)
```

**Параметры, влияющие на размер батча:**
- `max_num_seqs` — максимальное количество запросов, обрабатываемых параллельно
- `max_num_batched_tokens` — максимальное количество токенов во всём батче
- `gpu_memory_utilization` — сколько памяти выделять под KV-cache

### Как выбрать правильный размер батча

**Для низкой задержки (чат-боты, интерактивные приложения):**
```
Целевая задержка: < 500ms
Рекомендуемый батч: 1-8
Throughput: 5-30 req/s
```

**Для высокой пропускной способности (пакетная обработка, ETL):**
```
Целевая задержка: не критична
Рекомендуемый батч: 32-128
Throughput: максимальный
```

**Для баланса (обычные API):**
```
Целевая задержка: < 2 секунды
Рекомендуемый батч: 16-32
Throughput: 40-80 req/s
```

### Практический совет: измеряйте!

Не доверяйте теоретическим значениям. Замеряйте на вашем железе:

```python
import time
import asyncio
from vllm import LLM, SamplingParams

async def benchmark_batch_size(batch_size, num_requests=100):
    llm = LLM(
        model="meta-llama/Llama-2-7b-chat-hf",
        max_num_seqs=batch_size
    )
    sampling_params = SamplingParams(temperature=0.7, max_tokens=100)
    prompts = ["Tell me a story"] * num_requests
    
    start = time.time()
    outputs = llm.generate(prompts, sampling_params)
    total_time = time.time() - start
    
    return {
        "batch_size": batch_size,
        "total_time": total_time,
        "throughput": num_requests / total_time,
        "avg_latency": total_time / num_requests * batch_size
    }

# Тестируем разные размеры батча
for batch_size in [1, 8, 16, 32, 64]:
    results = asyncio.run(benchmark_batch_size(batch_size))
    print(f"Batch {batch_size}: {results['throughput']:.2f} req/s, "
          f"latency {results['avg_latency']*1000:.0f}ms")
```

## 6. Паттерны балансировки нагрузки

Когда у вас несколько реплик, нужно решить, как распределять запросы между ними.

### Паттерн 1: Круговой (Round Robin)

**Как работает:** запросы распределяются по очереди.

```
Запрос 1 → Под 1
Запрос 2 → Под 2
Запрос 3 → Под 3
Запрос 4 → Под 1
...
```

**Плюсы:** простой, предсказуемый  
**Минусы:** не учитывает текущую загрузку подов

**Проблема для LLM:**
```
Под 1: обрабатывает запрос на 2000 токенов (занят на 10 секунд)
Под 2: свободен
Под 3: свободен

Новый запрос → Под 1 (по круговому)
Результат: Под 1 перегружен, Поды 2 и 3 простаивают
```

### Паттерн 2: На основе загрузки (Load-aware)

**Как работает:** запросы идут на наименее загруженный под.

```
Запрос приходит → Смотрим на метрики всех подов:
- Под 1: очередь = 5, загрузка = 90%
- Под 2: очередь = 0, загрузка = 20%
- Под 3: очередь = 2, загрузка = 50%

Запрос → Под 2 (наименее загруженный)
```

**Реализация через K8s Service (Istio):**
```yaml
# Istio DestinationRule с балансировкой по загрузке
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: llm-server
spec:
  host: llm-server
  trafficPolicy:
    loadBalancer:
      simple: LEAST_REQUEST  # наименьшее количество активных запросов
```

### Паттерн 3: На основе очереди (Queue-based)

**Как работает:** каждый под имеет очередь запросов. Запросы распределяются на под с наименьшей очередью.

```
Новый запрос:
1. Опросить все поды: "Какая у тебя очередь?"
2. Выбрать под с минимальной очередью
3. Отправить запрос на этот под
```

**Реализация через custom load balancer:**
```python
import requests

class QueueBasedLoadBalancer:
    def __init__(self, pod_urls):
        self.pod_urls = pod_urls
    
    def get_queue_length(self, pod_url):
        try:
            response = requests.get(f"{pod_url}/metrics", timeout=1)
            # Парсим метрику из Prometheus формата
            for line in response.text.split('\n'):
                if line.startswith('llm_requests_in_queue'):
                    return float(line.split()[-1])
        except:
            return float('inf')
        return float('inf')
    
    def route_request(self, request):
        # Находим под с минимальной очередью
        best_pod = min(
            self.pod_urls,
            key=self.get_queue_length
        )
        return best_pod

lb = QueueBasedLoadBalancer([
    "http://pod-1:8000",
    "http://pod-2:8000",
    "http://pod-3:8000"
])

target_pod = lb.route_request(request)
response = requests.post(f"{target_pod}/generate", json=request)
```

### Паттерн 4: Приоритизация запросов

**Как работает:** разные типы запросов имеют разный приоритет.

```
Приоритет 1: Короткие запросы (< 100 токенов)
Приоритет 2: Средние запросы (100-500 токенов)
Приоритет 3: Длинные запросы (> 500 токенов)

Новый короткий запрос → Высокий приоритет → Обрабатывается первым
Новый длинный запрос → Низкий приоритет → Ждёт в очереди
```

**Реализация:**
```python
from priorityqueue import PriorityQueue

class PriorityRequestQueue:
    def __init__(self):
        self.queue = PriorityQueue()
    
    def add_request(self, request):
        # Определяем приоритет на основе ожидаемой длины генерации
        expected_tokens = estimate_output_length(request)
        
        if expected_tokens < 100:
            priority = 1  # высокий
        elif expected_tokens < 500:
            priority = 2  # средний
        else:
            priority = 3  # низкий
        
        self.queue.put(request, priority=priority)
    
    def get_next_request(self):
        return self.queue.get()  # возвращает запрос с наивысшим приоритетом
```

**Почему это важно:**
- Короткие запросы обрабатываются быстро → пользователи довольны
- Длинные запросы не блокируют короткие
- Общая удовлетворённость выше

## 7. Graceful Degradation

Когда нагрузка превышает возможности системы, нужно **изящно деградировать**, а не падать.

### Уровни деградации:

```
Уровень 1: Очередь заполнена → Отклонять новые запросы с 503
Уровень 2: Задержка слишком высокая → Переход на меньшую модель
Уровень 3: Память заканчивается → Выгружать старые запросы из памяти
Уровень 4: Система падает → Включать circuit breaker
```

### Пример реализации:

```python
from fastapi import FastAPI, HTTPException

app = FastAPI()

MAX_QUEUE_SIZE = 100
MAX_LATENCY_MS = 5000

@app.post("/generate")
async def generate(request: GenerateRequest):
    # Уровень 1: проверяем очередь
    if queue.size() >= MAX_QUEUE_SIZE:
        raise HTTPException(
            status_code=503,
            detail="Service overloaded, please retry later"
        )
    
    # Уровень 2: проверяем текущую задержку
    current_latency = get_current_p95_latency()
    if current_latency > MAX_LATENCY_MS:
        # Переключаемся на меньшую модель
        model = "llama-7b"  # вместо "llama-70b"
    else:
        model = "llama-70b"
    
    # Обработка запроса
    result = await process_request(request, model=model)
    return result
```

## 8. Связь с предыдущими блоками

### Связь с B.1 (Continuous batching)

Помните проблему статического батчинга?
```
Статический батч:
- Запросы 1, 2, 3 в батче
- Запрос 1 завершился за 10 токенов
- Запрос 2 завершился за 50 токенов
- Запрос 3 ещё генерирует (500 токенов)
- Батч простаивает, пока Запрос 3 не завершится
```

**В контексте масштабирования:**
- Неправильный размер батча → низкая пропускная способность
- Continuous batching решает эту проблему
- Но требует правильного размера `max_num_seqs`

### Связь с B.2 (vLLM, PagedAttention)

Помните, как PagedAttention решает проблему фрагментации памяти?
```
Без PagedAttention:
- Каждый запрос получает непрерывный блок памяти
- Память фрагментируется
- Нельзя эффективно использовать свободные блоки

С PagedAttention:
- Память разбита на страницы
- Каждая страница может использоваться любым запросом
- Максимальная утилизация памяти
```

**В контексте масштабирования:**
- Размер батча напрямую зависит от доступной памяти
- Чем эффективнее используется память (благодаря PagedAttention), тем больше батч
- Чем больше батч, тем выше пропускная способность

### Связь с C.4 (Context caching)

Помните, как можно кэшировать KV-state для повторяющихся префиксов?
```
Системный промпт: "Ты — полезный ассистент..."
Этот промпт одинаковый для всех запросов
Можно закэшировать его вычисление
```

**В контексте масштабирования:**
- Кэширование контекста снижает время обработки запроса
- Это позволяет обрабатывать больше запросов в единицу времени
- Увеличивает пропускную способность без увеличения реплик

## 9. Практические рекомендации

### Для вашего проекта (LangGraph-агент с артефактами)

**Текущий стек (предположительно):**
- Одна реплика для разработки
- Нет продакшен-нагрузки
- Используется локально или на небольшом сервере

**Что нужно для продакшена:**

**1. Определите целевые метрики:**
```
Целевая задержка: сколько секунд приемлемо для пользователя?
Целевая пропускная способность: сколько запросов в секунду?
Максимальная очередь: сколько запросов может ждать?
```

**2. Выберите размер батча:**
```
Для интерактивного агента: batch_size = 1-8
Для пакетной обработки: batch_size = 32-64
```

**3. Настройте метрики:**
```
- Длина очереди запросов
- Latency percentiles (p50, p95, p99)
- GPU memory usage
```

**4. Настройте HPA:**
```yaml
minReplicas: 1
maxReplicas: 5  # ограничьте бюджет
metrics:
- llm_requests_in_queue > 5 → scale up
- llm_request_latency_p95 > 3000ms → scale up
```

**5. Добавьте мониторинг:**
```
- Prometheus для сбора метрик
- Grafana для визуализации
- Алерты на критические значения
```

### Типичные ошибки

**Ошибка 1: Скейлинг по CPU**
```
Результат: скейлер никогда не срабатывает
Решение: использовать очередь или задержку
```

**Ошибка 2: Слишком агрессивный скейл**
```
Результат: реплики создаются и удаляются каждые 30 секунд
Решение: увеличить стабилизационное окно
```

**Ошибка 3: Недооценка холодного старта**
```
Результат: новые реплики не успевают за нагрузкой
Решение: использовать pre-warming или init containers
```

**Ошибка 4: Игнорирование длинных запросов**
```
Результат: один длинный запрос блокирует очередь
Решение: приоритизация или отдельные очереди для разных типов запросов
```

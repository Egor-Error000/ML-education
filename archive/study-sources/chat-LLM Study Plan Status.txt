Отлично, переходим к **C.2 — Structured Output / Constrained Decoding**. Это одна из самых "инженерно красивых" тем в инференсе: здесь чистая теория формальных языков встречается с практикой LLM-генерации, и это даёт гарантии, которые невозможно получить промптами.

## Проблема: почему prompting недостаточен

Когда вы просите LLM выдать JSON, SQL-запрос или функцию для tool-calling, вы сталкиваетесь с фундаментальной проблемой: **модель генерирует вероятностный текст, а не валидные структуры данных**.

Типичные сбои:
- Забытая закрывающая скобка `}` или `]`
- Лишний текст перед JSON ("Конечно, вот результат:")
- Невалидные enum-значения
- Поле не того типа (строка вместо числа)
- Пропущенное обязательное поле

Промпт-инженерия ("строго следуй формату JSON, без пояснений") работает ~90-95% времени. Для пайплайна, делающего 1000 запросов в час, это 50-100 падений. Retry'и дороги (время, деньги), парсинг с fallback'ами — хрупкий.

## Идея constrained decoding

Вместо того чтобы генерировать "что угодно" и потом валидировать/чинить, мы **принудительно ограничиваем пространство возможных токенов на каждом шаге генерации** так, чтобы любой путь через дерево токенов давал валидную строку по заданной спецификации.

Ключевая интуиция: на шаге $t$, имея уже сгенерированный префикс $s_{<t}$, мы можем точно сказать, какие токены $v \in V$ (словарь) могут быть следующими, чтобы $s_{<t} + v$ оставался **префиксом хотя бы одной валидной строки**. Всё остальное — отсекаем.

Это кардинально отличается от:
- **Post-hoc валидации** (сгенерировали → проверили → переделали если плохо)
- **Retry-loop** (повторяем пока не повезёт)
- **Fine-tuning на JSON** (модель учится форматировать, но всё равно иногда ошибается)

Здесь гарантия **100%-ная на уровне токена**: физически невозможно сгенерировать невалидный JSON, если грамматика корректна.

## Механика: как это работает внутри

### 1. Формализация ограничений

Спецификация задаётся как **формальная грамматика**. Обычно это:
- **JSON Schema** (самый популярный вариант для tool-calling)
- **Regex** (для простых структур)
- **Context-Free Grammar (CFG)** (самая выразительная форма; например, GBNF в llama.cpp)
- **Pydantic-модели** (Python-обёртки, которые компилируются в JSON Schema)

Любую из этих форм можно преобразовать в автомат — **детерминированный конечный автомат (DFA)** для регулярных языков или **pushdown-automaton (PDA)** для контекстно-свободных (JSON — это КС-язык из-за вложенных скобок).

### 2. Маскирование логитов

На каждом шаге генерации движок (vLLM, llama.cpp, TGI):

1. Делает forward pass → получает **логиты** — "сырые" оценки для всех ~50k-150k токенов в словаре.
2. Смотрит на **текущее состояние автомата** (где мы в грамматике).
3. Вычисляет множество допустимых следующих токенов $V_{valid}$.
4. Для всех $v \notin V_{valid}$ устанавливает логит в $-\infty$ (практически — очень большое отрицательное число, типа -1e10).
5. Дальше стандартный softmax + sampling (greedy, top-k, top-p) работает уже по **отфильтрованному распределению**.

```
logits[v] = -inf  для всех невалидных v
probs = softmax(logits / temperature)
next_token = sample(probs)
```

Автомат переходит в следующее состояние, и цикл повторяется.

### 3. Префикс-валидность — ключевое свойство

Здесь есть тонкость: мы отсекаем не только токены, которые ломают структуру **прямо сейчас**, но и токены, которые приведут к тупику в будущем.

Например, если спецификация требует поле `"age": integer`, и мы уже сгенерировали `"age": `, то токен `"hello"` недопустим не потому что строка `"age": "hello"` невалидна (она валидна как JSON!), а потому что она **не соответствует schema**. Автомат на уровне JSON Schema знает: после `"age":` ожидается число, не строка.

Автомат "видит будущее" в том смысле, что отслеживает, какие терминалы (токены) могут завершить текущую продукцию.

## Производительность: где узкие места

Вычисление маски на каждом шаге — это overhead. Если делать это "в лоб" (прогонять все 50k токенов через автомат), получится ~10-30% замедление генерации.

Оптимизации:
- **Lazy evaluation**: маска вычисляется не для всего словаря, а для множества уникальных "первых токенов", которые может принять автомат. Часто это сотни токенов, а не десятки тысяч.
- **Кэширование состояний**: автоматы детерминированы — одно и то же состояние даёт одну и ту же маску. Кэш "состояние → битовая маска" экономит вычисления.
- **Trie по токенам**: словарь можно представить как trie, и обходить только те ветви, которые совместимы с текущим состоянием автомата.
- **Batching-friendly**: в Continuous Batching у каждого запроса в батче свой автомат, маски вычисляются параллельно.

В vLLM и llama.cpp этот overhead обычно составляет **1-5%** от времени генерации — практически незаметно.

## Реализации в экосистеме

Разные подходы к одной и той же идее:

- **Outlines** — пионер, использует CFG и компилирует в индексированный автомат. Очень выразительный, поддерживает regex, JSON Schema, Python-функции как спецификации.
- **Guidance** (Microsoft) — синтаксис в стиле `{{gen "field" regex="[a-z]+"}}`, смешивает промпты и ограничения.
- **GBNF в llama.cpp** — собственный формат CFG, используется в Ollama/LM Studio. Минималистичный, но покрывает основные кейсы.
- **Instructor** — обёртка над Pydantic, использует constrained decoding под капотом. Самый удобный API для Python: `client.chat.completions.create(..., response_model=User)`.
- **Встроенный JSON-режим в OpenAI/Anthropic API** — гарантированный валидный JSON (но без произвольной схемы, хотя у Anthropic есть `tool_use` со строгой схемой).

## Связь с tool-calling (мост к Блоку D)

Это прямое применение C.2. Когда LLM должен вызвать функцию:

```json
{"name": "search", "arguments": {"query": "Paris weather", "limit": 10}}
```

Без constrained decoding модель может:
- Забыть `"arguments"`
- Передать `limit` как строку `"10"`
- Галлюцинировать несуществующий параметр `filter`

Со structured output: JSON Schema для параметров функции **компилируется в автомат**, и на уровне токенов модель физически не может сгенерировать неправильный вызов. Это и есть причина, почему современные tool-calling API (OpenAI, Anthropic) используют constrained decoding под капотом — без этого надёжных агентов не построить.

## Ограничения и нюансы

Важно понимать, что constrained decoding решает **форму**, но не **содержание**:
- JSON будет валидным, но значения могут быть галлюцинациями
- Enum будет валидным, но модель может выбрать не тот элемент
- Сложные семантические ограничения ("если `status` = 'error', то должно быть поле `error_message`") не всегда выражаются в JSON Schema

Ещё нюанс: **слишком жёсткие ограничения могут сломать сэмплирование**. Если на каком-то шаге модель "хочет" сказать нечто, но грамматика это запрещает, она может зациклиться или генерировать странные вещи. Особенно это проявляется с **top-p sampling**: если все валидные токены имеют маленькую вероятность, а high-probability токены отсечены, сэмплирование деградирует.

# C.3 — Стратегии сэмплирования

Мы только что видели, как constrained decoding **отсекает** токены на уровне маски логитов. Но даже после этой маски остаётся распределение вероятностей по валидным токенам — и вопрос "какой токен выбрать следующим" остаётся. Это и есть зона ответственности стратегий сэмплирования.

Это **не** просто "инженерная настройка" — стратегия сэмплирования напрямую определяет качество текста: его разнообразие, согласованность, креативность, склонность к повторам. Один и тот же промпт с разными настройками может дать принципиально разные ответы.

## Исходная точка: логиты → вероятности

На каждом шаге модель выдаёт вектор **логитов** $l \in \mathbb{R}^{|V|}$ (размер словаря, обычно 32k–150k). Это "сырые" ненормированные оценки. Стандартное преобразование — **softmax**:

$$P(v) = \frac{\exp(l_v)}{\sum_{u \in V} \exp(l_u)}$$

Все стратегии сэмплирования — это модификации этой формулы и/или правил выбора токена из полученного распределения.

## 1. Greedy decoding — детерминированный выбор

$$v_t = \arg\max_v P(v | s_{<t})$$

На каждом шаге берём токен с максимальной вероятностью. Полностью детерминированно, воспроизводимо, быстро.

**Проблема**: жадный выбор часто зацикливается и генерирует "плоские" тексты. Модель не исследует альтернативы — если на шаге 10 она выбрала слово "интересный" (p=0.31) вместо "увлекательный" (p=0.29), это решение необратимо, хотя глобально второй вариант мог бы привести к более связному продолжению.

**Когда применять**: для структурированных ответов где важна воспроизводимость (tool-calling, JSON, классификация). Часто дефолт для constrained decoding — там и так пространство сильно ограничено.

## 2. Beam search — N параллельных гипотез

Вместо одной последовательности ведём $B$ (beam width) лучших гипотез одновременно. На каждом шаге расширяем каждую гипотезу на все возможные токены, оставляем топ-$B$ по суммарной вероятности (score = $\sum \log P$).

**Плюсы**: находит более вероятные последовательности в глобальном смысле, меньше зацикливается чем greedy.

**Проблемы**:
- **Length bias**: чем длиннее последовательность, тем меньше сумма лог-вероятностей (слагаемые отрицательные), поэтому beam естественно "хочет" остановиться раньше. Приходится использовать length penalty.
- **Lack of diversity**: все $B$ гипотез часто похожи друг на друга (вариации одной идеи). Для креативных задач это плохо.
- **Вычислительная стоимость**: $B$ forward pass'ов на шаг.

**Когда применять**: machine translation, суммаризация, captioning — задачи с чётким "правильным" ответом, где нужна согласованность, а не креативность. Для открытого диалога почти не используется.

## 3. Temperature — "растягивание" распределения

$$P(v) = \frac{\exp(l_v / T)}{\sum_u \exp(l_u / T)}$$

Температура $T > 0$ масштабирует логиты **до** softmax:

- **T = 1**: исходное распределение модели
- **T → 0**: распределение стягивается к argmax (эквивалент greedy)
- **T > 1**: распределение "расплющивается", маловероятные токены получают больше шансов
- **T → ∞**: равномерное распределение по всему словарю (чистый random)

**Интуиция**: температура меняет **уверенность** модели. При низкой T модель "уверена в себе" и идёт по самому вероятному пути. При высокой T она "сомневается" и чаще пробует маловероятные варианты — это может дать креативные находки, а может и галлюцинации.

Типичные диапазоны: 0.5–0.8 для кода/структурированного вывода, 0.9–1.1 для диалога, 1.2+ для креатива.

## 4. Top-k sampling — отсечение хвоста

Оставляем только $k$ токенов с наибольшими вероятностями, обнуляем остальные и ренормируем:

$$V^{(k)} = \text{top-k токенов по } P(v)$$
$$P'(v) = \begin{cases} P(v) / Z & v \in V^{(k)} \\ 0 & \text{иначе} \end{cases}$$

Из этого усечённого распределения сэмплируем (обычно с температурой).

**Проблема top-k**: **фиксированный размер ядра**. В некоторых позициях распределение "острое" — только 3 токена разумны (например, после "2+2=" только "4" и близко к нему). В других — "плоское" — сотни токенов почти равновероятны (например, в начале нового предложения). Фиксированное k=50 в первом случае допускает откровенную бессмыслицу, а во втором — режет интересные варианты.

## 5. Top-p (nucleus) sampling — динамическое ядро

Решает проблему top-k через адаптивный размер:

$$V^{(p)} = \text{наименьшее множество, s.t. } \sum_{v \in V^{(p)}} P(v) \ge p$$

Типично $p \in [0.85, 0.95]$. Сортируем токены по убыванию вероятности, накапливаем сумму, пока не превысим $p$. Всё что сверху — наше ядро, всё что снизу — отбрасываем.

**Интуиция**: мы оставляем "достаточно вероятные" токены, и их количество естественно адаптируется к позиции. В острых позициях ядро маленькое (2–5 токенов), в плоских — большое (сотни).

**Дефолт в индустрии**: большинство API (OpenAI, Anthropic) по умолчанию используют **temperature + top-p одновременно**, например `T=1.0, p=0.95`. Они комбинируются: сначала температура растягивает/сжимает распределение, потом top-p обрезает хвост.

## Современные варианты (2024–2026)

- **Min-p**: оставляет токены с $P(v) \ge p \cdot P_{max}$. Похоже на top-p, но более интуитивно — отсекает всё, что "в N раз менее вероятно чем лучший вариант". Популярен в локальных движках (llama.cpp, LM Studio).
- **Typical sampling**: выбирает токены с энтропией, близкой к ожидаемой энтропии распределения — идея "типичных" последовательностей из теории информации.
- **Eta / Epsilon sampling**: модификации top-k с адаптивными порогами.

## Почему это часть качества, а не инфраструктуры

Параметры сэмплирования **не влияют** на то, что модель "знает" (это веса), но **сильно влияют** на то, как она это проявляет:

- Низкая температура + greedy → модель повторяет одни и те же фразы, "заезженные" паттерны, часто зацикливается
- Слишком высокая температура → галлюцинации, противоречия внутри одного ответа, синтаксические ошибки
- Неправильный top-p → либо скучные шаблонные ответы (p слишком маленький), либо "пьяный бред" (p слишком большой)

Это значит, что **одна и та же модель с разными параметрами сэмплирования — это практически разные модели с точки зрения пользователя**. Эмпирический подбор этих параметров под конкретный use case — обязательная часть разработки LLM-приложения, не "довесок".

## Взаимодействие со speculative decoding

Помнишь C.1? Там draft-модель генерирует последовательность, а большая модель её верифицирует. **Стратегия сэмплирования должна быть согласована между ними**: если обе используют temperature=0.8, top-p=0.9 с одинаковым seed, то принятые токены будут иметь точное распределение "как если бы работала только большая модель". Если стратегии расходятся — acceptance rate падает, ускорение исчезает.

## Взаимодействие с constrained decoding

Когда работает маска по грамматике (C.2), top-k и top-p применяются **после** маскирования. То есть сначала мы отсекаем токены по грамматике (ставим $-\infty$ логиты), потом оставшиеся валидные токены подвергаются температурной коррекции и top-p/top-k отбору. Это работает корректно — главное, чтобы ядро top-p не получилось пустым (тогда fallback на greedy по оставшимся).

## Практические рекомендации

| Задача | Temperature | Top-p | Top-k | Комментарий |
|---|---|---|---|---|
| Tool-calling / JSON | 0–0.2 | 0.95 | — | + constrained decoding |
| Классификация / extraction | 0 | — | — | нужен детерминированный ответ |
| Код | 0–0.3 | 0.95 | — | код плохо терпит креатив |
| Диалог / ассистент | 0.7–1.0 | 0.9 | — | стандартный баланс |
| Креатив / брейнсторм | 1.1–1.3 | 0.95 | — | больше разнообразия |
| Перевод | 0.3–0.5 | — | — | часто beam search |

## Технически ты прав — это почти бессмыслица

Greedy **всегда** берёт `argmax` — токен с максимальной вероятностью. Temperature меняет форму распределения, но **argmax обычно не меняется** (если только два токена не были очень близки по вероятности изначально).

То есть **greedy + high temperature ≈ greedy + low temperature** в большинстве случаев.

# C.4 — Техники работы с длинным контекстом

Контекст 128k–1M+ токенов — это не просто "больше текста". Это качественно другая инженерная проблема, которая ломает наивные подходы к инференсу. Разберём её по слоям — от того, почему это сложно, до конкретных техник решения.

## 1. Почему длинный контекст — это проблема (в цифрах)

Self-attention имеет сложность **O(n²)** по времени и памяти на вычисление attention scores. Это означает, что удвоение длины контекста вчетверо увеличивает вычисления. Но ещё хуже — **рост KV-cache**.

Конкретный пример для **Llama-3 70B** (80 слоёв, GQA с 8 KV-головами, head_dim=128):
- На один токен: `80 layers × 8 kv_heads × 128 dim × 2 (K+V) × 2 bytes (FP16) ≈ 640 KB`
- На 8k контекст: ~5 GB KV-cache
- На 128k контекст: **~82 GB KV-cache**
- При этом сами веса модели занимают ~140 GB (в FP16)

Получается, для длинного контекста KV-cache становится сравним по размеру с самими весами. При batch_size=10 и 128k контексте вам нужно ~800 GB только под кэш — это больше памяти, чем есть на большинстве GPU-серверов.

Вторая проблема: **latency префилла**. Обработать промпт длиной 128k токенов одним forward pass'ом требует огромного времени (секунды, а не миллисекунды), потому что нужно вычислить attention между всеми парами токенов.

## 2. Sliding Window Attention (SWA) — локальное внимание

Идея: на каждом слое каждый токен видит только **W предыдущих** токенов (обычно W=4096 или 8192), а не весь контекст.

**Как информация всё равно распространяется на весь контекст:**
Если на слое $l$ токен $i$ видит токены $[i-W, i]$, то на слое $l+1$ он видит уже "представления" токенов $[i-W, i]$, которые сами содержат информацию о своих окнах. Через $L$ слоёв "эффективный контекст" расширяется примерно до $W \times L$ токенов.

**Но это упрощение — точнее так:**
- Информация распространяется **с затуханием**. Точные детали из позиции $i - 10W$ не дойдут до позиции $i$ в неизменном виде — они будут "сжаты" через промежуточные слои.
- Модель теряет способность делать **точные retrieval** из далёких частей контекста (типа "какое третье слово в 47-м абзаце?").
- Для задач, требующих точного воспоминания (legal docs, needle-in-haystack), SWA даёт деградацию качества.
- Для задач общего понимания (суммаризация, Q&A по общему смыслу) — работает нормально.

**Примеры использования:**
- Mistral 7B: W=4096, что даёт effective context ~128k при 32 слоях
- Современные модели часто используют **смешанный подход**: часть слоёв с full attention, часть с SWA (например, каждый 4-й слой — dense, остальные — SWA)

**Разреженные паттерны внимания** — более общее семейство:
- **Dilated attention**: токены видят не подряд, а с шагом (как в WaveNet)
- **Block-sparse** (Longformer, BigBird): глобальные токены (например, [CLS]) видят всех, остальные — локально
- **LongAttention** паттерны: комбинация локального + глобального внимания

## 3. Квантизация KV-cache

Раз кэш такой большой — его можно квантовать. Это отдельная от квантизации весов задача (связка с A.6).

**Почему это работает хорошо:**
- Веса модели обучены и фиксированы — их квантизация накапливает ошибку на каждом слое.
- KV-cache вычисляется "свежим" на каждом forward pass — ошибка квантизации **не накапливается** между шагами генерации.
- Ключи и значения имеют более предсказуемое распределение, чем веса, поэтому квантуются легче.

**Типичные режимы:**
- FP16 → FP8 (на H100 с аппаратной поддержкой FP8) — минимальная потеря, 2× сжатие
- FP16 → INT8 — 2× сжатие, небольшая потеря качества
- FP16 → INT4 — 4× сжатие, заметная деградация на длинных контекстах

**Особенность:** для квантизации кэша обычно используется **per-token** или **per-head** квантизация (не per-tensor), потому что разные головы внимания имеют разные диапазоны значений.

**Практика в vLLM:** есть флаг `--kv-cache-dtype fp8` для H100/A100, что даёт почти удвоение пропускной способности на длинных контекстах без заметной потери качества.

## 4. Prompt / Context Caching у API-провайдеров

Это техника **на уровне сервиса**, а не модели. Идея: если префикс промпта одинаковый между запросами, не пересчитывать его KV-cache.

**Как это работает:**
1. Вы отправляете первый запрос с длинным системным промптом (например, 10k токенов инструкций + 50k токенов документации).
2. Провайдер (Anthropic, OpenAI, Google) вычисляет KV-cache для этого префикса и сохраняет его в памяти сервера (обычно на несколько часов).
3. Последующие запросы с **тем же побайтно префиксом** пропускают этап префилла для этой части — сразу используют сохранённый KV-state.

**Экономия:**
- Anthropic Prompt Caching: **до 90% дешевле** и **до 85% ниже latency** на префилл
- OpenAI: ~50% дешевле на кэшированные токены
- Google Context Caching: похоже на Anthropic

**Требования (важно!):**
- Префикс должен быть **длинным** (обычно ≥1024 токенов у Anthropic, ≥1024 у OpenAI)
- Префикс должен быть **побайтно идентичным** — даже пробел в начале ломает кэш
- Кэш живёт ограниченное время (5 минут — 1 час, в зависимости от провайдера)

**Типичные use cases:**
- Длинный system prompt для агента
- Один и тот же документ как контекст для множества вопросов (RAG-style, но без векторной БД)
- Few-shot примеры, которые одинаковы для всех запросов

**Отличие от semantic caching (Блок E.3):**
- Prompt caching: кэш **вычислений модели**, работает на уровне идентичных префиксов, детерминированно
- Semantic caching: кэш **готовых ответов**, работает на уровне семантически близких запросов (через эмбеддинги), вероятностный

## 5. Алгоритмические оптимизации attention

### FlashAttention (1, 2, 3)
Это **не** изменение асимптотики — всё ещё O(n²) по вычислениям. Но это **радикальное** улучшение по константе и паттерну доступа к памяти.

**Суть:**
- Стандартный attention: вычисляет полную N×N матрицу attention scores, сохраняет её в HBM (GPU memory), потом читает обратно для softmax и умножения на V
- FlashAttention: разбивает последовательность на тайлы (chunks), вычисляет attention для тайла **целиком в SRAM** (внутричиповая память, в 100× быстрее HBM), не сохраняет промежуточную N×N матрицу

**Результат:** в 2–4× ускорение и **линейный** рост памяти по длине контекста (вместо квадратичного), потому что мы не храним N×N матрицу.

**Важный нюанс:** FlashAttention требует аккуратной реализации с учётом численной стабильности softmax (online softmax algorithm). Не просто "сделали тайлы".

### Multi-Query Attention (MQA) и Grouped-Query Attention (GQA)
Это **архитектурные** решения на уровне модели (упоминались в A.6).

- **MHA (Multi-Head Attention)**: каждая query-голова имеет свои K и V. Размер KV-cache = num_heads × head_dim
- **MQA**: одна общая K и V для всех query-голов. Размер KV-cache уменьшается в num_heads раз (обычно 32× или 64×)
- **GQA**: компромисс — groups из G query-голов делят одну K/V. Обычно G=8, что даёт 4–8× сжатие при почти неизменном качестве

**Все современные LLM** (Llama-2/3, Qwen, Mistral) используют GQA — это де-факто стандарт.

### Ring Attention
Для контекстов, которые не помещаются на один GPU (1M+ токенов):
- Контекст разбивается между несколькими GPU
- Каждый GPU вычисляет attention для своего сегмента, обмениваясь K/V с соседями по кольцу
- Даёт почти линейное масштабирование по длине контекста при добавлении GPU

Используется в инфраструктурных решениях для контекстов >1M токенов.

## 6. Позиционные эмбеддинги для длинных контекстов

Это скрытая, но критическая проблема. Transformer не понимает порядка токенов без positional encoding.

**RoPE (Rotary Position Embedding)** — де-факто стандарт современных LLM:
- К query и key применяется вращение в комплексной плоскости, зависящее от позиции токена
- Красивое свойство: relative position encoding "бесплатно" через скалярное произведение

**Проблема масштабирования:**
Модель обучена на контексте длины $L_{train}$ (например, 8k). Если мы хотим инференс на $L_{infer} = 4 \times L_{train}$ (32k), то позиции в диапазоне [8k, 32k] — это **незнакомые** позиционные эмбеддинги, которые модель никогда не видела при обучении. Качество резко падает.

**Решения (length extrapolation):**
- **Position Interpolation (PI)**: "сжать" позиции при инференсе: $p' = p \times L_{train} / L_{infer}$. Все позиции попадают в знакомый диапазон, но модель теряет "разрешение" — близкие позиции становятся трудноразличимы.
- **YaRN (Yet another RoPE extensioN)**: умное масштабирование, которое по-разному интерполирует разные частоты — низкие частоты (отвечающие за далёкие позиции) растягиваются, высокие (локальные) остаются нетронутыми.
- **NTK-aware scaling / Dynamic NTK**: похожая идея — нелинейное масштабирование base частоты RoPE.

**Практика:** модели, обученные на 8k, обычно можно без дообучения расширить до 32k с YaRN/NTK, и с небольшим LoRA-дообучением — до 128k. Дальше — уже нужно полноценное continued pretraining.

## 7. Альтернативные архитектуры (кратко)

Для очень длинных контекстов (1M+) O(n²) attention становится непреодолимым барьером, поэтому появились альтернативы:

- **State Space Models (SSM)** — Mamba, Samba: линейная O(n) сложность через рекуррентное обновление скрытого состояния. Недостаток: "сжатие" всей истории в фиксированный hidden state, что может терять детали.
- **RWKV** — гибрид RNN и Transformer с линейной сложностью.
- **Гибриды** — Jamba (Mistral): часть слоёв Mamba, часть attention. Получают O(n) для большинства слоёв + O(n²) для небольшого числа слоёв, сохраняя качество.

Это пока не мейнстрим, но для контекстов >1M токенов это может стать стандартом.

## 8. Практический чек-лист для длинного контекста

Если вам нужно работать с контекстами >32k токенов в проде:

| Размер контекста | Основные техники |
|---|---|
| 8k–32k | GQA + FlashAttention + prompt caching — обычно достаточно |
| 32k–128k | + квантизация KV-cache в FP8/INT8 + SWA на части слоёв + YaRN/NTK для RoPE |
| 128k–1M | + Ring Attention (много-GPU) или переход на гибридные SSM/attention архитектуры |
| >1M | SSM-подобные архитектуры (Mamba, Jamba) или специализированные решения |

**Типичные ошибки при работе с длинным контекстом:**
1. **Lost in the middle**: модели лучше всего "помнят" начало и конец контекста, середину — плохо (эмпирический результат из Liu et al. 2023). Это фундаментальное свойство attention, а не баг.
2. **Забыть про префилл latency**: первый запрос с длинным промптом может обрабатываться 5–30 секунд — это нужно учитывать в UX.
3. **Думать, что модель "видит" весь контекст одинаково**: SWA + RoPE-экстраполяция + lost-in-the-middle означают, что "длинный контекст" — это не равно "модель читает весь текст как человек".

## Что можно углубить

- Математика RoPE и почему именно rotation работает для relative position encoding
- Детали FlashAttention 2 vs 3 (H100-specific оптимизации)
- Почему Mamba проигрывает Transformer на "recall" задачах, но выигрывает на streaming
- Конкретные бенчмарки: needle-in-haystack, RULER, LongBench — как мерить качество на длинных контекстах

## Сценарий: AI-ассистент по технической документации

Допустим, у нас проект: **внутренний AI-ассистент для разработчиков**, который отвечает на вопросы по внутренней документации компании. Это типичный use case, где prompt caching даёт максимальную выгоду.

### Структура промпта

```
[SYSTEM PROMPT] — ~8,000 токенов
  - Инструкции как себя вести
  - Правила безопасности  
  - Формат ответов
  - Описание компании

[CONTEXT DOCUMENTS] — ~15,000 токенов  
  - Архитектура микросервисов компании
  - API-документация
  - Внутренние гайды
  - Troubleshooting docs

[USER QUERY] — ~100-500 токенов
  - Конкретный вопрос разработчика
```

**Итого на запрос:** ~23,500 токенов input + output

Без кэша: каждый запрос обрабатывает все 23,500 токенов с нуля.
С кэшем: префикс (23,000 токенов) кэшируется, вычисляется только user query.

---

## Реализация: Anthropic Claude API

Anthropic — самый зрелый по prompt caching. Рассмотрим на нём.

### Шаг 1: Первый запрос (кэш создаётся)

```python

ПРАВИЛА:
1. Отвечай только на основе предоставленной документации
2. Если не уверен — скажи "не нашёл в документации"
3. Цитируй конкретные разделы с номерами
4. Используй markdown для форматирования кода

[здесь ещё 7500 токенов детальных инструкций...]
"""

DOCUMENTATION = """# Архитектура TechCorp

## Микросервисы
- user-service (Go, port 8080)
- order-service (Java, port 8081)  
- payment-service (Rust, port 8082)

## Общие паттерны
- Все сервисы используют gRPC для inter-service communication
- Circuit breaker через Envoy sidecar
- Distributed tracing через Jaeger

[здесь ещё 14500 токенов документации...]
"""

# Первый запрос

    model="claude-sonnet-4-20250514",
    max_tokens=1024,
    system=[
        {
            "type": "text",
            "text": SYSTEM_PROMPT,
            "cache_control": {"type": "ephemeral"}  # ← КЛЮЧЕВОЙ ФЛАГ
        }
    ],
    messages=[
        {
            "role": "user",
            "content": [
                {
                    "type": "text",
                    "text": DOCUMENTATION,
                    "cache_control": {"type": "ephemeral"}  # ← кэшируем документы
                },
                {
                    "type": "text", 
                    "text": "Как устроен circuit breaker между сервисами? Приведи пример кода."
                }
            ]
        }
    ]
)
elapsed_1 = time.time() - start

# Смотрим метрики кэша в ответе
usage = response.usage
print(f"Запрос 1:")
print(f"  Время: {elapsed_1:.2f}s")
print(f"  Cache creation tokens: {usage.cache_creation_input_tokens}")  # ~23000
print(f"  Cache read tokens: {usage.cache_read_input_tokens}")            # 0
print(f"  Non-cached input tokens: {usage.input_tokens}")               # ~500
print(f"  Output tokens: {usage.output_tokens}")
```

## Критические требования (без этого кэш не сработает)

### 1. Побайтовое совпадение префикса

```python
# ❌ НЕ РАБОТАЕТ — пробел в начале
SYSTEM_PROMPT_1 = "Ты ассистент..."
SYSTEM_PROMPT_2 = " Ты ассистент..."  # лишний пробел — кэш ломается

# ❌ НЕ РАБОТАЕТ — разный порядок блоков
# Запрос 1: system + docs + query
# Запрос 2: docs + system + query

# ✓ РАБОТАЕТ — идентичные строки
SYSTEM_PROMPT_1 = SYSTEM_PROMPT_2 = "Ты ассистент..."
```

### 2. Минимальная длина кэшируемого блока

| Провайдер | Минимум токенов |
|---|---|
| Anthropic Claude | 1024 (Haiku), 2048 (Sonnet/Opus) |
| OpenAI GPT | 1024 |
| Google Gemini | 32768 |

Если ваш system prompt короче — кэш не создастся, даже если поставить `cache_control`.

### 3. TTL (time-to-live) кэша

- **Anthropic**: ~5 минут по умолчанию, автоматически продлевается при каждом попадании
- **OpenAI**: 5-10 минут без продления
- **Google**: до 1 часа (но дороже)

Если между запросами проходит больше TTL — кэш протухает и создаётся заново.

## Практический паттерн: пул долгоживущих сессий

В реальном приложении не создают новый клиент на каждый запрос. Обычно:

```python
class CachedAssistant:
    def __init__(self, system_prompt: str, docs: str):
        self.system_prompt = system_prompt
        self.docs = docs
        self.client = anthropic.Anthropic()
        # Прекомпьютируем хэши для мониторинга
        self.prefix_hash = hash(system_prompt + docs)
    
    def ask(self, question: str) -> str:
        response = self.client.messages.create(
            model="claude-sonnet-4-20250514",
            max_tokens=1024,
            system=[{
                "type": "text",
                "text": self.system_prompt,
                "cache_control": {"type": "ephemeral"}
            }],
            messages=[{
                "role": "user",
                "content": [
                    {
                        "type": "text",
                        "text": self.docs,
                        "cache_control": {"type": "ephemeral"}
                    },
                    {"type": "text", "text": question}
                ]
            }]
        )
        
        # Мониторинг: логируем, попадает ли в кэш
        if response.usage.cache_read_input_tokens > 0:
            logger.info("Cache HIT")
        else:
            logger.warning("Cache MISS — создан новый кэш")
        
        return response.content[0].text

# Использование
assistant = CachedAssistant(SYSTEM_PROMPT, DOCUMENTATION)

# Первый запрос — cache miss
assistant.ask("Как устроен circuit breaker?")

# Второй — cache hit
assistant.ask("Какие порты у payment-service?")

# Через 10 минут — cache miss (протух)
assistant.ask("Где хранить секреты?")
```

## Когда кэш НЕ работает

### Сценарий 1: Персонализация на уровне пользователя
```python
# ❌ У каждого юзера свой system prompt
system_prompt = f"Ты помогаешь пользователю {user_name}..."
# → кэш создаётся для КАЖДОГО пользователя отдельно
# → при 1000 пользователей — 1000 кэшей, которые быстро протухают
```

**Решение**: вынести персонализацию в конец, после общего префикса.

### Сценарий 2: Динамический RAG с разными документами
```python
# ❌ Каждый запрос подтягивает свой набор документов
docs = retrieve_top_k_docs(query)  # разные для каждого query
# → префикс разный → кэш не работает
```

**Решение**: кэшировать только system prompt (если он длинный), а документы — нет. Или использовать один "master document set" для всех запросов.

### Сценарий 3: Слишком короткие промпты
```python
# ❌ System prompt всего 200 токенов
system_prompt = "Ты helpful assistant."
# → не проходит порог 1024/2048 токенов
# → кэш не создаётся
```

**Решение**: либо не использовать кэш, либо искусственно "раздуть" system prompt до нужного размера (например, подробными инструкциями).

## Сравнение с обычным RAG без кэша

Допустим, у нас 1000 запросов в день от разработчиков:

**Без кэша:**
- Input tokens: 1000 × 23,500 = 23.5M токенов/день
- Стоимость input: 23.5M × $3.00/MTok = $70.50/день
- Latency: ~8s на запрос
- **Итого: ~$2100/месяц**

**С кэшем** (при условии 90% hit rate, обновления документации раз в день):
- Cache creation: ~3 × 23k × $3.75/MTok = $0.26/день (3 холодных старта)
- Cache read: 1000 × 23k × $0.30/MTok = $6.90/день
- Non-cached: 1000 × 500 × $3.00/MTok = $1.50/день
- **Итого: ~$260/месяц** (в 8× дешевле!)
- **Latency: ~2s на запрос** (в 4× быстрее)

## Как это выглядит в OpenAI API (для сравнения)

OpenAI добавил prompt caching позже (2024), и он работает **автоматически** — не нужно явно указывать `cache_control`:

```python
from openai import OpenAI
client = OpenAI()

# Первый запрос — кэш создаётся автоматически
response1 = client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {"role": "system", "content": SYSTEM_PROMPT},  # >1024 токенов
        {"role": "user", "content": DOCUMENTATION + "\n\nВопрос: ..."}
    ]
)

# Второй запрос — кэш используется автоматически
response2 = client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {"role": "system", "content": SYSTEM_PROMPT},  # ТОТ ЖЕ текст
        {"role": "user", "content": DOCUMENTATION + "\n\nВопрос: ..."}
    ]
)

# В response2.usage будет:
# - prompt_tokens_details.cached_tokens = 23000
# - prompt_tokens_details.cached_tokens стоимость: 50% от обычной
```

**Отличия от Anthropic:**
- ✓ Автоматический (не нужен `cache_control`)
- ✓ Дешевле на 50% (не 90% как у Anthropic)
- ✗ Менее предсказуемо (нельзя явно контролировать)
- ✗ Меньше метрик в ответе

## Резюме для вашего проекта

Prompt caching работает **отлично**, если у вас:
1. **Длинный стабильный префикс** (system prompt + документы >2k токенов)
2. **Много похожих запросов** к этому префиксу
3. **Запросы идут часто** (чтобы кэш не протухал)

Это идеальный паттерн для:
- AI-ассистентов с длинными инструкциями
- RAG с фиксированным набором документов
- Чат-ботов с длинным system prompt
- Multi-turn диалогов, где начало разговора кэшируется

Это **плохо работает** для:
- Персонализированных промптов
- Динамического RAG с разными документами
- Коротких промптов (<1024 токенов)
- Разовых запросов

## Фундаментальная проблема: один вызов LLM — это не приложение

Когда вы впервые знакомитесь с LLM, всё кажется простым:

```python
response = client.messages.create(
    model="claude-sonnet-4-20250514",
    messages=[{"role": "user", "content": "Какая погода в Москве?"}]
)
print(response.content[0].text)
# "Я не могу предоставить актуальную информацию о погоде..."
```

**Модель галлюцинирует или отказывается отвечать**, потому что:
1. У неё нет доступа к реальному миру (API погоды)
2. Она не помнит предыдущие разговоры
3. Она не может проверить свои ответы
4. Она не может выполнить сложные многошаговые задачи

Это не баг модели — это **архитектурное ограничение** LLM как функции `text → text`. Реальные приложения требуют больше.

## Пять "дыр" одиночного вызова

### 1. Отсутствие памяти (statelessness)

```python
# Запрос 1
user: "Меня зовут Алексей"
llm: "Приятно познакомиться, Алексей!"

# Запрос 2 (через 5 минут)
user: "Как меня зовут?"
llm: "Я не знаю вашего имени."  # ← модель не помнит!
```

Каждый вызов LLM — это **чистая функция**: `f(prompt) → response`. Нет внутреннего состояния между вызовами.

**Что нужно:** механизм сохранения истории разговора и передачи её в следующий промпт.

### 2. Отсутствие доступа к инструментам (tooling)

```python
user: "Посчитай интеграл sin(x) от 0 до π"
llm: "Интеграл sin(x) от 0 до π равен... 2? Или 1? Я не уверен."

# Нужен Python-интерпретатор!
```

LLM не может:
- Выполнять код
- Делать запросы к БД
- Звонить в API
- Читать файлы
- Искать в интернете

**Что нужно:** механизм, где модель решает "мне нужен инструмент", вызывает его, получает результат, продолжает генерацию.

### 3. Отсутствие проверки и коррекции (no verification)

```python
user: "Сколько будет 247 × 891?"
llm: "247 × 891 = 219,577"

# Правильный ответ: 220,077
# Модель ошиблась, но не может проверить себя
```

**Что нужно:** цикл "сгенерировал → проверил → исправил если надо" (agentic loop).

### 4. Отсутствие сложной логики (no control flow)

```python
user: "Найди все коммиты за последнюю неделю, где были изменения в auth-модуле, и создай отчёт"

# Нужна логика:
# 1. Вызвать git log с фильтрами
# 2. Для каждого коммита проверить diff
# 3. Отфильтровать только auth-связанные
# 4. Сгенерировать markdown-отчёт
# 5. Если отчёт слишком длинный — суммаризировать
```

**Что нужно:** граф состояний с условными перехода, циклами, ветвлениями.

### 5. Отсутствие обработки ошибок (no error handling)

```python
# API вернул ошибку
response = client.messages.create(...)
# NetworkError: Connection timeout

# Или модель вернула невалидный JSON для tool-calling
# JSONDecodeError: Expecting ',' delimiter
```

**Что нужно:** retry-логика, fallback-стратегии, graceful degradation.

## Эволюция: от промпта к оркестрации

### Уровень 0: Raw API call (что мы только что видели)

```python
response = client.messages.create(messages=[...])
```

**Плюсы:** просто, прозрачно
**Минусы:** все 5 проблем выше

### Уровень 1: Wrapper функции (ручная оркестрация)

```python
class ChatBot:
    def __init__(self):
        self.history = []
    
    def ask(self, question: str) -> str:
        # Добавляем вопрос в историю
        self.history.append({"role": "user", "content": question})
        
        # Формируем промпт с историей
        messages = [
            {"role": "system", "content": "Ты helpful assistant."},
            *self.history
        ]
        
        # Вызываем API
        response = client.messages.create(messages=messages)
        answer = response.content[0].text
        
        # Сохраняем ответ в историю
        self.history.append({"role": "assistant", "content": answer})
        
        return answer

bot = ChatBot()
bot.ask("Меня зовут Алексей")
bot.ask("Как меня зовут?")  # Теперь работает!
```

**Плюсы:** решает проблему памяти
**Минусы:** всё ещё нет инструментов, проверки, сложной логики

### Уровень 2: Tool-calling (добавляем доступ к миру)

```python
import json
import subprocess

def execute_python(code: str) -> str:
    """Выполняет Python-код и возвращает результат"""
    result = subprocess.run(
        ["python", "-c", code],
        capture_output=True,
        text=True
    )
    return result.stdout or result.stderr

def search_web(query: str) -> str:
    """Ищет в интернете"""
    # Вызов API поиска (например, Tavily, Bing)
    return search_api.query(query)

# Определяем инструменты для модели
tools = [
    {
        "name": "execute_python",
        "description": "Выполняет Python-код",
        "parameters": {
            "type": "object",
            "properties": {
                "code": {"type": "string"}
            },
            "required": ["code"]
        }
    },
    {
        "name": "search_web",
        "description": "Ищет в интернете",
        "parameters": {
            "type": "object",
            "properties": {
                "query": {"type": "string"}
            },
            "required": ["query"]
        }
    }
]

class ToolUsingBot:
    def __init__(self):
        self.history = []
        self.tools = {"execute_python": execute_python, "search_web": search_web}
    
    def ask(self, question: str) -> str:
        self.history.append({"role": "user", "content": question})
        
        while True:
            response = client.messages.create(
                messages=self.history,
                tools=tools
            )
            
            # Проверяем, хочет ли модель вызвать инструмент
            if response.stop_reason == "tool_use":
                tool_use = response.content[0]
                tool_name = tool_use.name
                tool_input = tool_use.input
                
                # Выполняем инструмент
                result = self.tools[tool_name](**tool_input)
                
                # Добавляем результат в историю
                self.history.append({
                    "role": "user",
                    "content": [
                        {
                            "type": "tool_result",
                            "tool_use_id": tool_use.id,
                            "content": result
                        }
                    ]
                })
            else:
                # Модель дала финальный ответ
                answer = response.content[0].text
                self.history.append({"role": "assistant", "content": answer})
                return answer

bot = ToolUsingBot()
bot.ask("Посчитай интеграл sin(x) от 0 до π")
# → модель вызывает execute_python("import scipy.integrate; print(scipy.integrate.quad(np.sin, 0, np.pi))")
# → получает результат "2.0"
# → отвечает "Интеграл равен 2.0"
```

**Плюсы:** модель может использовать инструменты
**Минусы:** линейная логика (один инструмент за раз), нет сложных workflow

### Уровень 3: Chain / Pipeline (последовательные шаги)

```python
class ResearchPipeline:
    def __init__(self):
        self.bot = ToolUsingBot()
    
    def research(self, topic: str) -> str:
        # Шаг 1: Найти ключевые вопросы
        questions = self.bot.ask(
            f"Сгенерируй 5 ключевых вопросов по теме '{topic}'"
        )
        
        # Шаг 2: Для каждого вопроса найти информацию
        findings = []
        for q in questions.split("\n"):
            if q.strip():
                info = self.bot.ask(f"Найди ответ на вопрос: {q}")
                findings.append(info)
        
        # Шаг 3: Синтезировать отчёт
        report = self.bot.ask(
            f"На основе следующих находок:\n{chr(10).join(findings)}\n\n"
            f"Создай структурированный отчёт по теме '{topic}'"
        )
        
        return report

pipeline = ResearchPipeline()
report = pipeline.research("Трансформеры в NLP")
```

**Плюсы:** многошаговые задачи
**Минусы:** жёсткая последовательность, нет условной логики, нет циклов

### Уровень 4: Agent / Graph (сложная логика с циклами и ветвлениями)

Вот здесь начинается **настоящая оркестрация**. Пример псевдокода:

```python
class DataAnalysisAgent:
    def __init__(self):
        self.tools = {
            "load_data": load_data,
            "run_analysis": run_analysis,
            "visualize": visualize,
            "interpret": interpret
        }
    
    def analyze(self, dataset_path: str, question: str) -> str:
        state = {
            "dataset": None,
            "analyses": [],
            "visualizations": [],
            "iteration": 0,
            "max_iterations": 5
        }
        
        while state["iteration"] < state["max_iterations"]:
            # Модель решает, что делать дальше
            decision = self.plan_next_step(state, question)
            
            if decision.action == "load_data":
                state["dataset"] = self.tools["load_data"](dataset_path)
            
            elif decision.action == "run_analysis":
                result = self.tools["run_analysis"](
                    state["dataset"],
                    decision.analysis_type
                )
                state["analyses"].append(result)
                
                # Проверяем, достаточно ли информации
                if self.is_sufficient(state["analyses"], question):
                    break  # Выходим из цикла
            
            elif decision.action == "visualize":
                viz = self.tools["visualize"](
                    state["dataset"],
                    decision.viz_type
                )
                state["visualizations"].append(viz)
            
            state["iteration"] += 1
        
        # Финальная интерпретация
        return self.tools["interpret"](
            state["analyses"],
            state["visualizations"],
            question
        )
```

**Плюсы:** полная гибкость, циклы, условная логика, самокоррекция
**Минусы:** сложно отлаживать, сложно тестировать

## Зачем это всё нужно (практическая мотивация)

### Для вашего проекта (LangGraph-агент)

Ваш проект — это **аналитический агент**, который:
1. Загружает данные
2. Выполняет различные анализы
3. Строит визуализации
4. Интерпретирует результаты
5. **Итеративно уточняет** анализ на основе промежуточных результатов

Это **невозможно** сделать одним вызовом LLM. Нужен граф состояний с:
- Узлами для каждого типа операции
- Рёбрами для условных переходов ("если p-value < 0.05, то...")
- Циклами для итеративного уточнения
- Состоянием, которое передаётся между узлами

### Типичные production-сценарии

**1. Customer Support Bot:**
```
User Query → Classify Intent → 
  if "billing": BillingAgent (with DB access)
  if "technical": TechnicalAgent (with knowledge base)
  if "complaint": EscalationAgent (human handoff)
```

**2. Code Review Agent:**
```
PR Diff → 
  Run Linters → 
  Check Security → 
  Generate Review Comments →
  if "critical issues found": Request Changes
  else: Approve
```

**3. Research Assistant:**
```
Research Question →
  Search Literature →
  Extract Key Findings →
  Identify Gaps →
  Propose Experiments →
  while not satisfied:
    Refine Search
    Update Findings
```

## Что даёт оркестрация (резюме)

| Проблема | Решение через оркестрацию |
|---|---|
| Нет памяти | State management между вызовами |
| Нет инструментов | Tool-calling framework |
| Нет проверки | Cycles with verification steps |
| Нет сложной логики | Graph-based workflows |
| Нет обработки ошибок | Retry logic, fallback strategies |
| Нет наблюдаемости | Logging, tracing каждого шага |
| Нет тестируемости | Unit tests для каждого узла графа |

Всё вышеописанное можно написать **с нуля** на чистом Python (как в примерах). Но это:

Они абстрагируют типичные паттерны и дают готовые кирпичики.

## LangChain как паттерн, а не библиотека

LangChain часто воспринимают как конкретную Python-библиотеку (`pip install langchain`), но на уровне идеи это **набор паттернов для композиции LLM-вызовов с другими компонентами**. Эти паттерны можно реализовать на любом языке и в любом фреймворке — LangChain просто дал им имена и стандартизированные абстракции.

Если D.1 объяснял **зачем** нужна оркестрация, то D.2 — это **стандартный словарь кирпичиков**, из которых строятся пайплайны.

## Четыре базовых абстракции

### 1. Prompt Templates — параметризация промптов

Вместо склеивания строк:

```python
# Плохо: ручная интерполяция, хрупко
prompt = f"Переведи на {lang}: {text}"
```

Используем template с явной схемой переменных:

```python
from langchain_core.prompts import ChatPromptTemplate

template = ChatPromptTemplate.from_messages([
    ("system", "Ты переводчик на {language}."),
    ("user", "{text}")
])

# Явная валидация: если забыть передать переменную — ошибка на этапе создания
prompt = template.invoke({"language": "французский", "text": "Привет мир"})
# → [("system", "Ты переводчик на французский."), ("user", "Привет мир")]
```

**Зачем это нужно:**
- Валидация обязательных переменных на этапе создания, а не в рантайме
- Переиспользование шаблонов между частями приложения
- Версионирование промптов как артефактов (можно хранить в YAML/JSON)
- A/B-тестирование: легко подменить шаблон без изменения кода

**Output Parsers** — обратная сторона: парсинг ответа модели в структурированный объект.

```python
from langchain_core.output_parsers import JsonOutputParser
from pydantic import BaseModel

class Translation(BaseModel):
    original: str
    translated: str
    confidence: float

parser = JsonOutputParser(pydantic_object=Translation)

# Под капотом это использует constrained decoding (C.2)!
# Parser инжектит инструкции в prompt + валидирует результат
```

### 2. Models и Chat Models — абстракция над API

Единый интерфейс для разных провайдеров:

```python
from langchain_openai import ChatOpenAI
from langchain_anthropic import ChatAnthropic
from langchain_community.llms import Ollama

# Один и тот же интерфейс для всех
llm_openai = ChatOpenAI(model="gpt-4o")
llm_claude = ChatAnthropic(model="claude-sonnet-4-20250514")
llm_local = Ollama(model="llama3")

# Swap провайдера — одна строка кода
response = llm_claude.invoke(messages)
```

**Ценность:** провайдер-agnostic код. Особенно полезно для:
- Локальной разработки (Ollama/llama.cpp) с продакшн-переключением на облачный API
- A/B-тестов между моделями
- Fallback-логики: если один провайдер упал — переключаемся на другой

### 3. Chains (LCEL) — композиция компонентов

Это **сердце** LangChain. Идея: компоненты можно соединять через оператор `|` (pipe), как Unix pipelines.

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI

prompt = ChatPromptTemplate.from_template("Объясни {concept} простыми словами")
model = ChatOpenAI(model="gpt-4o")
output_parser = StrOutputParser()

# Chain = prompt → model → parser
chain = prompt | model | output_parser

# Вызов
result = chain.invoke({"concept": "квантовая запутанность"})
```

**LCEL (LangChain Expression Language)** — это современный способ композиции (с 2023 года), пришедший на замену старым классам `LLMChain`, `SequentialChain`.

**Почему pipe-оператор, а не классы:**
- Читается линейно слева направо
- Автоматически поддерживает batch, async, streaming
- Встроенная поддержка retries и fallbacks
- Лучшая интеграция с observability (LangSmith)

```python
# Batch-обработка из коробки
results = chain.batch([
    {"concept": "нейросети"},
    {"concept": "квантизация"},
    {"concept": "attention"}
])

# Streaming
for chunk in chain.stream({"concept": "трансформеры"}):
    print(chunk, end="", flush=True)
```

### 4. Tools и Tool-calling

Интеграция инструментов в цепочки:

```python
from langchain_core.tools import tool

@tool
def search_web(query: str) -> str:
    """Ищет актуальную информацию в интернете"""
    # Реальная реализация через Tavily/Bing
    return search_api.query(query)

@tool
def calculate(expression: str) -> str:
    """Вычисляет математическое выражение"""
    return str(eval(expression))

# Модель с инструментами
llm_with_tools = ChatOpenAI(model="gpt-4o").bind_tools([search_web, calculate])

# Модель сама решает, вызывать ли инструмент
response = llm_with_tools.invoke("Какая погода в Москве сегодня и сколько это в Фаренгейтах?")
# → tool_calls: [{"name": "search_web", ...}, {"name": "calculate", ...}]
```

## Memory — решение проблемы statelessness

Это одна из самых важных (и самых неправильно используемых) частей LangChain.

### Базовая проблема

LLM — чистая функция `f(prompt) → response`. Чтобы модель "помнила" контекст разговора, нужно **явно передавать историю** в каждый следующий промпт. Memory автоматизирует это.

### Типы памяти (по компромиссу качество/стоимость)

#### 1. Buffer Memory — хранение всей истории

```python
from langchain.memory import ConversationBufferMemory

memory = ConversationBufferMemory()
memory.save_context({"input": "Меня зовут Алексей"}, {"output": "Привет, Алексей!"})
memory.save_context({"input": "Я из Москвы"}, {"output": "Замечательно!"})

# При следующем вызове вся история добавляется в промпт
messages = memory.load_memory_variables({})
# → {"history": "Human: Меня зовут Алексей\nAI: Привет, Алексей!\nHuman: Я из Москвы\nAI: Замечательно!"}
```

**Проблема:** история растёт бесконечно → промпт превышает контекстное окно → ошибка или дорогие запросы.

#### 2. Buffer Window Memory — последние K сообщений

```python
from langchain.memory import ConversationBufferWindowMemory

memory = ConversationBufferWindowMemory(k=10)  # только последние 10 реплик
```

**Компромисс:** ограниченный размер, но модель "забывает" старое.

#### 3. Summary Memory — сжатие истории

```python
from langchain.memory import ConversationSummaryMemory

memory = ConversationSummaryMemory(llm=ChatOpenAI())
# При каждом новом сообщении запускается LLM, который суммаризирует историю
# Вместо 1000 сообщений хранится одна суммаризация
```

**Компромисс:** дешевле по токенам, но:
- Теряются детали (имена, конкретные факты могут "раствориться")
- Дополнительные LLM-вызовы на каждое сообщение (дорого!)
- Риск галлюцинаций в самой суммаризации

#### 4. Hybrid: Summary + Buffer

```python
from langchain.memory import ConversationSummaryBufferMemory

memory = ConversationSummaryBufferMemory(
    llm=ChatOpenAI(),
    max_token_limit=2000  # пока история <2000 токенов — храним всё, потом сжимаем
)
```

**Практический дефолт** для большинства приложений.

### Критика LangChain Memory

Честно говоря, memory в LangChain — **самая критикуемая часть** фреймворка:

1. **Неявная магия**: легко не понять, что именно передаётся в промпт
2. **Сложная отладка**: когда история становится большой, трудно отследить, что именно модель "видит"
3. **Ограниченная гибкость**: для сложных сценариев (персистентность, multi-user, branching conversations) встроенные memory-классы не подходят

**Production-реальность:** большинство серьёзных приложений пишут свою memory-логику поверх Postgres/Redis, а не используют встроенные LangChain memory. LangChain memory хороша для прототипов.

## Retrievers и RAG-примитивы

LangChain предоставляет абстракции для retrieval (детальнее в D.5):

```python
from langchain_openai import OpenAIEmbeddings
from langchain_community.vectorstores import FAISS

# Создание индекса
embeddings = OpenAIEmbeddings()
vectorstore = FAISS.from_documents(documents, embeddings)
retriever = vectorstore.as_retriever(search_kwargs={"k": 5})

# Использование в chain
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnablePassthrough

prompt = ChatPromptTemplate.from_template("""
Ответь на вопрос, используя контекст:
{context}

Вопрос: {question}
""")

def format_docs(docs):
    return "\n\n".join(doc.page_content for doc in docs)

rag_chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | llm
    | StrOutputParser()
)

answer = rag_chain.invoke("Какая архитектура у микросервисов?")
```

## Где LangChain хорош, а где нет

### ✅ Где LangChain оправдан

1. **Быстрое прототипирование** — за час можно собрать работающий RAG-пайплайн
2. **Стандартизация** — команда использует единые абстракции, код читаем
3. **Интеграции** — готовые коннекторы к 100+ провайдерам, vector stores, инструментам
4. **LCEL для линейных пайплайнов** — элегантная композиция для ETL-style задач

### ❌ Где LangChain становится проблемой

1. **Сложная ветвящаяся логика** — chains линейны, трудно выразить условные переходы
2. **Циклы и итерации** — нет нативной поддержки agentic loops
3. **Сложный state management** — передавать состояние между шагами через chains неуклюже
4. **Отладка** — цепочки из 10+ компонентов трудно дебажить, особенно при ошибках
5. **Over-abstraction** — для простых случаев обёртки добавляют сложности без пользы

### Пример проблемы с линейностью

Допустим, вы хотите реализовать паттерн "попробуй ответь, если не уверен — поищи, потом ответь снова":

```python
# На чистом Python — просто и понятно
def answer_with_fallback(question):
    answer = llm.invoke(question)
    if not is_confident(answer):
        context = retriever.invoke(question)
        answer = llm.invoke(f"{context}\n\n{question}")
    return answer

# На LangChain chains — неуклюже, через кастомные Runnable
class ConfidenceCheck(Runnable):
    def invoke(self, input):
        if not is_confident(input):
            # нужно как-то "вернуться" и вызвать retriever...
            # LangChain chains не поддерживают это элегантно
            ...
```

Это и есть **мотивация для LangGraph** (D.3) — переход от линейных цепочек к графам состояний, где:
- Узлы — это функции/компоненты
- Рёбра — условные переходы
- Состояние передаётся явно между узлами
- Циклы — нативная часть модели

## Эволюция экосистемы LangChain (важно знать!)

LangChain сильно изменился в 2023-2024. Если читаете старые туториалы — будьте осторожны:

**Было (до 2023):**
- Один большой пакет `langchain`
- Классы `LLMChain`, `SequentialChain`, `AgentExecutor`
- Много "магии" под капотом

**Стало (2024+):**
- Разбит на отдельные пакеты: `langchain-core`, `langchain-openai`, `langchain-community` и т.д.
- **LCEL** вместо старых классов chains
- `AgentExecutor` **deprecated** в пользу LangGraph
- Фокус на **LangGraph** для агентов, **LangChain** для RAG-примитивов и интеграций

**Практический совет:** если начинаете новый проект в 2026 году:
- Используйте `langchain-core` для базовых абстракций (prompts, parsers)
- Используйте `langgraph` для любой агентной/ветвящейся логики
- Избегайте старых `AgentExecutor`, `LLMChain` — они устарели

## Альтернативы LangChain

Стоит знать, что LangChain — не единственный вариант:

- **Чистый Python + API-клиенты** — для простых случаев это проще и прозрачнее
- **LlamaIndex** — специализация на RAG и data frameworks, меньше "магии"
- **DSPy** — принципиально другой подход: "компиляция" промптов вместо их ручного написания
- **Mirascope** — лёгкая альтернатива с фокусом на type safety
- **PydanticAI** — от создателей Pydantic, минималистичный и type-safe

## Итог: когда использовать LangChain

| Сценарий | Рекомендация |
|---|---|
| Простой RAG-пайплайн | ✅ LangChain + FAISS/Chroma |
| Линейный ETL через LLM | ✅ LCEL chains |
| Агенты с tool-calling | ❌ Старый LangChain, ✅ LangGraph |
| Сложные multi-step workflow | ❌ LangChain, ✅ LangGraph |
| Простой чат-бот | ⚠️ Избыточно, хватит чистого Python |
| Production с observability | ✅ LangChain + LangSmith |

## Почему LangChain chains недостаточно

В D.2 мы видели, что LangChain chains (LCEL) отлично работают для **линейных** пайплайнов: `prompt → model → parser`. Но реальные агентные задачи редко линейны. Они требуют:

- **Условных переходов**: "если модель уверена → верни ответ, если нет → вызови инструмент"
- **Циклов**: "вызывай инструменты, пока не получишь достаточно информации"
- **Ветвлений**: "в зависимости от типа запроса, иди по разным путям"
- **Явного state**: "сохраняй промежуточные результаты между шагами"
- **Self-correction**: "если шаг провалился, попробуй ещё раз с другой стратегией"

Chains этого не умеют элегантно. LangGraph решает эту проблему через **StateGraph** — граф, где узлы — функции, рёбра — условные переходы, а состояние передаётся явно между узлами.

## Базовая концепция: StateGraph

```python
from langgraph.graph import StateGraph, START, END
from typing import TypedDict

# 1. Определяем структуру состояния (типизированно!)
class AgentState(TypedDict):
    messages: list          # история разговора
    tool_results: dict      # результаты вызовов инструментов
    iteration: int          # счётчик итераций
    final_answer: str       # финальный ответ

# 2. Определяем узлы — функции, которые модифицируют состояние
def call_model(state: AgentState) -> dict:
    """Узел: вызов LLM для принятия решения"""
    messages = state["messages"]
    response = llm.invoke(messages)
    
    # Возвращаем только изменения состояния (delta update)
    return {"messages": messages + [response]}

def execute_tool(state: AgentState) -> dict:
    """Узел: выполнение вызванного инструмента"""
    last_message = state["messages"][-1]
    tool_call = last_message.tool_calls[0]
    
    # Выполняем инструмент
    result = tools[tool_call["name"]](**tool_call["args"])
    
    tool_message = ToolMessage(content=result, tool_call_id=tool_call["id"])
    return {
        "messages": state["messages"] + [tool_message],
        "tool_results": {**state["tool_results"], tool_call["name"]: result}
    }

# 3. Определяем условные переходы
def should_continue(state: AgentState) -> str:
    """Решаем, куда идти дальше"""
    last_message = state["messages"][-1]
    
    # Если модель вызвала инструмент — идём в execute_tool
    if hasattr(last_message, "tool_calls") and last_message.tool_calls:
        return "execute_tool"
    
    # Иначе — завершаем
    return "end"

# 4. Строим граф
graph = StateGraph(AgentState)

# Добавляем узлы
graph.add_node("call_model", call_model)
graph.add_node("execute_tool", execute_tool)

# Добавляем рёбра
graph.add_edge(START, "call_model")                    # Старт → call_model
graph.add_conditional_edges("call_model", should_continue)  # Условный переход
graph.add_edge("execute_tool", "call_model")           # Цикл: execute_tool → call_model
graph.add_edge("end", END)                             # Завершение

# Компилируем
app = graph.compile()
```

**Что здесь происходит:**

```
START → call_model ──(есть tool_call?)──→ execute_tool
              ↓ нет                           ↓
            END                        (возврат к call_model)
```

Это **агентный цикл**: модель думает → вызывает инструмент → получает результат → думает снова → повторяет, пока не даст финальный ответ.

## Ключевые отличия от chains

| Аспект | LangChain Chains | LangGraph |
|---|---|---|
| **Структура** | Линейная последовательность | Граф с ветвлениями и циклами |
| **Состояние** | Неявное (через memory) | Явное (TypedDict, передаётся между узлами) |
| **Условные переходы** | Громоздко (кастомные Runnable) | Нативно (conditional edges) |
| **Циклы** | Практически невозможно | Первая-class citizen |
| **Отладка** | Сложно (много абстракций) | Легко (каждый узел — отдельная функция) |
| **Визуализация** | Нет встроенной | `app.get_graph().draw_mermaid()` |

## State management: как передаются данные

Одна из самых мощных фич LangGraph — **явное типизированное состояние**.

### Почему это важно

В chains состояние передаётся неявно через memory или через возвращаемые значения. Это приводит к:
- Неожиданным побочным эффектам
- Сложности отладки ("откуда взялась эта переменная?")
- Трудности тестирования (нужно мокать весь контекст)

В LangGraph состояние — это **TypedDict** с явной схемой:

```python
class AgentState(TypedDict):
    messages: list[BaseMessage]
    tool_results: dict[str, Any]
    iteration: int
    final_answer: str
    dataset_path: str  # путь к данным для анализа
```

Каждый узел:
1. **Получает** текущее состояние как аргумент
2. **Возвращает** только изменения (delta update)
3. LangGraph **автоматически мержит** изменения в состояние

```python
def analyze_data(state: AgentState) -> dict:
    # Читаем из состояния
    dataset = load_data(state["dataset_path"])
    
    # Выполняем анализ
    results = perform_analysis(dataset)
    
    # Возвращаем только то, что изменилось
    return {
        "tool_results": {**state["tool_results"], "analysis": results},
        "iteration": state["iteration"] + 1
    }
```

**Преимущества:**
- Type safety (mypy проверяет схему)
- Predictable updates (нет неожиданных мутаций)
- Easy testing (можно передать моковое состояние)
- Debugging (можно инспектировать состояние на каждом шаге)

## Циклы: agentic loops

Циклы — это **killer feature** LangGraph. Они позволяют реализовать паттерны, невозможные в chains:

### Паттерн 1: Tool-calling loop

```python
def should_continue(state: AgentState) -> str:
    last_message = state["messages"][-1]
    
    # Если есть tool_call — продолжаем цикл
    if last_message.tool_calls:
        return "execute_tool"
    
    # Иначе завершаем
    return "end"

graph.add_conditional_edges("call_model", should_continue)
graph.add_edge("execute_tool", "call_model")  # ← цикл!
```

Модель может вызывать инструменты **столько раз, сколько нужно**, пока не решит, что у неё достаточно информации для финального ответа.

### Паттерн 2: Self-correction loop

```python
def validate_answer(state: AgentState) -> dict:
    """Проверяем качество ответа"""
    answer = state["messages"][-1].content
    
    # Проверяем, есть ли ссылки на источники
    has_citations = check_citations(answer)
    
    # Проверяем, отвечает ли на вопрос
    answers_question = check_relevance(answer, state["original_question"])
    
    return {
        "validation_passed": has_citations and answers_question,
        "validation_errors": [] if (has_citations and answers_question) else ["missing citations"]
    }

def should_retry(state: AgentState) -> str:
    if state["validation_passed"]:
        return "end"
    
    # Если не прошло валидацию и не превысили лимит попыток — повторяем
    if state["iteration"] < 3:
        return "retry"
    
    return "end"

graph.add_node("validate", validate_answer)
graph.add_conditional_edges("validate", should_retry)
graph.add_edge("retry", "call_model")  # ← цикл для самокоррекции
```

### Паттерн 3: Multi-step workflow с циклами

```python
class ResearchState(TypedDict):
    query: str
    sources: list[str]
    findings: list[str]
    iteration: int
    max_iterations: int

def search_sources(state: ResearchState) -> dict:
    """Ищем источники"""
    new_sources = search_web(state["query"])
    return {"sources": state["sources"] + new_sources}

def extract_findings(state: ResearchState) -> dict:
    """Извлекаем находки из источников"""
    new_findings = []
    for source in state["sources"]:
        finding = llm.invoke(f"Извлеки ключевые факты из: {source}")
        new_findings.append(finding)
    return {"findings": state["findings"] + new_findings}

def check_sufficiency(state: ResearchState) -> str:
    """Достаточно ли информации?"""
    if len(state["findings"]) >= 5:
        return "synthesize"
    
    if state["iteration"] >= state["max_iterations"]:
        return "synthesize"  # вынуждены завершить
    
    return "search_more"

def refine_query(state: ResearchState) -> dict:
    """Уточняем запрос для следующего раунда поиска"""
    refined = llm.invoke(f"Уточни запрос '{state['query']}' на основе: {state['findings']}")
    return {
        "query": refined,
        "iteration": state["iteration"] + 1
    }

# Граф с циклом
graph = StateGraph(ResearchState)
graph.add_node("search", search_sources)
graph.add_node("extract", extract_findings)
graph.add_node("refine", refine_query)
graph.add_node("synthesize", synthesize_findings)

graph.add_edge(START, "search")
graph.add_edge("search", "extract")
graph.add_conditional_edges("extract", check_sufficiency)
graph.add_edge("search_more", "refine")
graph.add_edge("refine", "search")  # ← цикл!
graph.add_edge("synthesize", END)
```

## Практический пример: аналитический агент (ваш кейс)

Вот как может выглядеть агент для вашего проекта (анализ данных с tool-calling):

```python
from langgraph.graph import StateGraph, START, END
from typing import TypedDict, Annotated
from langgraph.graph.message import add_messages
import operator

class DataAnalysisState(TypedDict):
    messages: Annotated[list, add_messages]  # автоматически мерджит сообщения
    dataset_path: str
    analysis_results: Annotated[dict, operator.or_]  # мерджит словари
    visualizations: list
    iteration: int
    question: str

# Определяем инструменты
@tool
def load_dataset(path: str) -> str:
    """Загружает датасет и возвращает описание"""
    df = pd.read_csv(path)
    return f"Загружен датасет: {df.shape[0]} строк, {df.shape[1]} колонок. Колонки: {list(df.columns)}"

@tool
def run_statistical_test(dataset_path: str, test_type: str, columns: list) -> str:
    """Выполняет статистический тест"""
    df = pd.read_csv(dataset_path)
    
    if test_type == "t_test":
        from scipy import stats
        stat, p_value = stats.ttest_ind(df[columns[0]], df[columns[1]])
        return f"T-test: statistic={stat:.4f}, p-value={p_value:.4f}"
    
    elif test_type == "correlation":
        corr = df[columns].corr()
        return f"Correlation matrix:\n{corr.to_string()}"

@tool
def create_visualization(dataset_path: str, viz_type: str, columns: list) -> str:
    """Создаёт визуализацию и сохраняет в файл"""
    df = pd.read_csv(dataset_path)
    
    if viz_type == "scatter":
        plt.scatter(df[columns[0]], df[columns[1]])
    
    elif viz_type == "histogram":
        plt.hist(df[columns[0]], bins=30)
    
    filename = f"viz_{len(state['visualizations'])}.png"
    plt.savefig(filename)
    plt.close()
    
    return f"Визуализация сохранена: {filename}"

# Узлы графа
def analyze(state: DataAnalysisState) -> dict:
    """LLM решает, какой анализ выполнить"""
    tools = [load_dataset, run_statistical_test, create_visualization]
    llm_with_tools = ChatOpenAI(model="gpt-4o").bind_tools(tools)
    
    response = llm_with_tools.invoke(state["messages"])
    return {"messages": [response]}

def execute_tool(state: DataAnalysisState) -> dict:
    """Выполняет вызванный инструмент"""
    last_message = state["messages"][-1]
    tool_call = last_message.tool_calls[0]
    
    tools_dict = {
        "load_dataset": load_dataset,
        "run_statistical_test": run_statistical_test,
        "create_visualization": create_visualization
    }
    
    result = tools_dict[tool_call["name"]].invoke(tool_call["args"])
    tool_message = ToolMessage(content=result, tool_call_id=tool_call["id"])
    
    return {
        "messages": [tool_message],
        "analysis_results": {tool_call["name"]: result}
    }

def check_completion(state: DataAnalysisState) -> str:
    """Проверяем, достаточно ли анализа"""
    last_message = state["messages"][-1]
    
    # Если последний message — от инструмента, продолжаем
    if isinstance(last_message, ToolMessage):
        return "continue"
    
    # Если модель дала финальный ответ, проверяем качество
    if hasattr(last_message, "content") and last_message.content:
        # Простая эвристика: если ответ содержит "результаты" или "выводы"
        if any(keyword in last_message.content.lower() for keyword in ["результат", "вывод", "итог"]):
            return "end"
    
    return "continue"

# Строим граф
graph = StateGraph(DataAnalysisState)

graph.add_node("analyze", analyze)
graph.add_node("execute_tool", execute_tool)

graph.add_edge(START, "analyze")
graph.add_conditional_edges("analyze", check_completion, {
    "continue": "execute_tool",
    "end": END
})
graph.add_edge("execute_tool", "analyze")  # цикл

app = graph.compile()

# Запуск
result = app.invoke({
    "messages": [HumanMessage(content="Проанализируй связь между возрастом и доходом в датасете")],
    "dataset_path": "data.csv",
    "analysis_results": {},
    "visualizations": [],
    "iteration": 0,
    "question": "Проанализируй связь между возрастом и доходом"
})

print(result["messages"][-1].content)
```

## Продвинутые возможности

### 1. Checkpointer (персистентность состояния)

LangGraph может сохранять состояние между запусками — полезно для long-running agents:

```python
from langgraph.checkpoint.memory import MemorySaver

checkpointer = MemorySaver()
app = graph.compile(checkpointer=checkpointer)

# Первый запуск
result1 = app.invoke(
    {"messages": [HumanMessage(content="Привет")]},
    config={"configurable": {"thread_id": "user-123"}}
)

# Второй запуск с тем же thread_id — состояние сохраняется!
result2 = app.invoke(
    {"messages": [HumanMessage(content="Как меня зовут?")]},
    config={"configurable": {"thread_id": "user-123"}}
)
```

Для production используйте `SqliteSaver` или `PostgresSaver` вместо `MemorySaver`.

### 2. Human-in-the-loop

Можно добавить узлы, где агент останавливается и ждёт подтверждения человека:

```python
from langgraph.types import interrupt

def sensitive_action(state: AgentState) -> dict:
    """Действие, требующее подтверждения"""
    action = state["proposed_action"]
    
    # Останавливаем граф и ждём подтверждения
    human_response = interrupt({
        "question": f"Выполнить действие: {action}?",
        "options": ["yes", "no"]
    })
    
    if human_response == "yes":
        return execute_action(action)
    else:
        return {"status": "cancelled"}

# При компиляции указываем checkpointer
app = graph.compile(checkpointer=checkpointer, interrupt_before=["sensitive_action"])

# Запуск
result = app.invoke(initial_state, config={"configurable": {"thread_id": "session-1"}})

# Граф остановился перед sensitive_action
# Человек подтверждает:
app.invoke(Command(resume="yes"), config={"configurable": {"thread_id": "session-1"}})
```

### 3. Subgraphs (вложенные графы)

Сложные агенты можно разбивать на подграфы:

```python
# Подграф для анализа данных
analysis_graph = StateGraph(AnalysisState)
# ... определение узлов и рёбер ...
analysis_app = analysis_graph.compile()

# Основной граф использует подграф как узел
main_graph = StateGraph(MainState)
main_graph.add_node("analyze_data", analysis_app)  # ← подграф как узел!
# ... остальные узлы ...
```

## Как это ложится на ваш проект

Ваш аналитический агент — это **идеальный кейс для LangGraph**:

1. **Tool-calling к готовым артефактам**: эмбеддинги, кластеры, ablation-таблица — это инструменты, которые агент вызывает
2. **Итеративный анализ**: агент может запускать несколько раундов анализа, уточняя гипотезы
3. **Self-correction**: если статистический тест не показал значимости, агент может попробовать другой тест
4. **Визуализация**: создание графиков — это отдельные инструменты
5. **Синтез результатов**: финальный узел, который собирает все результаты в отчёт

**Типичная структура вашего агента:**

```
START → understand_question
  ↓
plan_analysis (LLM решает, какие анализы нужны)
  ↓
execute_analyses (цикл: load_data → run_test → visualize → repeat)
  ↓
check_sufficiency (достаточно ли результатов?)
  ↓ нет → уточнить план и повторить
  ↓ да
synthesize_report (LLM пишет финальный отчёт)
  ↓
END
```

## Сравнение с другими подходами

| Подход | Когда использовать | Ограничения |
|---|---|---|
| **LangChain chains** | Линейные ETL-пайплайны | Нет циклов, сложная условная логика |
| **LangGraph** | Агенты, сложные workflow, циклы | Более сложный learning curve |
| **Чистый Python** | Простые случаи, полный контроль | Много boilerplate, нет готовых примитивов |
| **AutoGen** | Multi-agent conversation | Overhead для single-agent задач |
| **CrewAI** | Role-based агенты | Менее гибкий для custom workflow |

## Практические советы

1. **Всегда типизируйте состояние** через `TypedDict` — это спасает от багов
2. **Используйте `Annotated` для сложных мерджей** (например, `add_messages` для списков сообщений)
3. **Логируйте состояние на каждом шаге** — критично для отладки
4. **Используйте `app.get_graph().draw_mermaid()`** для визуализации графа
5. **Тестируйте узлы изолированно** — каждый узел это просто функция, её легко unit-тестить
6. **Не бойтесь вложенных графов** — это помогает управлять сложностью

## Что можно углубить

- Детали `Annotated` и custom reducers для состояния
- Streaming в LangGraph (как получать промежуточные результаты)
- Integration с LangSmith для observability
- Production patterns: error handling, retries, timeouts
- Сравнение с другими graph-based фреймворками (Prefect, Temporal)

## Архитектурное разделение: что есть что

Первое и самое важное понимание — **уровни ответственности**:

```
Уровень D (оркестрация):  агенты, циклы, инструменты, state
                          LangGraph / LangChain / свой код
                                    ↓ вызывает
Уровень B (serving):      подача запросов к модели
                          Ollama / LM Studio / vLLM / llama.cpp
                                    ↓ грузит
Уровень A (модель):       веса, квантизация, архитектура
                          GGUF-файлы моделей
```

**Ollama и LM Studio — это движки инференса уровня B.** Они не реализуют агентов, циклы и инструменты сами. Они только:
1. Загружают модель в память
2. Принимают запросы (обычно через HTTP API)
3. Генерируют ответ

Всё агентное строится **поверх** них в отдельном слое оркестрации. Это та же схема, что с Anthropic/OpenAI API, только "провайдер" — ваш локальный сервер.

## Что умеет Ollama из коробки

### Базовый API

Ollama поднимает HTTP-сервер на `localhost:11434` со следующими эндпоинтами:

```
POST /api/chat          # чат-формат (главный для агентов)
POST /api/generate      # простой completion
POST /api/embed         # эмбеддинги
GET  /api/tags          # список установленных моделей
```

Плюс **OpenAI-совместимый** эндпоинт:
```
POST /v1/chat/completions
```

Это ключевой момент — о нём ниже.

### Поддержка tool-calling в самом API

Начиная с версии 0.3.9 (сентябрь 2024), Ollama поддерживает параметр `tools` в `/api/chat`:

```python
import requests

response = requests.post(
    "http://localhost:11434/api/chat",
    json={
        "model": "qwen2.5:14b",
        "messages": [
            {"role": "user", "content": "Какая температура в Москве?"}
        ],
        "tools": [
            {
                "type": "function",
                "function": {
                    "name": "get_weather",
                    "description": "Получает текущую погоду для города",
                    "parameters": {
                        "type": "object",
                        "properties": {
                            "city": {
                                "type": "string",
                                "description": "Название города"
                            }
                        },
                        "required": ["city"]
                    }
                }
            }
        ],
        "stream": False
    }
)

result = response.json()

# Модель вернёт message с tool_calls, если решит вызвать инструмент
print(result["message"])
# {
#   "role": "assistant",
#   "content": "",
#   "tool_calls": [
#     {
#       "function": {
#         "name": "get_weather",
#         "arguments": {"city": "Москва"}
#       }
#     }
#   ]
# }
```

**Ollama сам форматирует запрос под конкретную модель** — каждая модель имеет свой внутренний формат вызова инструментов (у Llama 3.1 один, у Qwen 2.5 другой, у Mistral третий). Ollama читает шаблон модели и конвертирует JSON-описание инструмента в правильный формат. Это важно: без этого вам пришлось бы вручную прописывать формат под каждую модель.

### Параметр `format` — базовый constrained decoding

```python
response = requests.post(
    "http://localhost:11434/api/generate",
    json={
        "model": "qwen2.5:14b",
        "prompt": "Извлеки имя и возраст: 'Алексею 35 лет'",
        "format": "json"  # ← принудительный JSON-режим
    }
)
```

Или более продвинуто — со схемой:

```python
"format": {
    "type": "object",
    "properties": {
        "name": {"type": "string"},
        "age": {"type": "integer"}
    },
    "required": ["name", "age"]
}
```

Это **прямая реализация того, что мы разбирали в C.2** — constrained decoding через грамматику. Под капотом Ollama использует механизмы из llama.cpp для маскирования невалидных токенов.

### Шаг 2: определение инструментов

```python
import pandas as pd
import numpy as np
from pathlib import Path
from langchain_core.tools import tool

ARTIFACTS_DIR = Path("artifacts")

@tool
def load_embeddings(artifact_name: str) -> str:
    """Загружает сохранённые эмбеддинги и возвращает их описание.
    
    Args:
        artifact_name: имя артефакта, например 'user_embeddings_v2'
    """
    path = ARTIFACTS_DIR / f"{artifact_name}.npy"
    if not path.exists():
        return f"Ошибка: артефакт {artifact_name} не найден"
    
    embeddings = np.load(path)
    return (
        f"Загружены эмбеддинги: {embeddings.shape[0]} объектов, "
        f"размерность {embeddings.shape[1]}. "
        f"Нормы: min={np.linalg.norm(embeddings, axis=1).min():.3f}, "
        f"max={np.linalg.norm(embeddings, axis=1).max():.3f}"
    )

@tool
def describe_clusters(artifact_name: str) -> str:
    """Возвращает описание сохранённых кластеров."""
    path = ARTIFACTS_DIR / f"{artifact_name}_clusters.csv"
    if not path.exists():
        return f"Ошибка: кластеры {artifact_name} не найдены"
    
    df = pd.read_csv(path)
    summary = df.groupby("cluster").agg({
        "size": "count",
        "avg_distance_to_centroid": "mean"
    })
    return f"Кластеры:\n{summary.to_string()}"

@tool
def get_ablation_row(metric_name: str) -> str:
    """Возвращает строку из ablation-таблицы для указанной метрики."""
    df = pd.read_csv(ARTIFACTS_DIR / "ablation_results.csv")
    row = df[df["metric"] == metric_name]
    if row.empty:
        return f"Метрика {metric_name} не найдена в таблице"
    return row.to_markdown(index=False)
```

### Шаг 3: граф агента

```python
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode
from langchain_ollama import ChatOllama
from langchain_core.messages import HumanMessage

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
    iteration: int

tools = [load_embeddings, describe_clusters, get_ablation_row]

# Локальная модель с привязанными инструментами
llm = ChatOllama(
    model="qwen2.5:14b",
    temperature=0.1,      # для агентов — низкая температура
    num_ctx=32768,        # расширенный контекст
)
llm_with_tools = llm.bind_tools(tools)

def agent_node(state: AgentState) -> dict:
    """Модель принимает решение"""
    system = (
        "Ты аналитик данных. У тебя есть доступ к готовым артефактам: "
        "эмбеддинги, кластеры, ablation-таблица. Используй инструменты, "
        "чтобы ответить на вопрос. Не выдумывай данные — только из артефактов."
    )
    messages = [{"role": "system", "content": system}] + state["messages"]
    response = llm_with_tools.invoke(messages)
    return {
        "messages": [response],
        "iteration": state["iteration"] + 1
    }

def should_continue(state: AgentState) -> str:
    last = state["messages"][-1]
    
    # Защита от бесконечного цикла (критично для локальных моделей!)
    if state["iteration"] >= 8:
        return "end"
    
    if hasattr(last, "tool_calls") and last.tool_calls:
        return "tools"
    return "end"

# Строим граф
graph = StateGraph(AgentState)
graph.add_node("agent", agent_node)
graph.add_node("tools", ToolNode(tools))

graph.add_edge(START, "agent")
graph.add_conditional_edges("agent", should_continue, {
    "tools": "tools",
    "end": END
})
graph.add_edge("tools", "agent")  # ← цикл

app = graph.compile()

# Запуск
result = app.invoke({
    "messages": [HumanMessage(
        content="Сравни качество кластеризации по метрике silhouette "
                "для вариантов с 5 и 10 кластерами"
    )],
    "iteration": 0
})

print(result["messages"][-1].content)
```

Этот код **полностью идентичен** тому, что вы написали бы для Anthropic API, кроме строки инициализации LLM. Цикл `agent → tools → agent` работает точно так же, как в D.3.

## Специфичные проблемы локальных моделей для агентов

Здесь начинается честная реальность. Локальные модели (7B–32B) **слабее** облачных флагманов в агентных задачах, и это проявляется конкретно:

### Проблема 1: ломается формат вызова инструментов

Облачные модели почти всегда выдают валидный `tool_calls`. Локальные модели (особенно 7–8B) иногда:
- Выдают аргументы как строку вместо объекта
- Выдумывают несуществующие инструменты
- Забывают вызвать инструмент и отвечают "в текстовом виде"
- Нарушают типы параметров

**Решения:**
1. **Constrained decoding** через `format="json"` (базовый уровень)
2. **Модели, специально обученные под tool-calling**: 
   - `qwen2.5-coder`, `qwen3` — очень хороший function-calling
   - `llama3.1` / `llama3.3` — надёжный базовый
   - `hermes3` — специально заточен под агентные сценарии
   - `firefunction-v2`, `llama3-groq-tool-use` — tool-calling модели
3. **Парсинг с fallback**: если `tool_calls` пуст, но текст похож на вызов — парсить вручную

### Проблема 2: короткие контексты по умолчанию

По умолчанию большинство моделей в Ollama работают с `num_ctx=2048` или `4096`. Для агента с несколькими итерациями инструментов это **мгновенно переполняется**.

```python
# Всегда явно задавайте контекст
llm = ChatOllama(model="qwen2.5:14b", num_ctx=32768)
```

Помните из блока C.4: чем длиннее контекст, тем больше KV-cache. Для 14B модели с 32k контекста в квантованном виде это может занять 20–30 ГБ. На железе с 16 ГБ придётся либо ужимать контекст, либо брать модель меньше.

### Проблема 3: скорость итераций

Агент с 5 итерациями инструментов = минимум 5 генераций + префилл каждой. На локальном железе:
- 14B модель на RTX 4090: ~30–50 токенов/сек → каждая итерация ~3–10 секунд
- Итого полный прогон агента: 30–60 секунд

Это **нормально для разработки**, но не для интерактивного продакшена.

**Практический совет:** для локальных агентов используйте модели 7–14B. 70B локально = минуты на итерацию, агенты становятся неюзабельными.

## Грамматики и продвинутый constrained decoding

Если вам нужна **гарантированная** структура вывода (как в C.2), у локального инференса есть преимущество перед облачными API: **полный контроль над грамматиками**.

### В llama.cpp напрямую (через LM Studio или бинарник)

Формат **GBNF** (Grammar Based Normal Form):

```bnf
root ::= object
object ::= "{" ws pair (ws "," ws pair)* ws "}"
pair ::= "\"name\"" ws ":" ws string
       | "\"age\""  ws ":" ws number
string ::= "\"" [a-zA-Zа-яА-Я0-9 ]+ "\""
number ::= [0-9]+
ws ::= " "?
```

Эта грамматика **физически не даст** модели сгенерировать ничего, кроме объекта с полями `name` и `age`.

В LM Studio есть поддержка грамматик в настройках сервера. В llama.cpp CLI:

```bash
llama-cli -m model.gguf -p "Извлеки данные: Алексею 35 лет" --grammar-file extract.gbnf
```

### В Ollama через параметр `format`

Как показано выше — JSON Schema в параметре `format`. Это покрывает 95% случаев для агентов, сложные грамматики нужны редко.

## Сравнение: когда что использовать

| Сценарий | Рекомендация |
|---|---|
| Прототипирование агента, приватность критична | Ollama + Qwen 2.5 14B |
| Максимальный контроль (грамматики, параметры) | llama.cpp напрямую или LM Studio |
| Слабое железо (8–16 ГБ) | Qwen 2.5 7B в Q4 + минимум инструментов |
| Разработка без интернета | Любая локальная схема |
| Продакшн с высокими требованиями к качеству | Облачные API (Claude/GPT), локальные — только для чувствительных данных |
| Гибрид: чувствительное локально, сложное в облаке | Маршрутизация в графе: узел выбирает модель по типу задачи |

---

## Практический чек-лист для локального агента

1. **Выбор модели**: минимум 7B, лучше 13–14B; обязательно instruction-tuned с поддержкой tool-calling (Qwen 2.5+, Llama 3.1+, Hermes 3)
2. **Контекст**: явно задать `num_ctx ≥ 16384`, проверить что влезает в память
3. **Температура**: 0–0.3 для надёжности вызова инструментов
4. **Лимит итераций**: всегда ставить `max_iterations` в графе — локальные модели чаще зацикливаются
5. **Валидация вызовов**: проверять, что модель вызвала существующий инструмент с валидными параметрами; при ошибке — возвращать ей текст ошибки для исправления (паттерн из C.2 + self-correction из D.3)
6. **Логирование**: выводить каждый шаг графа — локальные модели делают странные вещи, без логов не разобраться
7. **Формат вывода**: где возможно, использовать `format="json"` или грамматики

# D.4 — Tool / Function Calling: механика

## Фундаментальная идея: модель сама решает, когда и что вызвать

До tool-calling взаимодействие с LLM было строго **текст → текст**. Модель генерировала слова, и если ей нужно было "что-то сделать", она просто описывала это словами:

```
User: Какая погода в Москве?
Model: Я не имею доступа к данным о погоде в реальном времени. 
       Вы можете проверить на weather.com...
```

С tool-calling модель получает **способность решать**: "сейчас мне нужно вызвать внешний инструмент, чтобы ответить". Это превращает LLM из генератора текста в **контроллер**, который оркестрирует вызовы внешних функций.

```
User: Какая погода в Москве?
Model: [решает вызвать get_weather]
       → tool_call: get_weather(city="Москва")
System: [выполняет, возвращает результат]
       → "В Москве +15°C, пасмурно"
Model: В Москве сейчас +15°C, пасмурно.
```

Ключевой вопрос: **как модель этому научилась?**

---

## Два подхода: prompt engineering vs fine-tuning

### Подход 1: Prompt Engineering (старый, хрупкий)

Ранние реализации tool-calling (2022–2023) работали через **инструкции в промпте**:

```python
system_prompt = """
Ты helpful assistant. Когда тебе нужно вызвать функцию, 
выведи её в формате:

FUNCTION_CALL: function_name(arg1=value1, arg2=value2)

Доступные функции:
- get_weather(city: str) - получает погоду
- calculate(expression: str) - вычисляет выражение

Если вызов не нужен, отвечай обычным текстом.
"""

user_input = "Какая погода в Москве?"
full_prompt = system_prompt + "\nUser: " + user_input + "\nAssistant:"

response = llm.invoke(full_prompt)
# Модель генерирует: "FUNCTION_CALL: get_weather(city='Москва')"

# Дальше парсим строку вручную
if response.startswith("FUNCTION_CALL:"):
    # хрупкий парсинг строки...
    function_name, args = parse_function_call(response)
```

**Проблемы этого подхода:**

1. **Ненадёжность формата**: модель может вывести:
   - `FUNCTION_CALL: get_weather("Москва")` (без имени аргумента)
   - `function_call: get_weather(city=Москва)` (без кавычек)
   - `I need to call get_weather(city="Москва")` (с лишним текстом)
   - Просто текстовый ответ вместо вызова

2. **Нет гарантий валидности**: модель может вызвать несуществующую функцию, передать неправильные типы аргументов, забыть обязательные параметры.

3. **Хрупкий парсинг**: нужен regex или эвристики для извлечения вызова из текста.

4. **Неэффективно**: модель тратит токены на "FUNCTION_CALL:" и форматирование вместо сути.

### Подход 2: Function-Calling Fine-Tuning (современный стандарт)

Современные модели (GPT-3.5/4, Claude 3, Llama 3.1, Qwen 2.5, Mistral) **специально дообучены** на task tool-calling. Это не prompt engineering — это **отдельный head модели**, обученный предсказывать структурированные вызовы.

**Как это работает:**

1. **Специальные токены**: в словаре модели добавлены специальные токены:
   - `<|tool_call|>` — начало вызова
   - `<|tool_sep|>` — разделитель
   - `<|tool_end|>` — конец вызова
   
2. **Обучение на парах**: модель обучается на датасетах вида:
   ```
   Input: "Какая погода в Москве?" + [описание инструментов]
   Target: <|tool_call|>get_weather{"city": "Москва"}<|tool_end|>
   ```

3. **Два режима генерации**:
   - **Обычный режим**: модель генерирует текст как обычно
   - **Tool-calling режим**: модель генерирует структурированный JSON вызова
   
   Модель **учится переключаться** между этими режимами в зависимости от контекста.

4. **Отдельный head для tool-calling**: у модели есть два "выхода":
   - **Text head**: предсказывает следующий токен текста
   - **Tool head**: предсказывает вызов инструмента (имя + аргументы)
   
   На каждом шаге модель решает: "генерировать текст или вызвать инструмент?"

**Преимущества:**

- **Надёжность**: модель выдает строго форматированный JSON
- **Валидность**: модель обучена вызывать только существующие инструменты с правильными типами
- **Эффективность**: нет лишних токенов на форматирование
- **Интеграция с constrained decoding**: tool-calling можно усилить грамматиками (связь с C.2)

## Формат описания инструментов: JSON Schema

Независимо от подхода (prompt или fine-tuning), инструменты описываются через **JSON Schema** — стандартный способ описания структуры JSON-объектов.

### Базовая структура

```json
{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "Получает текущую погоду для указанного города",
    "parameters": {
      "type": "object",
      "properties": {
        "city": {
          "type": "string",
          "description": "Название города на русском или английском"
        },
        "units": {
          "type": "string",
          "enum": ["celsius", "fahrenheit"],
          "description": "Единицы измерения температуры"
        }
      },
      "required": ["city"]
    }
  }
}
```

**Ключевые элементы:**

- **name**: уникальное имя функции (модель использует его для вызова)
- **description**: естественное описание — модель читает его, чтобы понять, **когда** вызывать эту функцию
- **parameters**: JSON Schema для аргументов
- **required**: список обязательных параметров

### Продвинутые возможности JSON Schema

```json
{
  "type": "function",
  "function": {
    "name": "analyze_data",
    "description": "Анализирует датасет и возвращает статистику",
    "parameters": {
      "type": "object",
      "properties": {
        "dataset_path": {
          "type": "string",
          "description": "Путь к CSV-файлу"
        },
        "columns": {
          "type": "array",
          "items": {"type": "string"},
          "description": "Список колонок для анализа"
        },
        "analysis_type": {
          "type": "string",
          "enum": ["descriptive", "correlation", "regression"],
          "description": "Тип анализа"
        },
        "config": {
          "type": "object",
          "properties": {
            "include_visualizations": {"type": "boolean"},
            "confidence_level": {
              "type": "number",
              "minimum": 0.8,
              "maximum": 0.99
            }
          }
        }
      },
      "required": ["dataset_path", "columns", "analysis_type"]
    }
  }
}
```

**Что здесь есть:**
- **Массивы** с типизированными элементами
- **Enum** — ограничение на конкретные значения
- **Вложенные объекты**
- **Числовые ограничения** (minimum/maximum)

### Как модель использует эти описания

Когда вы передаёте инструменты в API:

```python
)
```

   - **GPT-4**: использует специальный синтаксис с `
</think>

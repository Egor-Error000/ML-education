# А. Что предсказывает модель и на каких данных проверяется вывод

[Оглавление](README.md). Пункт 1 плана. **Происхождение:** дополнительный материал по действующему плану. В предоставленных чатах нет отдельного полного обсуждения этого курса; связанные примеры взяты из задач CV и LLM, без приписывания вам пройденных занятий.

## 1. Строка, объект и независимое наблюдение

Таблица с миллионом строк может описывать тысячу пользователей, каждого в тысяче моментов времени. Для задачи о новых пользователях независимая единица — пользователь; для прогнозирования завтрашней активности известных пользователей — временная последовательность с доступной историей. Число строк само по себе не определяет объём независимой информации.

До выбора модели ответьте: какое решение принимается, в какой момент, для какого объекта и как быстро требуется результат? Например, модель прогнозирует возврат товара при оформлении заказа. Статус «возврат одобрен» появляется позже и недоступен в момент предсказания. Даже если этот столбец находится в выгрузке рядом с обычными признаками, использовать его нельзя.

У каждого признака полезно различать время события и время доступности в системе. Покупка могла произойти вчера, но её обработанная категория появилась сегодня. Для вчерашнего решения этот признак был недоступен. То же относится к обновлённой версии документа, поздней разметке снимка и статистикам пользователя, посчитанным по всей будущей истории.

### 1.1. Сначала решение, затем строка таблицы

Постановка начинается с будущего применения: для кого, в какой момент и какое решение поддерживает prediction. «Есть CSV, нужно обучить классификатор» ещё не определяет задачу. Один и тот же CSV может использоваться для будущих заказов известных пользователей, для новых пользователей или для переноса на другой источник. Эти случаи требуют разных доказательств качества.

У строки есть несколько identities: prediction ID, исходный объект, группа зависимости, источник и время. Заказ может быть единицей prediction, пользователь — группой связанных заказов, магазин — источником, дата — осью будущего переноса. Не надо выбирать один ID и объявлять его единственной правильной единицей всех splits и metrics.

В CV кадр, видео, камера и физический объект также различаются. Сотня кадров одного проходящего объекта не равна сотне независимых новых объектов. Для текстов документ, его revision, chunks и вопросы к ним создают разные уровни зависимости. Цель «ответы на новые вопросы к известному corpus» отличается от «перенос encoder на новые документы»; одинаковый corpus в retrieval evaluation не всегда leakage, если именно такова целевая задача.

### 1.2. Момент события и момент доступности

Пусть prediction нужен в t0. Событие произошло за сутки до t0, но его обработанная категория попала в систему через сутки после t0. Исторический event_time подходит, available_at — нет: online pipeline не могла использовать этот feature. Простое условие event_time≤t0 не доказывает point-in-time корректность.

Для агрегата «средняя активность за предыдущие 30 дней» задают конец окна относительно t0, источник событий и задержку их обработки. Если при offline выгрузке пересчитать прошлый feature с полным знанием поздно прибывших данных, он может стать качественнее того, что реально доступно на serving. Backtest должен воспроизводить выбранный availability contract, а не только исторические timestamps событий.

Тот же принцип относится к manual labels, изменённым карточкам товаров и source revisions. Исправленная сегодня annotation может быть правильной truth для evaluation, но не входным feature вчерашнего prediction. Target information и input information имеют разные роли; хранение в одной таблице не делает оба типа доступными в t0.

### 1.3. Leakage можно создать без очевидного target column

Поле «return_approved» после события — явная утечка для прогноза при оформлении. Менее очевидны число обращений после заказа, итоговая длительность процесса, агрегаты по всей будущей user history или документ, обновлённый после решения. Даже feature с нейтральным названием может содержать downstream outcome.

Preprocessing тоже имеет время обучения. Scaler,imputer,словарь,feature selection и target statistics не должны узнавать test information через fit. Подробная mechanics split/cross-validation — в главе Б; здесь в паспорте уже отмечают, что вычисляется заранее и на какой части данных. Не вся трансформация является fit: deterministic смена единиц и learned normalization имеют разные требования.

Высокая importance подозрительного feature не доказывает leakage, но даёт повод проверить происхождение и availability. И низкая importance не доказывает отсутствие утечки: модель могла распределить сигнал по нескольким proxy. Нужны causal timing/data lineage, а не один график важностей.


## 2. Тип задачи определяет target и оценку

В классификации $y\in\{1,\ldots,K\}$; модель выдаёт класс или вероятности классов. В регрессии $y\in\mathbb R$; качество зависит от масштаба и цены отклонения. В ranking важен порядок кандидатов внутри запроса, а в retrieval — попадание релевантных документов в ограниченный набор. Превращение всех этих задач в одну «accuracy по строкам» теряет смысл решения.

Общая постановка риска:

$$
R(f)=\mathbb E_{(X,Y)\sim P_{\mathrm{future}}}
[\ell(f(X),Y)].
$$

Распределение $P_{\mathrm{future}}$ описывает целевое применение. Обучающий набор — приближение к нему, иногда смещённое отбором. Например, записи только одобренных заявок не позволяют без дополнительных предположений оценить качество на всех отклонённых клиентах. Отсутствие метки может зависеть от прежнего решения системы.

Средняя squared error и absolute error отражают разные цели. Для четырёх ошибок $(0,0,0,8)$:

$$
\operatorname{MAE}=\frac{8}{4}=2,
\qquad
\operatorname{RMSE}=\sqrt{\frac{64}{4}}=4.
$$

Большая редкая ошибка сильнее влияет на RMSE. Выбор метрики должен соответствовать цене такой ошибки, а не тому, какое число выглядит лучше. Для классификации аналогично важны последствия FP и FN, разобранные в главе Г.


### 2.1. Target —это определение события и горизонта

Для «возврат в течение 30 дней» надо определить начало отсчёта, событие возврата, time zone и правила отменённых/дублированных заказов. Это учебный target window, а не утверждение о праве потребителя. Метка «заявка на возврат» может отличаться от «товар физически получен обратно»; смешать их означает изменить задачу.

У positive событие иногда становится известно раньше конца окна. Для negative отсутствие события должно быть подтверждено полным наблюдением окна и нужной обработкой данных. Если label pipeline задерживается ещё 2 дня, заказ возрастом 31 день не обязательно имеет окончательно доступную negative label, даже когда сам 30-дневный horizon уже прошёл.

Можно оценивать только mature cohort с завершённым окном, либо выбрать метод, учитывающий censoring при другой постановке. Нельзя просто назвать всё ещё не случившееся negative и затем интерпретировать score как качество предсказания окончательных outcomes. Выбор mature cohort меняет период/популяцию оценки, что фиксируют отдельно.

### 2.2. Числовой пример задержки labels

В вымышленной выгрузке 1200 заказов. У 1000mature orders известно 100returns и 900negatives. Среди 200recent orders уже наблюдались 5returns, а 195 ещё не имеют завершённого outcome window. Есть 105confirmed positives,900confirmed negatives и 195unknown.

Если unknown механически считать negative, prevalence получится 105/1200=8.75%. Но до завершения окна итоговая positive rate может лежать от 105/1200=8.75% до(105+195)/1200=25%. Это логические границы по имеющимся данным, а не прогноз, что все unknown обязательно станут returns. У mature cohort prevalence10%, но она относится к другому временному subset.

Включить все ранние positives и только mature negatives тоже может создать outcome-dependent selection. Сначала определяют sampling/label availability rule, затем применяют его одинаково. «Меток стало больше» не всегда означает, что полученная выборка ближе к будущей популяции.

### 2.3. Classification, regression, ranking и retrieval

Классификация может выдавать probabilities, class decision и abstention по отдельной policy. Probability0.8 не тождественна решению класса 1 при любом cost/threshold. Числовые ID классов не делают расстояние между классами осмысленной regression target.

Регрессия предсказывает величину с units и допустимым диапазоном. Ranking сравнивает candidates внутри query/group, поэтому shuffle отдельных rows может разрушить evaluation unit. Retrieval ищет ограниченный набор evidence среди corpus; relevance labels и answerability не совпадают с обычной classification каждого документа без query.

Для multitask/multilabel данных задают, какие outputs доступны для каждой строки и как считаются missing labels. Unlabeled class не автоматически negative. Редкий класс и отсутствующая разметка —разные проблемы. Общая запись risk выше сохраняет выбранную loss и deployment distribution; она не выбирает их автоматически.

### 2.4. Почему mean и median baseline отличаются

Исходный пример ошибок[0,0,0,8] даётMAE2,RMSE4. Рассмотрим теперь именно targets y=[0,0,0,8] и constant prediction. При prediction0 эти ошибки совпадают с targets. При prediction2 absolute errors[2,2,2,6]:MAE3,RMSE√12≈3.464102. RMSE улучшилась, MAE ухудшилась.

Для empirical squared loss минимизирующая константа —mean targets, здесь 2. Для absolute loss подходит median, здесь 0. Это разные цели при одном dataset, а не противоречие quality report. В conditional regression аналогичный выбор loss связан с тем, какое свойство распределения Y|X нужно оценивать.

Если бизнес-ошибка асимметрична, ни MAE, ни RMSE не обязаны выражать её правильно. В учебной постановке сначала записывают consequences/error costs и допустимые constraints. Метрика выбирается для этого решения, а не по наиболее выгодному ranking моделей.


## 3. Паспорт набора

Паспорт — краткое проверяемое описание источника и правил обработки. В нём нужны единица предсказания, target и способ его получения, источник/даты, схема полей и типы, единицы измерения, размеры и группы, пропуски, частоты классов, доступность признаков и ограничения использования. Для динамических данных — ещё snapshot/version и задержка labels.

Пример для возвратов: строка — заказ; target — возврат в течение 30 дней; prediction time — подтверждение заказа; user ID задаёт группы; события последних 30 дней после заказа недоступны. В датасете, выгруженном сегодня, последние 30 дней ещё не полностью размечены. Если считать отсутствие возврата отрицательной меткой сразу после заказа, возникает правое цензурирование: часть positives ещё не успела проявиться.

Выбор зрелых заказов с полностью наблюдённым окном решает конкретную проблему неполных labels, но может сместить период оценки. Это фиксируется в паспорте. Нельзя одновременно включить вчерашние заказы и утверждать, что их 30-дневный outcome уже известен.

Для CV указываются камеры/видео, разрешения, правила аннотации и классы. Для текстов — источник документа, язык, версия, лицензия/доступ и способ получения метки. Chat logs должны сохранять роли и порядок: отдельная реплика без предыдущего контекста может не иметь определимого target.


### 3.1. Что делает паспорт проверяемым

Паспорт отделяет наблюдаемые факты от assumptions: источник/версия, схема, unit prediction, target/horizon, sampling, groups/time, missingness, units, labels и план переноса. Обсуждение [Datasheets for Datasets](https://arxiv.org/abs/1803.09010) мотивирует документирование происхождения, состава и intended uses; конкретный паспорт ниже — учебная схема этого курса, не обязательный единый стандарт.

Для toy orders dataset можно записать:

```text
prediction unit: order_id
dependency group: user_id
prediction time: подтверждение заказа
target: объявленное событие return в течение 30 дней
label availability: конец окна + задержка обработки, либо подтверждённый positive
evaluation cohort: mature orders по заранее заданному правилу
intended transfer: будущие заказы, тип пользователей указан отдельно
inputs: только поля с available_at <= prediction time
snapshot: immutable export version и manifest
```

Поля вроде user_id могут быть ключом группировки и одновременно доступным model input, но эти роли не тождественны. Исключить ID из features не значит устранить зависимость строк; другие attributes могут идентифицировать ту же группу. Числовой dtype ID также не делает его continuous measurement.

### 3.2. Manifest, schema и raw/processed distinction

Manifest связывает набор с конкретными файлами/shards, IDs, hashes, counts и transformation revisions. Passport объясняет смысл, manifest — воспроизводимую identity snapshot. Один hash подтверждает совпадение bytes, а не качество labels и отсутствие leakage. Человекочитаемый «тот же dataset» может означать уже другую выгрузку с изменёнными targets.

Raw данные сохраняют отдельно от processing logic, когда это возможно в выбранной среде. Для derived fields указывают source, fit subset и параметры. Тогда можно восстановить, что изменилось: исправили parse, обновили labels, исключили дубли или заменили model. Без этой связи улучшение score легко приписать не той причине.

Schema checks выявляют отсутствующий column, неожиданный dtype, единицы, диапазон и нарушенную identity. Но valid schema не доказывает смысловую корректность: возраст 300 может быть float, timestamp может быть в другой time zone, а status code — кодом иной версии API. Нужно сочетать автоматические invariants с аудитом содержимого.

### 3.3. Знание sampling process

Если labels получены только у выбранных предыдущей системой cases, не наблюдается outcome всей исходной популяции. Данные только одобренных заявок, только clicked documents или только успешно распарсенных изображений могут давать biased evaluation. «Данные из production» не означает representative sample автоматически.

В паспорте указывают механизм отбора, исключения и неизвестные причины missing labels. Не всегда можно восстановить полную population quality простым reweighting: нужны assumptions и доступная информация о sampling/support. В этом вводном разделе важно заметить ограничение, а не назначить универсальную коррекцию всем datasets.

Prediction quality также не является causal effect нового действия. Если система меняет intervention после прогноза и тем самым outcome, offline labels прежней policy отвечают другой ситуации. Нужно определить, оценивается прогноз наблюдаемого события или эффект принятого решения. Подробное causal inference не требуется для каждого baseline, но нельзя смешивать эти claims.


## 4. Baseline и срезы

Baseline нужен до сложной модели: majority class, константный прогноз, простое правило или линейная модель на разрешённых признаках. Он показывает, насколько задача вообще требует обучения. Accuracy 99% бессодержательна, если 99% объектов относятся к отрицательному классу и baseline всегда отвечает «нет».

Кроме общей метрики заранее выбираются важные срезы: источник, время, размер объекта, язык, новый/старый пользователь. Общая средняя может скрывать, что модель работает только на доминирующем источнике. Слишком мелкие срезы дают нестабильные оценки; всегда сообщается число наблюдений.


### 4.1. Простая модель как измерительный инструмент

Majority class,constant regression,простое lexical ranking илиprevious-period rule задают отправную точку. Если сложная модель не превосходит подходящий baseline, исследуют постановку/data/split/objective. Это ещё не доказательство плохой архитектуры: в labels может не быть полезного сигнала, а метрика может оценивать другое свойство.

При 1%positive majority negative classifier имеет 99%accuracy и 0positive recall. Такой baseline помогает увидеть, почему одна accuracy недостаточна. Threshold/PR/calibration подробно рассматриваются в главе Г; здесь паспорт уже должен фиксировать prevalence и требуемый decision criterion.

### 4.2. Aggregate score зависит от состава популяции

На sourceA accuracy0.95,наB0.60. Если offline sample содержит 90%A и 10%B,aggregate0.915. При future mixture20%A и 80%B получается 0.67 при **тех же** per-source accuracies. Падение average не доказывает изменение weights: изменилась оцениваемая смесь.

Поэтому source/time/language/new-user slices выбирают до окончательного вывода и сообщают их sizes. Малые slices имеют высокую uncertainty. Если искать только те subgroup plots, где candidate выигрывает, отчёт станет biased. Полезный report сохраняет полный declared набор критериев, а не выбор удачных картинок.

### 4.3. От паспорта к проверяемому вопросу

Для каждого field спрашивают: что он означает, когда доступен и как получен? Для target —когда его отсутствие становится negative? Для split —какие новые объекты имитируются? Для metric —какое решение и цену ошибки она отражает? Для quality claim —на какую популяцию он переносится и какие assumptions нужны?

Следующие главы применят ответы к split,cleaning,imbalance,augmentation,loaders,CV/text иdrift. Паспорт не заменяет эти механизмы, но делает их выбор осмысленным. Готовность этого учебного примера не означает, что реальный пользовательский dataset уже audited или model обучена.


## 5. Контроль и практика

1. Почему миллион строк не гарантирует миллион независимых примеров? **Ответ:** один объект может порождать множество связанных строк; схема обобщения определяется объектами, временем и источником.
2. Можно ли брать feature, появившийся после prediction time? **Ответ:** нет, даже если он находится в исходной таблице и очень полезен.
3. Почему свежий заказ без возврата не обязательно negative? **Ответ:** окно наблюдения outcome ещё не завершено.

4. Event раньше t0 гарантирует доступность feature? **Ответ:** нет, available_at может быть позже prediction time.
5. Почему известные early positives не решают проблему unknown negatives? **Ответ:** negative требует полного окна/наблюдения, а отбор только известных labels может быть outcome-dependent.
6. Доказывает ли hash корректность labels? **Ответ:** нет, он фиксирует bytes/identity, а не semantic quality.
7. Когда regression mean и median дают разные baselines? **Ответ:** при разных loss; squared loss предпочитает mean, absolute —median.
8. Почему один aggregate score не описывает все источники? **Ответ:** он зависит от mixture weights; per-source quality может различаться.
9. Всегда ли общий corpus train/test есть leakage для retrieval? **Ответ:** нет, зависит от того, проверяются новые queries к известной collection или перенос на новые documents.
10. Значит ли хороший prediction score доказанный эффект intervention? **Ответ:** нет, predictive association и causal effect —разные утверждения.

**Практика:** составьте паспорт одного набора. Для каждого поля запишите момент доступности; отдельно сформулируйте будущую популяцию и минимум две возможные утечки. Выберите baseline и метрику с объяснением цены ошибок. Это исходный artifact для остальных глав.

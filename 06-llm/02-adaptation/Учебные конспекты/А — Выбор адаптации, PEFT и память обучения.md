# А. Зачем адаптировать модель и откуда берётся расход памяти

Сохранён ход чата: full fine-tuning → память и забывание → frozen features → PEFT. **Углубление:** выбор вмешательства по типу ошибки и раздельный memory accounting. ## 1. Сначала ошибка, затем способ изменения модели

Адаптация — изменение поведения предобученной модели для нужной задачи. Иногда меняют параметры, иногда достаточно изменить доступный контекст. Чтобы выбрать метод, нужно зафиксировать примеры ошибок baseline.

Если модель не знает актуальную цену из внутреннего каталога, fine-tuning не обеспечивает регулярное обновление этого факта: полезнее retrieval/инструмент с актуальными данными. Если знает содержание, но нарушает формат или стиль, помогают точный prompt, structured decoding, SFT. Если неверно выбирает действие в известной среде, нужны демонстрации или другой feedback по действиям, а сначала — проверка контракта инструментов. Если рассуждение неверно, один шаблон ответа сам по себе проблему не решит.

Это диагностические гипотезы, а не запреты: SFT тоже может менять фактические ответы, RAG — ухудшать их из-за неверных документов. Выбирается изменение с проверяемым механизмом. До обучения собирают независимые evaluation prompts и определяют, какие регрессии недопустимы.

Различия стадий:

- **Pretraining:** обучение основного language objective на широком корпусе.
- **Continued pretraining, CPT:** продолжение такого обучения на доменном корпусе; данные могут быть сырым текстом.
- **SFT:** supervised обучение на выбранных демонстрациях целевого поведения; в instruction setting это инструкции, контекст и ответы.
- **Preference optimization:** обучение из сравнений/оценок ответов, а не только воспроизведение одной демонстрации.

Метод экономии параметров и objective — разные оси. Можно выполнять SFT с full fine-tuning, LoRA или другими PEFT. LoRA не является альтернативной функцией потерь к SFT.

## 2. Из чего состоит память

Пусть P — число параметров модели, P_train — число обучаемых. Память следует разложить:

$$
M_{\mathrm{total}}\approx M_{\mathrm{weights}}+M_{\mathrm{grad}}+M_{\mathrm{optimizer}}+M_{\mathrm{master}}+M_{\mathrm{activations}}+M_{\mathrm{buffers}}+M_{\mathrm{runtime}}.
$$

В BF16/FP16 вес обычно занимает 2 байта, в FP32 — 4. Adam хранит два moment states, но их dtype и распределение между устройствами зависят от реализации. Наличие отдельной FP32 master copy тоже зависит от способа mixed precision. Поэтому общая константа «на каждый параметр всегда 14 байт» неверна.

Два условных расчёта для $P=7\cdot10^9$:

$$
\begin{aligned}M_1&=(2+4+8)\,P=14P\;\text{байт}=98\;\text{GB},\\M_2&=(2+2+8+4)\,P=16P\;\text{байт}=112\;\text{GB},\qquad P=7\cdot10^9.\end{aligned}
$$

Это десятичные GB и только перечисленные состояния. Первый пример из чата арифметически даёт 98 GB; «больше ста» возникает после дополнительных расходов либо другой конфигурации. Нельзя из него выводить точный peak для любого trainer.

Frozen weights требуют хранения и forward compute, но для них не нужны обычные optimizer states и weight gradients. Для P_train=4 194 304 LoRA-параметров сами BF16 adapters занимают около 8.39 MB. Если условно выделить ещё 2 байта gradients и 8 байт moments, полный state адаптера получится около 50.33 MB без master/прочего. Это не вся модель: BF16 база 7B весит около 14 GB, а activations остаются.

Важная тонкость: замороженный модуль может участвовать в backward по входам, чтобы градиент дошёл до ранних обучаемых адаптеров. `requires_grad=False` для весов не равнозначно `no_grad()` для всей базы. Если отключить граф повсюду, adapters внутри неё не обучатся корректно.

Размер activations зависит от batch, длины, hidden size, реализации attention и checkpointing. Длинный контекст может вызвать OOM даже при маленьких adapters. Поэтому число trainable parameters — полезная, но неполная характеристика памяти.

## 3. Три режима изменения параметров

**Frozen features/linear probe:** encoder или другая база выдаёт представления, обучается небольшая head. При полностью фиксированном вычислении признаков их иногда можно предвычислить. Это сильный дешёвый baseline, а не заведомо плохой метод. Представления базы не меняются, но качество системы может ухудшиться из-за новой головы/порога — «никакого риска вообще» говорить нельзя.

**Full fine-tuning:** доступно обновление всех параметров. Такая свобода может помочь сложному domain shift, но требует большего state и контроля training data/LR. Забывание возможно, однако не обязательно: аккуратная настройка и mixing могут сохранить базовые способности. Качество LoRA не обязано всегда превосходить full tuning.

**PEFT:** изменяется ограниченное подмножество параметров или добавляются небольшие модули. Это уменьшает обучаемый state и стоимость хранения версий. База может обслуживать несколько задач с разными adapters, если runtime поддерживает нужную маршрутизацию. Сам факт маленького adapter не гарантирует ни отсутствие latency, ни сохранение общих способностей.

Даже при неизменной W0 функция $f(W_0,\mathrm{adapter},x)$ меняется. Сильный adapter может подавить полезное прежнее поведение. «База заморожена, значит catastrophic forgetting невозможно» — некорректный вывод о поведении полной системы. Можно отключить adapter и вернуть исходную базу, но активная адаптированная модель всё равно требует regression evaluation.

## 4. Какие способы экономии решают какую часть задачи

LoRA уменьшает P_train. Квантизация frozen base уменьшает storage весов. Gradient accumulation делит большой эффективный batch на microbatches: уменьшает одновременные activations, но не число весов. При одинаковых длинах effective batch обычно равен $microbatch\times accumulation_{\mathrm{steps}}\times data_{\mathrm{parallel\_workers}}$; нормировку loss нужно согласовать.

Activation checkpointing не хранит часть промежуточных активаций и пересчитывает их на backward: память меняется на время. Sharding распределяет состояния между устройствами. Offloading переносит данные в CPU/RAM или другой уровень памяти и добавляет обмены. Ни один из способов не является бесплатным универсальным ускорением.

**Разобранный выбор:** нужно исправить формат ответов на 500 размеченных запросах, есть 24 GB VRAM. Сначала проверяется prompting/schema baseline. Если нужен tuning, оценивается BF16 база плюс adapters и activations. Если база не помещается, рассматривается low-bit base/меньшая модель, затем длина и microbatch. Само число 500 не говорит, достаточно ли данных: важны coverage, качество и learning curve.

## 5. Самопроверка

1. Почему QLoRA и SFT можно использовать вместе? **Ответ:** первая задаёт хранение/обновление параметров, второе — обучающую задачу.
2. Уменьшает ли accumulation 14 GB базовых BF16 весов? **Ответ:** нет, оно влияет прежде всего на batch activations.
3. Почему PEFT может ухудшить ответы при frozen base? **Ответ:** adapter меняет общую функцию, хотя исходный массив W0 не изменился.
4. Сколько весят только 7B FP16 weights? **Ответ:** около 14 GB, без states, metadata и runtime.

**Практика:** составить бюджет для выбранного P и P_train с явно записанными dtype. Отдельно оставить измеряемые activations/buffers. После первого корректного batch сравнить расчёт с peak allocation; несоответствие разобрать по компонентам, а не подгонять «bytes/parameter».

# З. Как установить, что адаптация помогла

[Оглавление](README.md). Пункт 9 и протокол 14E; общая проверка 14A–D.

**Основа:** S3, строки 820–918. В исходнике evaluation завершает старый девятипунктный маршрут. Его вводные «мы обучили, сделали DPO, квантовали» заменены условной схемой: пользовательский запуск не подтверждён. **Исправления C09:** PPL не объявляется бесполезной, human preference не единственная ценность, contamination не выводится из высокой оценки. **Углубление:** paired comparison, ties, uncertainty и проверка экспортированного artifact.

## 1. Один score не отвечает на все вопросы

До обучения зафиксировать, что означает улучшение. Для QA — правильный ответ по допустимому evidence; для JSON extraction — правильные значения плюс нужная schema; для tool agent — допустимые действия и достигнутое состояние. Иногда правильный отказ при недостатке данных является успехом. Формулировка критерия должна быть проверяемой.

Полезно разложить качество:

- task correctness и полнота;
- следование конкретным инструкциям;
- формат/schema;
- factual grounding/citations;
- нежелательные регрессии;
- latency, память, стоимость успешного решения.

Успешный JSON parser не доказывает правильные поля. HTTP 200 от tool не доказывает достижение пользовательской цели. Красивый длинный ответ не гарантирует правильный факт. Поэтому нужно сохранять outputs и типы ошибок, а не только общий процент.

## 2. Где полезна perplexity

Для средневзвешенного token CE $H=-\frac1N\sum_t\log p(x_t\mid x_{<t})$ perplexity равна $\exp(H)$. Если H=ln2, PPL=2. Это характеристика предсказания **выбранного** текста при **выбранной** tokenization/mask. Она полезна для language modeling, domain adaptation и поиска явных регрессий распределения.

Но preference и task success — другие величины. У задачи может быть несколько одинаково верных формулировок; модель с иной формулировкой получает высокий CE относительно одного reference. С другой стороны, уверенное воспроизведение распространённой фактической ошибки может уменьшать CE на плохом корпусе. PPL не «мертва»: она отвечает на ограниченный вопрос.

Сравнивать PPL нужно на одинаковом objective, корпусе и согласованной единице tokenization. Если tokenizers разные, среднее «на токен» имеет другую единицу; сравнение требует дополнительной нормировки/осторожности. Loss по assistant-only и all-token тоже не одно и то же.

## 3. Прямое сравнение baseline и candidate

Для каждого evaluation prompt получить baseline и candidate outputs при одинаковом оговорённом decoding/budget. Зафиксировать model/base revision, tokenizer/template, adapter, dtype, seed где применимо, sampling и stop conditions. Наличие одного seed не гарантирует детерминизм между runtime/hardware, но позволяет воспроизвести конфигурацию.

Paired comparison полезно потому, что сложность вопроса общая для двух вариантов. Представим 100 задач: обе модели решили 60, только baseline 10, только candidate 20, обе ошиблись 10. Accuracy baseline=70%, candidate=80%; улучшение 10 percentage points. Чтобы понять механизм, важны 30 расхождений, а не только итоговые две цифры.

Для uncertainty можно пересэмплировать prompts парно: в bootstrap каждый выбранный prompt тянет обе оценки. Если prompts связаны общим документом/источником, пересэмплировать группы, иначе интервал окажется излишне узким. Повторы seeds оценивают training/decoding variation; они не устраняют sampling bias evaluation набора.

Не нужно искать один магический minimum N. Малый набор полезен для regression debugging, но слаб для тонкого ranking. В отчёте указать размер, происхождение, срезы и uncertainty; не превращать разницу в один случай из десяти в универсальное превосходство.

## 4. Люди и LLM-as-a-judge

Human comparison требует rubric, анонимизации outputs, возможности ties/disagreement и контроля разметки. Если из 100 пар candidate победил 45, проиграл 35, ties=20:

$$
\begin{aligned}\mathrm{WR}_{\mathrm{half\text{-}ties}}&=\frac{45+\tfrac12\cdot20}{100}=55\%,\\\mathrm{WR}_{\mathrm{non\text{-}ties}}&=\frac{45}{80}=56.25\%.\end{aligned}
$$

Обе convention допустимы при явном определении, но нельзя скрывать ties или менять denominator после получения результата. Human preference тоже может зависеть от verbosity и ошибочного понимания задачи.

Judge-модель масштабирует оценку, но наследует bias. Практический протокол: отдельные критерии, blind identities, смена порядка A/B, tie option, проверенная human subset и разбор disagreement. Если judge предпочитает A в одном порядке и B в другом, результат нестабилен. Judge prompt, model revision и generation config — часть eval artifact.

Для задач с объективной проверкой использовать её: execution tests, правильные поля, проверяемые source spans, state transition. Judge нужен там, где нельзя выразить всё простым oracle, но и там он не заменяет sampling audit. Ответ «модель нравится судье» уже по scope, чем «правильно решает задачу».

## 5. Contamination, alignment tax и честный вывод

Contamination возникает, если eval-примеры или близкие производные попали в training. Проверяют exact/near duplicates, происхождение synthetic data, split по источникам и доступность benchmark в корпусе. Высокий результат — повод разобраться, но не доказательство запоминания. Новая дата benchmark тоже не доказывает полную независимость, если задания автоматически построены из знакомых шаблонов.

«Перевернуть вопрос» может дать полезный robustness test, но это другая задача; провал сам по себе не доказывает contamination. Нужен набор свидетельств, а не один эффектный контрпример.

Alignment tax — изменение других способностей при оптимизации целевого поведения. Оно может быть отрицательным, нулевым или положительным в разных срезах. Не назначать универсальный допустимый процент. Например, улучшение format success при росте false refusals может быть неприемлемо для конкретного приложения, даже если общий preference score вырос.

## 6. Экспорт входит в оценку

Проверяется **загруженный итоговый artifact**: weights/adapters, точная база, tokenizer, template, generation config и dtype. Merge/requantization/export могут изменить outputs; забытый adapter даёт корректно работающую исходную модель с другим поведением.

Сохранить manifest и контрольные prompts; сравнить unmerged и merged/reloaded варианты, затем task metrics. Совпадение logits до малого tolerance полезно для численной проверки, но не заменяет end-to-end eval. Если tolerance/decoding приводит к другим discrete tokens, изучить причину и влияние на задачу.

1. Доказательство ли низкий train loss? **Ответ:** нет, он может отражать запоминание/ошибочную mask; нужен независимый набор.
2. Можно ли выбирать merge рецепт на test? **Ответ:** повторный подбор превращает test в validation; итоговая оценка требует новой независимой проверки.
3. Может ли PPL ухудшиться при росте task success? **Ответ:** да, objectives и distributions могут различаться.

**Практика:** спроектировать 20 regression prompts по 4 срезам и рубрику. Для условного результата 45/35/20 вручную посчитать две tie conventions. Никаких реальных метрик обучения в этой главе не заявлено: все числа иллюстративные.

# Ж. Объединение весов: что сохраняется, что может сломаться

[Оглавление](README.md). Пункт 8 и часть 14E.

**Основа:** S3, строки 719–816. Сохранены две задачи чата: выбор между несколькими хорошими checkpoints и обслуживание нескольких задач с одной базой. **Исправления C08:** soup не гарантирует улучшение; TIES не всегда majority vote; усреднение LoRA factors и full deltas различается; switching — отдельная операция. **Углубление:** контрпример factors, значений sign election и ожидание DARE.

## 1. Сначала определить операцию

**Merge одного adapter в base:** вычислить $W_0+sBA$; цель — материализовать ту же адаптированную linear функцию при оговорках о dtype. **Merging нескольких task models:** построить одну новую модель из разных learned deltas; качество может измениться непредсказуемо. **Switching:** по запросу выбрать один adapter к общей базе; единой смешанной модели не создаётся.

Эти операции можно использовать в одной системе, но нельзя доказывать поддержку одной наличием другой. Например, возможность указать adapter в config не означает быстрый concurrent hot-swap любых ranks в каждом backend. Runtime capability и фактическое поведение нужно проверять.

### Две задачи чата требуют разных итоговых артефактов

Первая ситуация S3: несколько checkpoints одной задачи после разных learning rates/epochs. Нужно выбрать или совместить их так, чтобы улучшить обобщение. Вторая: SQL, Python и юридический стиль требуют разных настроек общей базы. Здесь одна blended модель — лишь вариант; router может сохранять специализацию, выбирая task adapter. Дешёвое shared хранение не требует обязательно смешивать несовместимые behaviors.

Один adapter merge материализует уже обученную функцию, если условия равенства выполнены. Multi-model merge создаёт candidate новой функции без нового обычного training, но требует evaluation. Веса, outputs, generated texts и routing decisions — четыре разных объекта смешивания. Надпись «merged successfully» подтверждает вычисление файла, а не улучшение задач.

## 2. Model soup и совместимость координат

Для compatible checkpoints $\theta_{i}$ можно взять $\theta_{\mathrm{soup}}=\sum_iw_i\theta_i$, где веса суммируются к 1. Если все получили из одной базы $\theta_{0}$, эквивалентно $\theta_0+\sum_iw_i\delta_i$, $\delta_{i}=\theta_{i}-\theta_{0}$.

Интуиция: если good solutions лежат в совместимой области parameter space, среднее иногда сохраняет полезное поведение и ослабляет специфические вариации. Но в нелинейной сети `f(средние веса)` обычно не равно `среднее f(веса)`. Soup отличается от ансамбля predictions: на inference используется одна новая функция, а не голосование нескольких моделей.

Даже одинаковые shapes не гарантируют совместимость. Две независимо обученные сети могут иметь переставленные hidden units. Упрощённо, модель с двумя нейронами и модель с переставленными двумя нейронами вычисляют ту же функцию при согласованной перестановке следующего слоя; поэлементное среднее их параметров может дать другое поведение. Поэтому общая инициализация/revision и согласованные architecture/tokenizer важны. [Model soups](https://arxiv.org/abs/2203.05482).

### Почему model soup отличается от голосования ответов

Возьмём скалярную нелинейную модель fθ(x)=ReLU(θx), x=1, θ1=1,θ2=−1. Среднее predictions равно(1+0)/2=0.5. Средний параметр θ=0 даёт output0. Это простой контрпример равенству «усреднить веса — значит получить среднее поведение». В глубокой сети различие ещё сильнее из-за связей между слоями.

В чате использовалась картинка loss landscape с широким дном. Это полезная гипотеза для близких решений из общей инициализации, но она не доказывает, что arbitrary checkpoints лежат в одной удобной области или что плоскость в выбранной parameterization равна robust generalization. Средняя точка двух хороших минимумов может иметь высокий loss между ними. Выбор ingredients и interpolation проверяют на validation.

Uniform soup задаёт равные веса, weighted soup — выбранные w_i. Можно добавлять ingredients последовательно, принимая candidate по validation; это уже tuning procedure со своим бюджетом и риском переоптимизировать holdout. «Почти всегда лучше каждого ингредиента» из S3 не сохраняется как гарантия. [Model soups](https://arxiv.org/abs/2203.05482).

Task arithmetic использует θ0+Σα_iδ_i. Если Σα_i≠1, это не тот же average checkpoints, потому что коэффициент базовой θ0 при прямой сумме будет иным. Коэффициенты применяют к deltas относительно ровно той же base revision, а не к случайным weight files с одинаковым именем architecture.

### Почему нельзя просто усреднить A и B

Для двух adapters среднее deltas:

$$
\Delta_{\mathrm{avg}}=\frac{B_1A_1+B_2A_2}{2}.
$$

Если отдельно взять средние factors, получится:

$$
\left(\frac{B_1+B_2}{2}\right)\left(\frac{A_1+A_2}{2}\right)=\frac{B_1A_1+B_1A_2+B_2A_1+B_2A_2}{4}.
$$

Добавились cross terms, изменились коэффициенты. Скалярный пример: A1=1,B1=1; A2=-1,B2=-1. Обе deltas равны 1, их среднее 1. Средние A/B равны нулю, произведение 0. Значит, даже одинаковая функция adapters может исчезнуть при наивном factor averaging.

Для точного представления суммы можно конкатенировать factors с согласованными scales, увеличив rank, либо материализовать deltas и затем приближать их выбранным low-rank методом. При усечении rank появляется approximation error и нужна оценка.

### Точное low-rank представление суммы и цена компрессии

Для s1B1A1+s2B2A2 можно взять конкатенированные factors $B_c=[s_1B_1\;s_2B_2]$ и $A_c=[A_1;A_2]$. Тогда произведение ровно равно сумме без cross terms. Shapes: при ranks r1,r2 Bc имеет d_out×(r1+r2), Ac — (r1+r2)×d_in. Это доказывает возможность exact sum, но верхняя граница rank выросла.

Если нужно вернуть rank8 после сложения двух rank8 adapters, требуется approximation, например factorization усечённой dense delta. Ошибка в Frobenius norm матрицы не равна автоматически error downstream quality: входы и последующие layers могут усиливать отдельные направления. Поэтому final task validation нужна и после такой численно аккуратной компрессии.

Factor representation не уникальна: BA=(BR)(R^{-1}A) для подходящей обратимой R. Поэтому разница A/B двух обучений может отражать произвольный выбор basis, а не разные функции. Скалярный sign counterexample главы — частный случай этого факта. Анализировать только нормы одного factor без согласования scaling/basis опасно.

## 3. TIES: trim, sign election, согласованное слияние

Task delta задаёт изменение относительно общей base. TIES сначала обрезает малые компоненты по выбранному density/threshold. Это эвристика фильтрации, а не доказательство, что каждая малая delta была шумом. Затем для координаты выбирается агрегированный знак и усредняются согласованные изменения.

В стандартной смысловой схеме знак выбирается по сумме оставшихся значений. Пример $\left(+0.1,\,+0.1,\,+0.1,\,-1.0\right)$: положительных моделей три, отрицательная одна, но сумма -0.7, знак отрицательный. Поэтому из «3 против 1» нельзя вывести результат simple majority без указания варианта алгоритма. После отбора согласованных элементов выполняется disjoint merge и масштабирование по конфигурации. [TIES](https://arxiv.org/abs/2306.01708).

### Восстанавливаем три операции TIES по координатам

Trim оставляет выбранную долю крупных absolute delta entries в каждой модели по declared rule. Слово density означает долю сохраняемых entries в конкретной конфигурации; «нижние20%» — один возможный threshold, не неизменное свойство метода. Малые изменения могут быть полезными, большие — noise, поэтому смысл trim эмпирический.

Sign election разрешает конфликт по координате. Для values(+0.1,+0.1,+0.1,−1) sum=−0.7. В sum-based election сохраняется negative direction, хотя большинство знаков positive. После этого disjoint average использует согласованные nonzero entries. Если остался только−1, его среднее−1, не−0.7/4. Scale recipe затем отдельно регулирует общую силу update.

Три операции нельзя спутать с голосованием «какая модель лучше» целиком: у каждой coordinate может победить другой набор ingredients. Также zero после trim означает отсутствие выбранного вклада, а не доказательство семантической нейтральности параметра. [TIES](https://arxiv.org/abs/2306.01708).

## 4. DARE: случайно удалить и компенсировать масштаб

Пусть delta-компонента d сохраняется с вероятностью p. Определим $\widetilde d=\frac{m d}{p},\quad m\sim\operatorname{Bernoulli}(p)$. Тогда $\mathbb{E}[\widetilde d]=d$. При $p=0.25$ величина 0.4 становится 1.6 с вероятностью 0.25 и нулём с вероятностью 0.75.

Сохранение ожидания **дельты** не означает сохранение функции после нелинейного forward и не гарантирует качество конкретной маски. Variance растёт при малом p: $\operatorname{Var}(\widetilde d)=\frac{d^2(1-p)}{p}$. Для $d=0.4$,$p=0.25$ это 0.48. Поэтому «можно без потерь выкинуть 90% любых adapters» — неверный общий вывод. DARE может предобрабатывать deltas перед другим merging, включая TIES; это не одинаковые механизмы.

### DARE сохраняет expectation параметров, но не nonlinear behavior

При keep probability p=0.1 каждый сохранённый delta entry умножается на10, а90% entries зануляются. В одной mask важное направление может исчезнуть полностью. Для скалярного positive delta d>0 nonlinear f(d)=d² имеет expectation после DARE $E[\widetilde d^2]=d^2/p$, не d². При p=0.1 это в десять раз больше. Значит, даже точное сохранение Eδ не доказывает сохранение E f(δ).

В приведённой главой ситуации d=0.4,p=0.25 outcomes0 и1.6 имеют mean0.4 и variance0.48. Эта variance — не rounding: это встроенная случайность procedure. Seed, keep density и scaling сохраняют в manifest. Несколько masks могут дать разные metrics; отбор лучшей на test уже переиспользует test как validation.

DARE может готовить sparsified deltas для TIES, но «случайное удаление заставляет оставаться только устойчивые знания» из S3 не следует: selection здесь random, а не oracle importance. Успех high drop rate — эмпирический результат в условиях методов, не разрешение удалять90% любой адаптации без потерь.

### Switching, concurrency и caches

Router, выбрав SQL adapter, должен привязать его к запросу и всем последующим steps этого контекста. Если global mutable adapter меняется другим concurrent request, функции могут смешаться. Поддержка batched per-request adapters или иной изоляции — capability конкретного runtime, а не математическое следствие LoRA.

История K/V могла быть рассчитана с прежним adapter. Даже если менялись только projections некоторых layers, это может менять representations и будущие K/V. Поэтому после switching нельзя автоматически использовать старый cache как будто изменилась только подпись задачи. Загружают consistent base+adapter revision и проверяют first token/whole response после переключения.

Размер файла не задаёт latency: важны disk/cache, transfers, allocation, compilation и queue. API `load_adapter` и `set_adapter` описывают операции библиотеки, но не доказывают мгновенный concurrent hot-swap в другом engine. Пример `Modelfile ADAPTER` из S3 тоже не равен гарантии «всякая runtime автоматически держит одну shared base и меняет её за миллисекунды».

### Recipe, export и проверка после reload

Сохраняют ingredients, exact base/tokenizer revisions, scales, trim/density, merge method и dtype. Смешать scalar recipes TIES/DARE с raw adapter paths без поддержки выбранного инструмента нельзя только потому, что YAML синтаксически читается. Franken-merging слоёв разных моделей дополнительно требует совместимости residual width, positions, normalization и обученных interfaces; одинаковая ширина не является достаточным доказательством.

На одном evaluation наборе сравнивают best single checkpoint, простой average и candidate sophisticated merge. Проверяют все исходные задачи плюс regressions. После export/reload и quantization повторяют проверку, поскольку финальный artifact может отличаться. Это завершает задачу объединения весов конкретным проверенным результатом, а не обещанием бесплатного прироста.

## 5. Adapter switching и проверка итогового artifact

Switching выбирает задачу/tenant-specific adapter. Нужны routing, base revision, совместимость targets/rank, управление памятью и исключение случайного смешивания adapter states между запросами. Стоимость включает загрузку, возможную компиляцию и влияние очереди; «всегда несколько миллисекунд» нельзя обещать по размеру файла.

Перед любым merging проверить base/tokenizer/architecture и полный manifest. Затем оценить исходные отдельные модели, лучший single checkpoint и merged candidate на тех же prompts. Нужны все задачи, включая старые: улучшение SQL не доказывает сохранение Python/общего диалога. Hyperparameters merging выбираются на validation; test нельзя использовать как бесконечный конкурс рецептов.

После сохранения и reload повторить predictions/metrics, а для quantized export — отдельно проверить requantization. Успешное выполнение команды merge означает только получение файла.

1. Чем soup отличается от ensemble? **Ответ:** усредняются параметры одной функции, а не outputs нескольких функций.
2. Почему DARE rescale на 1/p? **Ответ:** чтобы сохранить математическое ожидание delta-компоненты.
3. Можно ли merge два adapters разных revisions базы? **Ответ:** без доказанной совместимости корректность не установлена; одинаковый размер не достаточен.

**Практика:** руками воспроизвести factor counterexample и sign election. Для реального merging сначала сравнить один простой weighted average с лучшим исходным checkpoint; усложнять алгоритм только при понятной ошибке, сохраняя independent evaluation.

## Диагностика CV: ошибки данных, модели и post-processing

**Статус сценария:** authored — расширение CV; приёмка текста отдельно

**Учебный вопрос:** Как локализовать причину плохого результата до замены архитектуры?

**Уровень:** основа ветки. **Предпосылки:** cv-losses, cv-detection, cv-semantic

**Потребители:** cv-cases

**Порядок объяснения:**

1. Разделить систему на проверяемые этапы.
2. Диагностика по типу задачи.
3. Ablation study.
4. Разобранный пример: suppression и conditional recall.
5. Артефакт диагностики.
6. Самопроверка с ответами.

**Разобранный пример:** Есть 100 GT objects. До score filtering candidates покрывают 90, после threshold — 80, после NMS — 70. Recall стадий относительно GT: 0.90,0.80,0.70. Доля сохранённых после threshold среди покрытых candidates $80/90\approx0.88889$, после NMS $70/80=0.875$. Если улучшить только NMS до идеального сохранения этих 80, верхняя граница recall в этом intervention 0.80, не 1.

Для двух режимов по 200 независимым изображениям accuracy 0.80 и 0.82 разница составляет четыре изображения. Если результаты paired, важны именно discordant pairs, а не только две marginal accuracies. При 10 исправленных и 6 испорченных примерах улучшение +4, но выборка мала для уверенного общего вывода. Срез новых камер может ухудшиться при росте среднего.


**Схемы и разбор:** Error localization: Data / annotations → Preprocess → raw predictions → Decode → filter / NMS → Final metric + error slices; Controlled experiment: Наблюдение → hypothesis → Один intervention + baseline → Тот же split / budget / seeds → Сравнение → следующий шаг.

**Практика и проверка:** вопросы и объяснения ответов находятся в главе. Изменение одного фактора разобрано в разделе самопроверки.

**Ограничения:** см. раздел границ, диагностики или выбора в главе.

**Критерий понимания:** объяснить вычислительный путь, воспроизвести расчёт и назвать условие, при котором вывод перестанет быть верным.

## Robustness, domain shift, OOD и отказ от ответа

**Статус сценария:** authored — расширение CV; приёмка текста отдельно

**Учебный вопрос:** Как обнаружить потерю качества при новой камере или неизвестных объектах?

**Уровень:** основа ветки. **Предпосылки:** cv-losses, cv-transfer

**Потребители:** Самостоятельное применение.

**Порядок объяснения:**

1. Виды сдвига.
2. Проверки invariance.
3. Confidence, OOD score и отказ.
4. Разобранный пример: coverage и uncertainty.
5. Monitoring.
6. Самопроверка с ответами.

**Разобранный пример:** Из 1000 images принимаются 800; среди них 40 errors. Coverage $800/1000=0.8$, risk $40/800=0.05$. После повышения порога принимаются 500, из них 10 errors: coverage 0.5, risk 0.02. Ошибка среди принятых уменьшилась, но объём ручной проверки вырос с 200 до 500.

В новом camera domain 20 из 100 samples ошибочны, хотя mean confidence 0.95. Наблюдаемая accuracy 0.8 против заявленных 0.95 показывает miscalibration на этом срезе; одной mean недостаточно для полной calibration curve. Если на 100 independent negative samples нет FP, это не доказывает FPR 0. Грубая 95% верхняя оценка «rule of three» около $3/100=3\%$, при assumptions Bernoulli и независимости.


**Схемы и разбор:** Shift evaluation: Independent domain slices → Baseline + controlled corruptions → Accuracy / AP / calibration → Failure analysis → adaptation; Selective prediction: Model score + OOD signal → Validation thresholds → Accept / reject decision → Coverage + selective risk.

## Deployment: экспорт, quantization, distillation и производительность

**Статус сценария:** authored — расширение CV; приёмка текста отдельно

**Учебный вопрос:** Как сохранить смысл предсказаний после экспорта и измерить полную стоимость?

**Уровень:** основа ветки. **Предпосылки:** cv-transfer, cv-losses

**Потребители:** cv-cases

**Порядок объяснения:**

1. Артефакт модели шире файла весов.
2. Precision и quantization.
3. Distillation и runtime.
4. Разобранный пример: quantization и latency.
5. Самопроверка с ответами.

**Разобранный пример:** Пусть $s=0.1,z=0$, допустимый signed range -128..127. Значение 0.26 округляется в $q=3$, reconstruction 0.3, error 0.04. Значение 20 clips до 127, reconstruction 12.7, error -7.3. Малый typical rounding error не спасает от clipping outliers.

Один запрос тратит 5 ms на decode, 3 ms preprocessing, 2 ms transfer, 12 ms model, 4 ms post-processing. Sequential latency 26 ms, максимум такого неперекрытого pipeline около $1000/26=38.46$ requests/s. Ускорение model вдвое даёт 20 ms и 50 requests/s, не удвоение всего pipeline. Параллельная pipeline-система может иметь иной throughput; p95 latency всё равно измеряют отдельно.

Для 10 million weights float32 storage примерно 40 MB, INT8 — 10 MB без scales и metadata. Peak memory также включает activations, buffers и runtime caches.


**Схемы и разбор:** Deployment bundle: Weights + input / output contract → Export → runtime graph → Numerical comparison + task eval → Versioned bundle → rollout; PTQ / performance: Representative calibration inputs → Activation ranges → scales → Quantized operators / backend → Full latency + quality validation.

## Сквозные разборы: дефекты, видеопоток и документы

**Статус сценария:** authored — расширение CV; приёмка текста отдельно

**Учебный вопрос:** Как выбрать и проверить весь CV pipeline под конкретную цель?

**Уровень:** основа ветки. **Предпосылки:** cv-anomaly, cv-tracking-models, cv-documents, cv-diagnosis, cv-deployment

**Потребители:** Самостоятельное применение.

**Порядок объяснения:**

1. Кейс 1: контроль дефектов.
2. Кейс 2: анализ видеопотока.
3. Кейс 3: обработка документов.
4. Разобранный пример: operational cost.
5. Проверяемый результат.
6. Самопроверка с ответами.

**Разобранный пример:** На линии за день 10000 изделий: 100 дефектных, 9900 нормальных. Candidate находит 90 дефектных и ошибочно отклоняет 198 нормальных. Recall 0.9, FPR $198/9900=0.02$, precision $90/(90+198)=0.3125$. Review получает 288 изделий. При цене FN 100 и FP 1 ожидаемая измеренная стоимость $10\cdot100+198=1198$ условных единиц.

Второй threshold даёт TP=95 и FP=396. Стоимость $5\cdot100+396=896$, но review 491. При capacity 300 второй threshold непригоден без изменения процесса, хотя стоимость ниже. Решение требует одновременно quality, capacity и latency, а не одного F1. Это учебные counts, не эксперимент курса.


**Схемы и разбор:** Контроль дефектов: Independent product + labels → Classifier / mask / anomaly → Threshold + review capacity → Miss cost + false alarms; Видео и документы: Frames / page regions → Tracking / OCR + structure → Event logic / field assignment → End-to-end errors + evidence.

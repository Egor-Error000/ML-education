**Учебный вопрос:** Как отличить нехватку знаний, ошибку поведения и проблему исполнения?

**Результат:** читатель объясняет механизм, воспроизводит числовой пример, называет предпосылку и проверяет её нарушение.

**Уровень:** основа ветки. **Предпосылки:** lm-training, lm-generation, df-split, df-text. **Потребители:** adapt-sft, adapt-regimes, adapt-lora, adapt-variants, adapt-alternatives, adapt-preference, adapt-merging, adapt-distillation, adapt-continual, adapt-evaluation.

**Порядок объяснения:** Сначала ошибка, затем способ изменения модели → Почему выбор fine-tuning не начинается с числа параметров → Как измерять forgetting без метафоры «стерли знания» → Из чего состоит память → Восстанавливаем memory accounting из разбираемого примера по каждому tensor → Три режима изменения параметров → Когда frozen features действительно можно предвычислить → Какие способы экономии решают какую часть задачи → Accumulation, checkpointing, sharding и ускорение — разные рычаги → Самопроверка.

**Определения:** Как отличить нехватку знаний, ошибку поведения и проблему исполнения?; формы, единицы и фиксированные/обучаемые величины проверяются при первом использовании.

**Формулы и выводы:** `M_{\mathrm{total}}\approx M_{\mathrm{weights}}+M_{\mathrm{grad}}+M_{\mathrm{optimizer}}+M_{\mathrm{master}}+M_{\mathrm{activations}}+M_{\mathrm{buffers}}+M_{\mathrm{runtime}}.`; `\begin{aligned}M_1&=(2+4+8)\,P=14P\;\text{байт}=98\;\text{GB},\\M_2&=(2+2+8+4)\,P=16P\;\text{байт}=112\;\text{GB},\qquad P=7\cdot10^9.\end{aligned}`

**Разобранный пример:** В S2 разговор начался с full fine-tuning как естественной попытки «дать модели датасет и обновить всё». Здесь полезно разложить целевое изменение. Если на задаче фактического QA обучить только стиль ответов, уменьшение training loss не подтвердит, что модель получила нужные факты. Если проблема в неверном JSON, добавление тысяч страниц сырого текста может вообще не показать правильного контракта output.

**Практика:** **Практика:** составить бюджет для выбранного P и P_train с явно записанными dtype. Отдельно оставить измеряемые activations/buffers. После первого корректного batch сравнить расчёт с peak allocation; несоответствие разобрать по компонентам, а не подгонять «bytes/parameter».

**Ограничения и ошибки:** Это десятичные GB и только перечисленные состояния. Первый пример из разбираемого примера арифметически даёт 98 GB; «больше ста» возникает после дополнительных расходов либо другой конфигурации. Нельзя из него выводить точный peak для любого trainer. В исходном расчёте 7 млрд весов BF16 дают14 GB, gradients FP32 —28 GB, два FP32 moments —56 GB; сумма98 GB. Это declared configuration. Если gradients BF16, их14 GB, а не28; если одновременно присутствует FP32 master copy, она добавит28 GB. Нельзя одновременно взять выгодные части одной схемы и неучтённые требования другой и назвать результат точным peak.

## SFT: данные, шаблоны, masks и objective

**Учебный вопрос:** Какие позиции становятся целями supervised fine-tuning?

**Результат:** читатель объясняет механизм, воспроизводит числовой пример, называет предпосылку и проверяет её нарушение.

**Уровень:** основа ветки. **Предпосылки:** adapt-choice. **Потребители:** adapt-regimes, adapt-lora, adapt-variants, adapt-alternatives, adapt-preference, adapt-merging, adapt-distillation, adapt-continual, adapt-evaluation, agent-demonstrations.

**Порядок объяснения:** SFT и pretraining могут использовать похожую CE для разных данных → Что меняется при превращении base model в instruction model → Книги: сырьё зависит от задачи → Возвращаем вопрос пользователя о книгах с тремя разными objectives → Ручные demonstrations, Self-Instruct и FLAN-style mixture → Роли, template и labels → Прослеживаем masking до конкретного logit → Padding, truncation и packing → Почему нормировка по tokens влияет на задачу → Как выглядит первый осмысленный эксперимент → Вопросы с ответами.

**Определения:** Self-Instruct; Evol-Instruct; целевые токены; Какие позиции становятся целями supervised fine-tuning?; формы, единицы и фиксированные/обучаемые величины проверяются при первом использовании.

**Формулы и выводы:** `\mathcal{L}=-\frac{\sum_t m_t\log p_t}{\sum_t m_t}.`

**Разобранный пример:** 1. Определить задачу и единицу примера. 2. Отделить источник/главы для holdout до массовой генерации похожих вопросов. 3. Сохранить passage ID и происхождение каждой пары. 4. Проверить ответы по тексту; убрать дубликаты и очевидные ошибки teacher. 5. Проверять перенос на новых вопросах и источниках, а не только те же passages с иной формулировкой.

**Схемы:** оформление/course/adapt-sft.svg; проследить вход, все блоки, выход и связи, сверить с описанием.

**Практика:** **Практика:** вручную разметить один двухходовый диалог. Указать input, shifted targets, active loss positions, padding и EOS. Затем обрезать последние три токена и объяснить, остаётся ли полезный supervised signal.

**Ограничения и ошибки:** Не нужно противопоставлять «pretraining даёт знания, SFT только форму» как строгий закон. Параметры после SFT могут изменять фактические ответы, reasoning и другие способности. Однако маленький набор демонстраций не гарантирует усвоения большого нового домена и не обеспечивает обновляемую базу фактов. **Self-Instruct** расширяет исходный набор задач: из seed-инструкций teacher предлагает новые инструкции и ответы, после чего отсеиваются повторы, непроверяемые задания и ошибки. Если seed охватывает только один тип задачи, увеличение количества само по себе не добавит coverage. **Evol-Instruct** преобразует задачи, добавляя сложность/ограничения; искусственно усложнённый prompt нужно проверять на непротиворечивость и наличие корректного ответа.

**Критерий понимания:** самостоятельно ответить «Какие позиции становятся целями supervised fine-tuning?», воспроизвести пример, назвать нарушение его предпосылки и выбрать корректную единицу оценки.

## LoRA: low-rank обновление и градиенты

**Учебный вопрос:** Как low-rank ветвь обновляет конкретную линейную проекцию?

**Результат:** читатель объясняет механизм, воспроизводит числовой пример, называет предпосылку и проверяет её нарушение.

**Уровень:** основа ветки. **Предпосылки:** adapt-choice, adapt-sft, adapt-regimes, lm-transformer. **Потребители:** adapt-variants.

**Порядок объяснения:** Добавляется ветвь к конкретному linear layer → Вопрос из разбираемого примера: «Куда мы вставляем эти матрицы?» → Почему маленький ранг не равен восьми степеням свободы весов → Что означают target_modules и как считать параметры → Вопрос из S2: «Всем блокам и всем головам или только некоторым?» → Сравниваем бюджет Q/V и всех linear modules → Почему A случайная, B нулевая → Frozen — запрет обновления параметра, а не обрыв вычислительного графа → Два шага на исходном числовом примере → Что означает каждый элемент первого шага → Merge и ограничения интуиции → Что сохраняется отдельно и что нужно для загрузки → Самопроверка.

**Определения:** Второй backward; Как low-rank ветвь обновляет конкретную линейную проекцию?; формы, единицы и фиксированные/обучаемые величины проверяются при первом использовании.

**Формулы и выводы:** `x\in\mathbb{R}^{d_{\mathrm{in}}},\qquad W_0\in\mathbb{R}^{d_{\mathrm{out}}\times d_{\mathrm{in}}},\qquad y_0=W_0x.`; `\begin{gathered}A\in\mathbb{R}^{r\times d_{\mathrm{in}}},\quad B\in\mathbb{R}^{d_{\mathrm{out}}\times r},\quad s=\frac{\alpha}{r},\\\boxed{y=W_0x+sB(Ax)}.\end{gathered}`; `BA=\sum_{k=1}^{r}B_{:,k}A_{k,:}.`

**Разобранный пример:** Пусть x имеет 4096 признаков, а `q_proj` возвращает столько же. Основная ветвь $W_0x$ остаётся. Дополнительная сначала вычисляет восемь промежуточных чисел $h=Ax$, затем разворачивает их в поправку из 4096 чисел $Bh$. Поэтому словосочетание «добавить матрицы» не означает добавить восемь позиций во вход или заменить 4096 чисел всего residual stream восемью. Узкий проход относится к ветви изменения; полный основной путь по-прежнему имеет ширину 4096.

**Схемы:** оформление/course/adapt-lora.svg; проследить вход, все блоки, выход и связи, сверить с описанием.

**Практика:** **Практика:** повторить два шага, затем задать $s=2$ и заново вычислить gradients. Не удваивать только forward: s входит и в derivatives. Основа метода: LoRA; параметры/режимы реализации: PEFT LoRA.

**Ограничения и ошибки:** Это не вставка дополнительных токенов и не отдельная сеть после всего Transformer. Обычно выбранный linear module оборачивается таким путём внутри блока. В row-vector batch convention формула становится $Y=XW_0^\top+sXA^\top B^\top$. Нельзя брать shapes из одного соглашения, а порядок произведения из другого: именно это противоречие было в исходном PDF. Ранг $BA$ не превосходит r. Однако не утверждается, что любое желаемое обновление любой задачи точно низкого ранга: это ограничение пространства доступных изменений, полезность которого проверяется. $r=8$ означает восемь промежуточных координат, а не восемь параметров.

**Критерий понимания:** самостоятельно ответить «Как low-rank ветвь обновляет конкретную линейную проекцию?», воспроизвести пример, назвать нарушение его предпосылки и выбрать корректную единицу оценки.

## DoRA, AdaLoRA, LoRA+ и QLoRA

**Учебный вопрос:** Как различаются изменяемый объект, бюджет ранга и формат хранения базы?

**Результат:** читатель объясняет механизм, воспроизводит числовой пример, называет предпосылку и проверяет её нарушение.

**Уровень:** углубление. **Предпосылки:** adapt-choice, adapt-sft, adapt-lora. **Потребители:** выбранная прикладная задача.

**Порядок объяснения:** DoRA: одна magnitude на выходной канал → Вопрос пользователя: «m — просто число? Размерности не сходятся» → Микромодель из двух выходов → Сохраняем полный DoRA-пример чата с нормированной исходной матрицей → Производная нормированного направления → AdaLoRA: не всем проекциям нужен одинаковый ранг → Сумма rank-one компонентов: что именно маскируют → Полный пример распределения бюджета из S2 → Что измеряет важность и почему одного большого λ недостаточно → Три фазы обучения и исправление tfinal → LoRA+ и вопрос про AdaDoRA → Почему для A и B вообще могут понадобиться разные learning rates → QLoRA: low-bit хранение базы и обучение adapters → Возвращаем вопрос чата: «Если LoRA маленькая, куда делась память базы?» → Коды, уровни и блочный scale на маленьком примере → Постоянная ошибка базы и возможность компенсации → Double quantization: повторяем расчёт и доводим до байтов → Что сравнивать после адаптации и merge → Как различать методы и проверять себя.

**Определения:** построчное; оценками важности; число финальных шагов; NF4; Double quantization; Paged optimizer; не NF4; Как различаются изменяемый объект, бюджет ранга и формат хранения базы?; формы, единицы и фиксированные/обучаемые величины проверяются при первом использовании.

**Формулы и выводы:** `\begin{gathered}V\in\mathbb{R}^{d_{\mathrm{out}}\times d_{\mathrm{in}}},\quad m\in\mathbb{R}^{d_{\mathrm{out}}\times1},\\n_i=\lVert V_{i,:}\rVert_2,\qquad W_{ij}=m_i\frac{V_{ij}}{n_i}.\end{gathered}`; `U=V_0+sBA,\qquad W_{\mathrm{DoRA},i,:}=m_i\frac{U_{i,:}}{\lVert U_{i,:}\rVert_2}.`; `5\begin{bmatrix}0.6&0.8\end{bmatrix}=\begin{bmatrix}3&4\end{bmatrix},\qquad2\begin{bmatrix}0&1\end{bmatrix}=\begin{bmatrix}0&2\end{bmatrix}.`

**Разобранный пример:** Пусть $W_0=\begin{bmatrix}3 & 4\\0 & 2\end{bmatrix}$. Тогда $m=(5,2)^\top $, нормированные направления $\begin{bmatrix}0.6 & 0.8\\0 & 1\end{bmatrix}$. Проверка восстановления:

**Схемы:** оформление/course/adapt-variants.svg; проследить вход, все блоки, выход и связи, сверить с описанием.

**Практика:** **Практика:** для двух проекций 4→4 и 4→10 сравнить uniform ranks $\left(2,\,2\right)$ и $\left(3,\,1\right)$. A/B counts соответственно $16+28=44$ и $24+14=38$: одинаковая сумма rank не означает одинаковую память. Затем восстановить W0 из m/V в DoRA-примере и проверить output на $x=\left(2,\,-1\right)$.

**Ограничения и ошибки:** Связь двух соглашений можно сделать точной. Для $D_m=\operatorname{diag}(5,2)$, $W_0=D_m\widehat V_0$ и заданной дельты BA в нормированных координатах возьмём ненормированную дельту $(D_mB)A$. Тогда $W_0+(D_mB)A=D_m(\widehat V_0+BA)$. Построчная нормировка уберёт положительный множитель m_i, и получатся те же направления. Но присвоить обоим соглашениям буквально один B и ожидать одинаковый forward нельзя. Фиксированная LoRA обычно задаёт один r или заранее выбранную карту рангов. Важность проекций и слоёв может различаться. AdaLoRA учит SVD-подобную параметризацию обновления и распределяет ограниченный бюджет компонентов по важности. Не нужно вычислять точное SVD всей W0 на каждом шаге.

**Критерий понимания:** самостоятельно ответить «Как различаются изменяемый объект, бюджет ранга и формат хранения базы?», воспроизвести пример, назвать нарушение его предпосылки и выбрать корректную единицу оценки.

## Adapters, prefix tuning, soft prompts и BitFit

**Учебный вопрос:** Где добавляются обучаемые параметры и что меняется при inference?

**Результат:** читатель объясняет механизм, воспроизводит числовой пример, называет предпосылку и проверяет её нарушение.

**Уровень:** углубление. **Предпосылки:** adapt-choice, adapt-sft. **Потребители:** выбранная прикладная задача.

**Порядок объяснения:** Adapter layer добавляет обучаемую нелинейную функцию → Почему это отдельный способ адаптации, хотя формы похожи на LoRA → Soft prompt: обучаемые входные векторы → Вопрос чата: почему нельзя просто оптимизировать слова prompt → Prefix tuning: дополнительные K/V в слоях → Что exactly добавлено в attention и какие query остаются → Почему deep prefix нельзя без оговорок свести к input prompt → Цена prefix на inference → BitFit: меняются только bias-параметры → Что делает bias в глубокой сети, кроме последнего сдвига → Как сравнивать методы.

**Определения:** Где добавляются обучаемые параметры и что меняется при inference?; формы, единицы и фиксированные/обучаемые величины проверяются при первом использовании.

**Формулы и выводы:** `\begin{gathered}h\in\mathbb{R}^{D},\quad W_{\mathrm{down}}\in\mathbb{R}^{r\times D},\quad W_{\mathrm{up}}\in\mathbb{R}^{D\times r},\\u=\varphi(W_{\mathrm{down}}h+b_{\mathrm{down}})\in\mathbb{R}^{r},\qquad h_{\mathrm{new}}=h+W_{\mathrm{up}}u+b_{\mathrm{up}}.\end{gathered}`; `\begin{gathered}Q\in\mathbb{R}^{L\times d_k},\quad K_{\mathrm{real}}\in\mathbb{R}^{L\times d_k},\quad V_{\mathrm{real}}\in\mathbb{R}^{L\times d_v},\\K_{\mathrm{prefix}}\in\mathbb{R}^{m\times d_k},\quad V_{\mathrm{prefix}}\in\mathbb{R}^{m\times d_v},\\K_{\mathrm{all}}=\begin{bmatrix}K_{\mathrm{prefix}}\\K_{\mathrm{real}}\end{bmatrix},\quad V_{\mathrm{all}}=\begin{bmatrix}V_{\mathrm{prefix}}\\V_{\mathrm{real}}\end{bmatrix},\quad QK_{\mathrm{all}}^\top\in\mathbb{R}^{L\times(m+L)}.\end{gathered}`

**Разобранный пример:** Пример $D=2$,$r=1$: $W_{\mathrm{down}}=\left(1,\,-1\right)$, $W_{\mathrm{up}}=[0.5,1]^\top $, φ=ReLU. Для h=(3,1) bottleneck равен 2, поправка (1,2), результат (4,3). Для h=(1,3) bottleneck 0, результат прежний. Из-за ReLU нельзя в общем случае свернуть всю функцию в одну постоянную матрицу, одинаковую для всех h. Поэтому обычный nonlinear adapter не merge-ится так же, как линейная LoRA.

**Схемы:** оформление/course/adapt-alternatives.svg; проследить вход, все блоки, выход и связи, сверить с описанием.

**Практика:** **Практика:** нарисовать для $L=3$,$m=2$ форму attention scores $3\times 5$ с prefix K/V. Отдельно выписать форму soft-prompt входа $5\times D$. Посчитать budget обеих схем для $N=4$,$D=16$ без biases/reparameterization.

**Ограничения и ошибки:** В S3 adapter описан как down→nonlinearity→up. Его bottleneck напоминает факторы LoRA, но объект входа и место residual принципиальны. LoRA меняет выбранный linear W0x внутри блока. Nonlinear adapter получает representation h и возвращает h+g(h). В зависимости от design его ставят после attention, после MLP или в другой residual branch. Нельзя по одной паре down/up заключить, что эти методы имеют одинаковую функцию. Если φ — identity и biases нулевые, adapter действительно становится $(I+W_up W_down)h$, то есть линейной residual correction. При ReLU область активных channels зависит от h. В примере [3,1] и [1,3] один и тот же module в первом случае меняет обе координаты, во втором выключается. Одна постоянная ΔW не воспроизведёт все такие переключения, если нет дополнительных ограничений.

**Критерий понимания:** самостоятельно ответить «Где добавляются обучаемые параметры и что меняется при inference?», воспроизвести пример, назвать нарушение его предпосылки и выбрать корректную единицу оценки.

## RLHF, PPO, DPO, IPO, KTO и ORPO

**Учебный вопрос:** Как предпочтения превращаются в objective и каких данных он требует?

**Результат:** читатель объясняет механизм, воспроизводит числовой пример, называет предпосылку и проверяет её нарушение.

**Порядок объяснения:** Что содержится в preference dataset → Разница между demonstration и сравнением → Reward model и классический RLHF → Почему Bradley–Terry использует разность scores → PPO: от sampled ответа к обучающему сигналу → От KL-regularized optimum к DPO → Откуда взялся exponential optimum → Margin может улучшиться при падении chosen probability → IPO, KTO и ORPO: не один и тот же dataset/loss → Уточнение пользовательского запроса: «подробнее IPO и KTO» → ORPO и смысл объединённого обучения → Как выбирать данные и проверять результат → Контроль понимания и эксперимент.

**Определения:** current policy; old rollout policy; reference; reward; value estimate; margin; IPO; KTO; ORPO; Как предпочтения превращаются в objective и каких данных он требует?; формы, единицы и фиксированные/обучаемые величины проверяются при первом использовании.

**Формулы и выводы:** `P(y_w\succ y_l\mid x)=\sigma(r_w-r_l),\qquad\mathcal{L}_{\mathrm{RM}}=-\log\sigma(r_w-r_l).`; `\max_\pi\;\mathbb{E}_{y\sim\pi(\cdot\mid x)}[r(x,y)]-\beta\,D_{\mathrm{KL}}\!\left(\pi(\cdot\mid x)\,\Vert\,\pi_{\mathrm{ref}}(\cdot\mid x)\right).`; `\min\!\left(\rho A,\;\operatorname{clip}(\rho,1-\varepsilon,1+\varepsilon)A\right).`

**Разобранный пример:** **Reward hacking:** policy может повышать RM score за счёт длины или шаблонов, а истинное task quality не растёт. Контроль — независимая оценка, аудит reward correlations, проверка shifts и ограничение update; один KL не доказывает отсутствие проблемы. Исторический пример пайплайна: InstructGPT.

**Практика:** **Практика:** пересчитать пример с $\beta=0.2$, затем поменять chosen/rejected местами. Проверить, что delta меняет знак и loss растёт. Для небольшого обучения сравнить baseline и DPO на одних prompts, срезах длины и factual tasks; проследить одновременно train margin, validation margin, chosen/rejected log-probs и task success. Все числа выше — ручные примеры, не результаты вашего запуска.

**Ограничения и ошибки:** Разделять данные нужно по prompts/семействам задач/источникам. Если ответы на один и тот же вопрос попали в train и validation, оценка переноса на новые вопросы будет завышена. Собранные прежней policy ответы также задают ограниченную область feedback: новая policy может генерировать совсем другие ответы. В PPO есть **current policy**, **old rollout policy**, **reference**, **reward** и **value estimate** как логические роли. Old policy нужна для importance ratio, reference — для удержания поведения; их нельзя без объяснения считать одним объектом. Некоторые роли используют общие backbones, adapters, precomputed values или другие размещения. Из схемы не следует требование держать четыре полных независимых 7B-модели на одном GPU.

**Критерий понимания:** самостоятельно ответить «Как предпочтения превращаются в objective и каких данных он требует?», воспроизвести пример, назвать нарушение его предпосылки и выбрать корректную единицу оценки.

## Дистилляция и обучение на траекториях

**Учебный вопрос:** Какой сигнал teacher передаёт student и как проверить перенос?

**Формулы и выводы:** `\begin{gathered}p_T^{(T)}=\operatorname{softmax}\!\left(\frac{z_T}{T}\right),\qquad p_S^{(T)}=\operatorname{softmax}\!\left(\frac{z_S}{T}\right),\\\mathcal{L}_{\mathrm{soft}}=T^2D_{\mathrm{KL}}\!\left(p_T^{(T)}\,\Vert\,p_S^{(T)}\right).\end{gathered}`; `\mathcal{L}=(1-\alpha)\mathcal{L}_{\mathrm{task}}+\alpha\mathcal{L}_{\mathrm{soft}},\qquad0\le\alpha\le1.`; `D_{\mathrm{KL}}=0.8\ln\frac{0.8}{0.6}+0.2\ln\frac{0.2}{0.4}\approx0.091516.`

**Разобранный пример:** Soft targets полезны тем, что различают альтернативы. Например, hard target $\left(1,\,0,\,0\right)$ говорит «первый класс», а teacher $\left(0.7,\,0.25,\,0.05\right)$ дополнительно задаёт относительное сходство/неуверенность. Однако это **модельные** альтернативы: teacher может быть неправильно уверен. Их имитация не гарантирует правильное причинное понимание.

**Схемы:** оформление/course/adapt-distillation.svg; проследить вход, все блоки, выход и связи, сверить с описанием.

**Практика:** **Практика:** пересчитать KL-пример, затем заменить student на $\left(0.8,\,0.2\right)$ и получить нулевой KL. Спроектировать сравнение трёх alpha schedules с независимым holdout. Выписать отдельно teacher data generation cost, student training cost и inference cost успешного решения.

**Ограничения и ошибки:** В примере чата с классификацией животных hard label «кошка» не показывает, какие альтернативы teacher считает правдоподобными. Soft targets дают распределение по всем классам. Но оно не является чистой картой семантического сходства: на probabilities влияют данные, calibration и ошибки. Если у «тигра» и «птицы» одинаковая вероятность0.01, нельзя по этому примеру утверждать, что tiger получил больший сигнал близости к кошке. Нужно читать фактические числа, а не желаемую историю. Hidden-state distillation требует согласовать shapes. Для teacher hidden width 1024 и student 512 иногда используют проекцию/выбор слоёв. Просто вычесть tensors несовместимой ширины нельзя; даже одинаковая ширина не означает одинаковые координаты.

## Оценка, perplexity, judge и экспорт

**Учебный вопрос:** Как сравнить candidate с baseline и подтвердить сохранение поведения после экспорта?

**Результат:** читатель объясняет механизм, воспроизводит числовой пример, называет предпосылку и проверяет её нарушение.

**Уровень:** основа ветки. **Предпосылки:** adapt-choice, adapt-sft. **Потребители:** выбранная прикладная задача.

**Порядок объяснения:** Один score не отвечает на все вопросы → От пользовательской задачи к проверяемому протоколу → Где полезна perplexity → Что именно усредняется в loss и perplexity → Прямое сравнение baseline и candidate → Парные различия, неопределённость и выбор модели → Люди и LLM-as-a-judge → Судье тоже нужен контракт входа и выходной оценки → Contamination, alignment tax и честный вывод → False refusals и contamination требуют разных проверок → Экспорт входит в оценку.

**Определения:** выбранного; выбранной; загруженный итоговый artifact; Как сравнить candidate с baseline и подтвердить сохранение поведения после экспорта?; формы, единицы и фиксированные/обучаемые величины проверяются при первом использовании.

**Формулы и выводы:** `\begin{aligned}\mathrm{WR}_{\mathrm{half\text{-}ties}}&=\frac{45+\tfrac12\cdot20}{100}=55\%,\\\mathrm{WR}_{\mathrm{non\text{-}ties}}&=\frac{45}{80}=56.25\%.\end{aligned}`

**Разобранный пример:** В S3 evaluation появляется после длинного списка методов, но выбирать критерий нужно до их применения. Например, для извлечения даты из договора есть три разных результата: ответ разбирается как JSON; поле действительно содержит дату; дата относится к требуемому событию, а не к подписанию другого документа. Обучение только на первом критерии может улучшить format score при неизменной фактической ошибке. Изменения нужно видеть по отдельности.

**Схемы:** оформление/course/adapt-evaluation.svg; проследить вход, все блоки, выход и связи, сверить с описанием.

**Практика:** **Практика:** спроектировать 20 regression prompts по 4 срезам и рубрику. Для условного результата 45/35/20 вручную посчитать две tie conventions. Никаких реальных метрик обучения в этой главе не заявлено: все числа иллюстративные.

**Ограничения и ошибки:** Успешный JSON parser не доказывает правильные поля. HTTP 200 от tool не доказывает достижение пользовательской цели. Красивый длинный ответ не гарантирует правильный факт. Поэтому нужно сохранять outputs и типы ошибок, а не только общий процент. После этого определяют допустимую информацию и бюджет. Сравнение модели с retrieval и модели без него измеряет целую систему. Если candidate получает правильный source passage, а baseline ищет его самостоятельно, разницу нельзя приписать только fine-tuning. Так же сохраняют одинаковые ограничения tools, число попыток и условия остановки. Разный бюджет допустим, если вопрос именно в качестве на единицу стоимости и это явно показано.

**Критерий понимания:** самостоятельно ответить «Как сравнить candidate с baseline и подтвердить сохранение поведения после экспорта?», воспроизвести пример, назвать нарушение его предпосылки и выбрать корректную единицу оценки.

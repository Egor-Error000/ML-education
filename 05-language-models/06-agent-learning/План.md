## Постановка обучения агента и baseline

**Учебный вопрос:** Как выбрать вмешательство по измеренному типу ошибки?

**Результат:** читатель объясняет механизм, воспроизводит числовой пример, называет предпосылку и проверяет её нарушение.

**Уровень:** основа ветки. **Предпосылки:** app-state, app-evaluation. **Потребители:** agent-environment.

**Порядок объяснения:** Цикл начинается с задачи и оценки → От этапов из разбираемого примера к управляемому циклу → Сначала задаём observable success → Failure trace важнее догадки по последней фразе → Что меняет каждое вмешательство → Prompt/schema/runtime и обучение дают разные типы изменений → Пять failures: что проверить и как опровергнуть выбор → Локальный ceiling вмешательства и interactions → Когда результат требует именно последовательного поведения → Сопоставимый baseline и стоимость → Сравнение вмешательств при заданных constraints → Training cost и горизонт использования → Веса, loss и task metrics → Какие артефакты связывают этапы → Version bundle связывает доказательство и исполняемый candidate → Offline test, integration и rollout проверяют разные вещи → Monitoring → новые данные → снова независимая проверка → Учебный маршрут к следующим главам → Самопроверка и упражнение.

**Определения:** не считается; какие параметры и как; Нет нового правила в доступном corpus.; Найдена v7 вместо v8.; Malformed tool arguments.; Повтор операции после timeout.; Неверный следующий шаг при правильных observations.; Как выбрать вмешательство по измеренному типу ошибки?; формы, единицы и фиксированные/обучаемые величины проверяются при первом использовании.

**Формулы и выводы:** `\max_{\text{system}}\;\mathbb{E}[\mathrm{success}] \quad\text{при}\quad \mathbb{E}[C]\le B_C,\qquad P(T> B_T)\le\varepsilon_T.`

**Разобранный пример:** При одинаковом условном качестве/прочих требованиях пусть подготовка+обучение+evaluation стоят F=600units, inference baseline0.10units/request, candidate0.08. Формальный break-even по этой упрощённой цене —$N_*=600/(0.10-0.08)=30000$ requests. При 15000 requests baseline1500units, candidate1800; при 100000 —10000 против 8600.

**Схемы:** оформление/course/agent-task.svg; проследить вход, все блоки, выход и связи, сверить с описанием.

**Практика:** **Практика:** взять пять условных failures и назначить layer/hypothesis: missing knowledge, wrong source version, malformed args, повтор после timeout, неверный вывод при верном evidence. Для каждого выбрать одну проверяемую intervention и результат, который опроверг бы гипотезу. Не назначать SFT/RL автоматически всем случаям.

**Ограничения и ошибки:** Для дальнейших глав удобно мыслить системой из компонентов: параметры θ, prompt/template P, данные/corpus D, retriever/index R, tool/environment E, control flow G, memory M и budget B. Пользователь видит результат совместного исполнения. Одинаковая θ не означает одинаковые ответы при других D/P/E, а новая θ не гарантирует, что исправлена ошибка в G. Версия системы должна фиксировать существенные компоненты, иначе сравнение неинтерпретируемо. Сначала выбирают unit оценки: independent task с initial state и stop condition. Отдельные messages/calls становятся диагностическими units. Затем выбирают task families, source/time/group split и критерии final outcome. Нельзя обещать качество на будущих данных по одной тренировочной траектории, даже если она полностью понятна и воспроизводима.

**Критерий понимания:** самостоятельно ответить «Как выбрать вмешательство по измеренному типу ошибки?», воспроизвести пример, назвать нарушение его предпосылки и выбрать корректную единицу оценки.

## Среда, observations, actions и horizon

**Учебный вопрос:** Как описать доступную агенту информацию и последствия действия?

**Результат:** читатель объясняет механизм, воспроизводит числовой пример, называет предпосылку и проверяет её нарушение.

**Уровень:** основа ветки. **Предпосылки:** agent-task. **Потребители:** agent-evaluation.

**Порядок объяснения:** Состояние мира и доступное наблюдение → Что делает задачу последовательной → Markov property и частичная наблюдаемость → Search получает информацию, хотя не меняет corpus → Конкретная маленькая среда → Полностью задаём игрушечную среду → Три траектории с разными outcomes → Reset, seeds и сопоставимость episodes → Return и delayed credit → Reward, outcome и стоимость —не одно поле → Discount меняет цель и credit ранних шагов → Слишком большая step cost и reward hacking → Termination и budgets → Естественный terminal state и внешнее обрезание → Три бюджета и зависимые действия → Запрос недостающей информации как action → Trajectory data и split → Что сохранять на границе environment и policy → Самопроверка.

**Определения:** без числа дней; что; как; встроенного; Как описать доступную агенту информацию и последствия действия?; формы, единицы и фиксированные/обучаемые величины проверяются при первом использовании.

**Формулы и выводы:** `h_t=(o_1,a_1,o_2,a_2,\ldots,o_t),\qquad a_t\sim\pi_\theta(\cdot\mid h_t).`; `s_{t+1}\sim P(\cdot\mid s_t,a_t),\quad o_{t+1}\sim O(\cdot\mid s_{t+1},a_t),\quad r_t=R(s_t,a_t,s_{t+1}).`; `b_{t+1}(s')\propto O(o_{t+1}\mid s',a_t)\sum_s P(s'\mid s,a_t)b_t(s).`

**Разобранный пример:** Пример: observation «найден report-policy» одинаков у двух задач, но в одной active revision v1, в другой v2. Если metadata скрыты, policy должна получить дополнительное evidence. Никакой classifier по одной этой фразе не различит два мира с гарантией. Если revision известна, а summary её потерял, это уже искусственно созданная неполнота памяти.

**Схемы:** оформление/course/agent-environment.svg; проследить вход, все блоки, выход и связи, сверить с описанием.

**Практика:** **Практика:** записать три toy trajectories: success через current v2, failure через stale v1 и recovery после search timeout. Для каждой указать observations, действия, return, termination и какой feedback доступен для обучения. Начать с этих записей, не с большого RL запуска.

**Ограничения и ошибки:** Model context — ограниченное представление этой истории, не обязательно полный $h_t$. Truncation/summary могут потерять information. Важно различать hidden state среды и скрытые нейросетевые activations: это разные смыслы слова state. В разбираемом примере tool loop описан как «модель предложила вызов → программа выполнила → observation вернулся модели». Для обучения нужно дополнительно определить, какую задачу решает вся последовательность и какие сведения доступны на каждом шаге. Без этого нельзя отличить правильный action от правдоподобного текста, который случайно совпал с ответом.

**Критерий понимания:** самостоятельно ответить «Как описать доступную агенту информацию и последствия действия?», воспроизвести пример, назвать нарушение его предпосылки и выбрать корректную единицу оценки.

## Оценка траекторий и воспроизводимость

**Учебный вопрос:** Что считать успехом целой попытки и как учитывать retries и стоимость?

**Результат:** читатель объясняет механизм, воспроизводит числовой пример, называет предпосылку и проверяет её нарушение.

**Уровень:** основа ветки. **Предпосылки:** agent-environment. **Потребители:** agent-demonstrations, agent-recovery, agent-rl, agent-reasoning, agent-memory, agent-preferences, agent-coordination.

**Порядок объяснения:** Проверяемый успех вместо впечатления → Task, run, attempt, action и candidate → Deadline, unknown и partial → Recovery, loops и остановка → Retry не обязательно loop → Полный журнал десяти учебных sessions → Считаем разные outcomes → Сколько стоит успешная задача → Цена учебного журнала → Fixed budget и сравнение вмешательств → Latency и timeouts → Split, seeds и статистическая неопределённость → Две оси variation → Ноль ошибок не доказывает нулевой риск → Подбор по test и независимый вывод → Итоговый учебный эксперимент → Benchmarks, оценивающие всю траекторию инструмента → Контроль и практика.

**Определения:** Что считать успехом целой попытки и как учитывать retries и стоимость?; формы, единицы и фиксированные/обучаемые величины проверяются при первом использовании.

**Формулы и выводы:** `\widehat S=\frac1n\sum_{i=1}^{n}\mathbf1[\text{oracle подтвердил успех задачи }i].`; `\widehat R_{\mathrm{recovery}}= \frac{\text{успешные задачи после заданного восстановимого сбоя}} {\text{задачи с таким сбоем}}.`; `C_{\mathrm{per\ success}}=\frac{\sum_i C_i}{\sum_i S_i}.`

**Разобранный пример:** В числителе остаются затраты failures. Например, 100 units при 40 успешных tasks дают 2.5 units/success. При нуле successes показатель не равен нулю: он не определён либо отображается как бесконечный по выбранной convention.

**Схемы:** оформление/course/agent-evaluation.svg; проследить вход, все блоки, выход и связи, сверить с описанием.

**Практика:** **Практика:** воспроизвести расчёты десяти sessions, затем изменить один outcome или cost и пересчитать success, validity, recovery и cost per success. Спроектировать comparison двух policies с одинаковым budget; указать, какие выводы десять задач ещё не поддерживают. Реальные metrics заявляются только после запуска соответствующего experiment.

**Ограничения и ошибки:** Unknown и partial можно считать неуспехом в конкретной binary metric, одновременно показывая их частоты отдельно. Нельзя удалить все engine errors и показать accuracy только для sessions с полученным ответом как качество всей системы. Нельзя вывести «задача решена» из того, что процесс достиг END. Чтобы проверить эффект обучения или координации, сравнивают также при сопоставимом inference budget. Чтобы выбрать целую систему, задают constraints или cost-quality curve. Прирост от трёх попыток нельзя целиком приписать новым weights, если baseline получила одну.

**Критерий понимания:** самостоятельно ответить «Что считать успехом целой попытки и как учитывать retries и стоимость?», воспроизвести пример, назвать нарушение его предпосылки и выбрать корректную единицу оценки.

## Behavior cloning и SFT на демонстрациях

**Учебный вопрос:** Как из траектории получить targets для обучения политики?

**Результат:** читатель объясняет механизм, воспроизводит числовой пример, называет предпосылку и проверяет её нарушение.

**Уровень:** основа ветки. **Предпосылки:** agent-evaluation, adapt-sft. **Потребители:** agent-recovery.

**Порядок объяснения:** Что является supervised target → Из instruction-response в history-action → Teacher forcing по траектории → Три decisions и простая likelihood арифметика → Нормировка задаёт относительное влияние sessions → Какие demonstrations нужны → Полная demonstration с наблюдаемыми границами → Recovery data должна показывать причину выбора → Нет единственной правильной search строки → Книги и диалоги как обучающие данные → Template, masks и dependency boundaries → Assistant-only loss не означает удаление tool result → Causal shift на десяти условных tokens → Templates, markers и непрозрачные IDs → Packing, truncation и границы episodes → Первый training experiment → До optimizer: inspect, replay и крошечный overfit check → Оценка policy отдельно от обучения на красивых messages → Почему выученное поведение не заменяет runtime invariant → Вопросы и практика.

**Определения:** настоящее; все; Как из траектории получить targets для обучения политики?; формы, единицы и фиксированные/обучаемые величины проверяются при первом использовании.

**Формулы и выводы:** `\mathcal{L}_{\mathrm{BC}}= -\frac{1}{Z}\sum_{\tau\in\mathcal D}\sum_t\sum_{j=1}^{m_t} w_{t,j}\log\pi_\theta(a_{t,j}\mid h_t,a_{t,<j}).`

**Разобранный пример:** Пусть trajectory A имеет 2 active tokens со средним loss0.2, B —8 active tokens со средним loss1.2. Token-average loss=(2·0.2+8·1.2)/10=1.0. Если усреднить сначала внутри каждой trajectory, затем по двум trajectories, получится 0.7. В первом objective B получает 80% token weight, во втором обе sessions равный вес.

**Схемы:** оформление/course/agent-demonstrations.svg; проследить вход, все блоки, выход и связи, сверить с описанием.

**Практика:** **Практика:** размечать assistant/tool roles и loss positions в трёх trajectories предыдущей главы. Добавить one recovery path и one no-tool-needed case. Сформулировать oracle для action semantics и final state; затем спроектировать small SFT comparison, не заявляя numerical results до запуска.

**Ограничения и ошибки:** S3 объяснял SFT как demonstrations полезных ответов, а S6 —tool loop с реальными observations. Их соединение даёт training unit: доступная history → очередной допустимый action. Это новое agentic углубление по плану. Нельзя из него заключить, что исходные чаты уже содержали выполненное обучение агента. При training очередной target token предсказывается при известных предыдущих tokens правильной demonstration. Для следующего action в prefix уже включено **настоящее** tool observation этой trajectory. Во время rollout предыдущие actions генерирует сама policy, поэтому history может отличаться. Это источник train/inference mismatch, а не ошибка teacher forcing как арифметической операции.

**Критерий понимания:** самостоятельно ответить «Как из траектории получить targets для обучения политики?», воспроизвести пример, назвать нарушение его предпосылки и выбрать корректную единицу оценки.

## Distribution shift, recovery и DAgger

**Учебный вопрос:** Как научиться действовать в состояниях, порождённых собственными ошибками?

**Уровень:** основа ветки. **Предпосылки:** agent-evaluation, agent-demonstrations. **Потребители:** agent-rl.

**Порядок объяснения:** У данных есть распределение состояний → Почему iid minibatch не делает rollout iid задачей → Как накапливаются ошибки: допущения и границы вывода → Маленький distribution-shift пример → Как работает агрегирование данных → Исполненное действие и экспертный label —два отдельных объекта → Один раунд сбора по шагам → Mixture β и почему assisted rollout не равен student evaluation → Агрегирование, sampling и устаревшие labels → Привилегированный expert и реализуемость policy → Разобранная recovery-траектория → Два fictional policy примера и общий read-only corpus → После timeout, denied и необратимого effect → Когда добавление coverage не помогает → Как сравнивать честно → Controlled comparison и независимый final test → Контроль и практика.

**Определения:** той же; действительно выполненного; Как научиться действовать в состояниях, порождённых собственными ошибками?; формы, единицы и фиксированные/обучаемые величины проверяются при первом использовании.

**Формулы и выводы:** `\mathbb E_{h\sim d_{\pi_E}}[\ell(\pi_\theta(h),\pi_E(h))] \quad\text{и}\quad \mathbb E_{h\sim d_{\pi_\theta}}[\ell(\pi_\theta(h),\pi_E(h))]`; `P(\text{ошибка в сессии})=1-(1-\varepsilon)^H.`; `\mathcal D_{i+1}=\mathcal D_i\cup \{(h,\pi_E(h)):h\text{ посещена на итерации }i\}.`

## Обучение через взаимодействие: PPO и GRPO

**Учебный вопрос:** Как отложенный reward меняет вероятность последовательности действий?

**Результат:** читатель объясняет механизм, воспроизводит числовой пример, называет предпосылку и проверяет её нарушение.

**Уровень:** основа ветки. **Предпосылки:** agent-evaluation, agent-recovery. **Потребители:** выбранная прикладная задача.

**Порядок объяснения:** Что оптимизирует политика → Rollout → reward → update: что меняется между итерациями → Уточняем discount в policy gradient → Микромодель gradient с двумя macro actions → Advantage и отложенный результат → Почему baseline не должен зависеть от sampled action → Temporal differences и GAE на трёх шагах → Terminal reward не доказывает полезность каждого token → Зачем PPO ограничивает обновление → Old policy, current policy и reference → PPO clipping со знаками advantage → Token ratios и длинная trajectory → Group-relative advantage в GRPO → Группа должна отвечать одной сопоставимой задаче → Один success в группе и нулевая variance → Length weighting, masks и варианты реализации → Exact KL и sampled terms → Reward hacking и toy experiment → Возвращаемся к RLHF source: четыре роли не обязательные четыре GPU-копии → Что проверять до объявления успеха RL → Исследовательский пример многошагового RL: AgentGym-RL → Контроль и практика.

**Определения:** Как отложенный reward меняет вероятность последовательности действий?; формы, единицы и фиксированные/обучаемые величины проверяются при первом использовании.

**Формулы и выводы:** `G_t=\sum_{k=t}^{T-1}\gamma^{k-t}r_k, \qquad J(\theta)=\mathbb E_{\tau\sim\pi_\theta}[G_0].`; `\nabla_\theta J(\theta)= \mathbb E\left[\sum_t \gamma^tG_t\nabla_\theta\log\pi_\theta(a_t\mid h_t)\right].`; `A_t=G_t-b(h_t).`

**Разобранный пример:** При $\gamma=1$ и конечном горизонте все будущие rewards имеют одинаковый временной вес. Если нужен штраф за каждый tool call, его лучше явно включить в reward или ограничение, а не надеяться, что discount точно выразит стоимость. Например, успешная сессия с тремя вызовами при награде за успех 1 и штрафе $0.05$ за вызов получает $0.85$. Неуспешная без вызовов получает 0. Если штраф чрезмерен, политика может предпочесть ничего не делать; objective тогда расходится с намерением пользователя.

**Схемы:** оформление/course/agent-rl.svg; проследить вход, все блоки, выход и связи, сверить с описанием.

**Практика:** **Практика:** вычислите advantages для $(0,0,0,0)$, $(1,1,0,0)$ и $(1,1,1,1)$. Предложите две policy, одна из которых получает высокий плохо заданный reward без выполнения задачи. Исправьте oracle и составьте план сравнения, включающий затраты неудачных rollouts.

**Ограничения и ошибки:** Нельзя оптимизировать правдоподобие наблюдений базы данных так, будто их сгенерировала политика. Для LLM log-probability действия — сумма log-probabilities его tokens, обусловленных реальным context. Где закончился action и началось observation, определяет сериализация. Для objective $J=\mathbb E[\sum_t\gamma^t r_t]$ и обычного суммирования по временным позициям trajectory корректный score-function expression содержит $\gamma^tG_t$. Иногда формулы без этого множителя используют γ=1 или иначе взвешенное state distribution; эти conventions нельзя молча смешивать. В этой главе формула выше приведена к explicit discounted-return convention.

**Критерий понимания:** самостоятельно ответить «Как отложенный reward меняет вероятность последовательности действий?», воспроизвести пример, назвать нарушение его предпосылки и выбрать корректную единицу оценки.

**Учебный вопрос:** Когда дополнительный поиск и проверка улучшают результат?

**Результат:** читатель объясняет механизм, воспроизводит числовой пример, называет предпосылку и проверяет её нарушение.

**Формулы и выводы:** `\mathcal L_{\mathrm{verifier}}= -\frac1M\sum_{i=1}^M \bigl[y_i\log v_\phi(z_i)+(1-y_i)\log(1-v_\phi(z_i))\bigr].`; `P(\text{успех хотя бы одного})=1-(1-p)^N.`; `C(N)=N(c_g+c_v)+c_{\mathrm{selection}}.`

**Разобранный пример:** В STaR модель итеративно генерирует рассуждения и обучается на отобранных примерах; используется также генерация объяснения с подсказанным правильным ответом для первоначально неуспешных задач. Это полезный способ собирать данные, но знание ответа при генерации нельзя тайно переносить в inference benchmark. На тесте ответ неизвестен.

**Ограничения и ошибки:** Filtering только по final answer сохраняет и cases с ошибочными промежуточными объяснениями. Filtering только по syntax сохраняет бессмысленный valid JSON. Поэтому retained data quality зависит от полноты oracle и labels. Дешёвый validator может давать полезный первый фильтр, но его ограниченность должна быть видна в итоговом протоколе. В STaR правильный answer используется при рационализации первоначально неудачных training cases; затем модель обучается на отобранных объяснениях. Это supervision, а не доступный на test магический ресурс. В STaR paper этот итеративный цикл заявлен явно. При evaluation нельзя давать generator hidden answer и затем сравнивать с baseline без такой подсказки.

**Ограничения и ошибки:** Если агенты имеют политики $\pi_{\theta_1},\ldots,\pi_{\theta_K}$, совместное поведение определяется ещё и правилами передачи сообщений.
